# MuscleMap body geometry

The real-anatomy SVG artwork behind Train's muscle map (`BodyMap`/`MuscleChip`, Titanium T3,
`mezo-88iwa.4`) — front/back human silhouettes broken into named muscle shapes, heat-colored per
training load. Not an ingested article: the source is a live upstream repository, vendored
directly into the tree (see [NOTICE.md](../../NOTICE.md) at the repository root), so `sources` is
empty and this page instead cites the vendored paths.

## What it is and where it came from

Two Swift source files — `MaleFrontPaths.swift` (28 shapes) and `MaleBackPaths.swift`
(16 shapes) — vendored verbatim under `scripts/vendor/musclemap/` from
[MuscleMap](https://github.com/melihcolpan/MuscleMap), Copyright (c) Melih Colpan, **MIT
License**. Each file is a list of `BodyPartPathData` entries: a `slug` (e.g. `.chest`,
`.tibialis`) plus one or more SVG-style path strings tracing that muscle's outline.

**The MIT/AGPL distinction matters and is deliberate.** The same anatomy artwork also circulates,
converted, inside **openGym**, which is **AGPL-3.0**. AGPL's copyleft would force any code that
links against it to also be AGPL — unacceptable for mezo's proprietary frontend. The Train
Titanium openGym-audit handoff named MuscleMap specifically as the "safe upstream": geometry is
taken **only** from `github.com/melihcolpan/MuscleMap` `Sources/MuscleMap/Data/*.swift`, **never**
from openGym's own `body-paths.js`. openGym was consulted for *behaviour* (which muscles get
grouped, how a body map like this is typically presented) but no openGym source was copied — see
the closing line of [NOTICE.md](../../NOTICE.md).

## How the generator works

`scripts/gen-body-geometry.mjs` (committed, run on demand — not a build step) turns the two Swift
files into `frontend/src/features/train/logic/bodyGeometry.gen.ts`, a generated module carrying,
per view (`front`/`back`), a viewBox string and a `slug → path[]` / `slug → bbox` map. Three
stages:

1. **`parse()`** splits each Swift file on `BodyPartPathData(`, pulls the `slug:` enum case and
   every quoted path string, and kebab-cases the slug (`hipFlexors` → `hip-flexors`).
2. **`bbox()`** walks each path's drawing cursor to compute a per-shape bounding box, used for
   viewBox sizing and (in later Train tasks) `MuscleChip`'s zoom-crop anchor.
3. The module is written with a `// Generated by scripts/gen-body-geometry.mjs — do not
   hand-edit.` banner and a `--check` flag that regenerates to a temp buffer and diffs it against
   the committed file, so CI/local runs can assert the generator and its output never drift.

**Two bugs were found and fixed against the source repo's own vendored data while building this**
(Task 1 of this slice, see `.superpowers/sdd/2026-09-15-train-titanium-t3-body-geometry/task-1-report.md`):

- **Bounding-box collapse on relative paths.** The straightforward approach — record only
  absolute (uppercase) `M`/`L`/`C`/... anchors — assumes every shape's extremes are pinned by an
  absolute command. That's false for 33 of the 44 shapes across both views (`tibialis`,
  `hip-flexors`, `upper-chest`, `front-deltoid`, `head`, …), whose entire outline after the
  opening `M` is drawn in **relative** (lowercase) commands: they collapsed to a zero-size
  `[x, y, 0, 0]` bbox. The fix walks the cursor through *both* absolute and relative commands
  (tracking current position like an SVG renderer would), recording endpoints and control points
  as a safe over-approximation of the true bezier bounding box.
- **Adjacent-decimal tokenization.** MuscleMap's compact path data sometimes writes two numbers
  back-to-back with no separator between a trailing and a leading decimal point, e.g. `37.02.75`
  meaning `37.02` then `.75`. A naive `-?[\d.]+` number regex swallows both dots into one `NaN`
  token. The fix uses a decimal-aware alternation
  (`-?\d*\.\d+(?:[eE][-+]?\d+)?|-?\d+(?:[eE][-+]?\d+)?`) that splits the two numbers correctly.

Both fixes only change *derived* bbox math — no vendored path data was altered. Post-fix, all 44
shape bboxes (28 front + 16 back) have positive, finite width/height, and `--check` confirms the
generator is idempotent.

## Why the arm mapping is lossy

Train's own 21-token muscle taxonomy (biceps, triceps, front-delt, side-delt, rear-delt, …) is
finer-grained than MuscleMap's drawn shapes in the arm region: several of our tokens land on the
*same* MuscleMap shape (there is one drawable "upper arm" outline behind what our taxonomy splits
into separate front/side/rear deltoid and biceps/triceps tokens). Per the Train Titanium T3 plan's
global constraint, this is handled by **summing** every co-located token's training load onto that
one shape rather than guessing a finer split that doesn't exist in the source artwork — so an arm
shape's heat color reflects the combined load of every token mapped to it, not any single muscle's
load in isolation. Nothing is invented: an unmapped token is simply dropped, never approximated
onto a shape it doesn't belong to.

## Female-view deferral

MuscleMap upstream ships a second, symmetric set of path files — `FemaleFrontPaths.swift` /
`FemaleBackPaths.swift` — under the same MIT terms as the male paths vendored here. Train
Titanium's frozen coverage manifest
([`docs/design_2.0/2026-09-12-train-coverage.md`](../design_2.0/2026-09-12-train-coverage.md),
"Still open") lists the female body view explicitly: geometry exists upstream and could be vendored
the same way, but it was **deliberately deferred** rather than built speculatively — it is a bd
triage item on the manifest's open list, not part of this slice's committed scope. The generator
and generated-module shape (`BODY: Record<BodyView, …>`) already anticipate a second view being
added the same way front/back were, when that triage item is picked up.
