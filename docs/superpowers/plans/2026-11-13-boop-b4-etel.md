# Boop B4 — Étel implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Build the complete Étel room of Boop (inner tabs `Ma · Receptek · Kamra · Hét`) on the existing food
backend, adding a sensitivity model, a server-side day plan with budget and next-meal tip, barcode scanning,
recipe import, stored meal photos and an editable supplement stack — everything capturing offline.

**Architecture:** Backend first, contract-first: new columns and endpoints in `pantry`, `recipe`, `nutrition`,
`meal`; the web frontend's day planner is ported into a new server-side planner service that also feeds Boop's
brief. Then iOS: the food operations enter the BoopAPI generator filter, a `FoodClient` + models land in
`BoopCore` with `StubTransport` tests, and the room is built from the Napkelte kit's `NKDrillPage(tabs:)`,
reusing B3's `Outbox`/`DayLedger` for offline capture.

**Tech Stack:** Spring Boot + Liquibase + OpenAPI-generated controllers (Java 21), PostgreSQL;
SwiftUI / Swift 6, VisionKit `DataScannerViewController`, swift-openapi-generator.

**Spec:** `docs/superpowers/specs/2026-11-13-boop-b4-etel-design.md` (owner-approved decisions 8–21 in §2;
parent `docs/superpowers/specs/2026-11-11-boop-standalone-design.md` §3.1).

## Global Constraints

- **B3 must be on main before Task 1 starts** (`mezo-r36n9.13` owns `api/openapi.yml`, `merge.yml`,
  `1.1.0_master.yml`, `ResetDatabase.java`, `openapi-generator-config.yaml`, `CaptureSheet.swift`,
  `BoopDayAssembler.java`). Rebase on main immediately before each merge.
- **Contract first:** every endpoint is defined in `api/feature/<x>/*.yml`, merged through `api/generate/merge.yml`,
  and the controller implements the generated `*Api` (ArchUnit `controllers_implement_generated_api`).
- **Feature slices stay cycle-free** (ArchUnit, frozen); no class-level `@Transactional`.
- **Numbers never come from the LLM.** Macros come from DB rows; LLM output is prose or a draft the owner confirms.
- **Napkelte look only** (dark glass, painted sky, serif headlines / Outfit numbers / mono labels); no emoji, no
  SF Symbols except chevrons and arrows; the companion is **Boop**, never "Mezo".
- **Nothing is saved without the owner's tap.** No automatic meal writes, ever.
- **Hungarian user-visible copy**, tegeződő, adherence-neutral: no red over-budget states, no streaks, no nagging.
- **Free Apple team** until the owner confirms the paid team: no new bundle ids, no widgets, no APNs.
- Backend ITs run with `-Dmezo.test.use-testcontainers=true`; LLM ITs use `@ActiveProfiles("companion-fake")`.
  iOS is not built in CI — run `xcodebuild test` locally.
- FE gates run in **both** modes (`CI=true` with mock and with `VITE_USE_MOCK=false`) whenever a shared DTO changes.

## Review Focus

Five things the spec implies, no task's happy path exercises, and the owner would hit:

1. **A catalog row with no allergen data** must read "nincs adat" everywhere and never be suggested as safe for an
   *allergia*-level sensitivity (Task 1 test).
2. **An offline photo meal synced after midnight** must keep its own capture date and window, not land on the new
   day (Task 10 test).
3. **A barcode that OpenFoodFacts does not know** must fall through to the label-photo path carrying the code, and
   must not create an empty catalog row (Task 2 test).
4. **A day with no recipe passing the rules** must still produce a plan: windows, budgets and an ingredient-level
   tip instead of an empty suggestion (Task 4 test).
5. **A recipe import whose page has no machine-readable recipe** must return an honest empty result or a draft with
   its unmatched lines flagged — never a silently half-filled recipe (Task 6 test).
