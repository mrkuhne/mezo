# Check-in 2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the four-item check-in with the owner-approved Check-in 2.0 (14 items, per-slot plan,
question of the day, quick exit, no pre-selection) and wire every answer into every area that can use
it, so the whole app gets richer from one check-in.

**Spec:** [`docs/superpowers/specs/2026-09-27-checkin-2-design.md`](../specs/2026-09-27-checkin-2-design.md)
(§ references below point there).
**Approved prototype (build target, owner OK 2026-09-27):** Nap living prototype
[`elo/nap.html`](../../design_2.0/prototypes/elo/nap.html) — `#checkin`, the four slot sheets, `#hatasok`,
`#napom`, `#napzaras/3`, `#ikonok`; Edzés living prototype [`elo/edzes.html`](../../design_2.0/prototypes/elo/edzes.html)
— `#mai` readiness card. URLs in [`elo/README.md`](../../design_2.0/prototypes/elo/README.md).

**Architecture:**
- **Data.** `check_in` grows nullable columns (§4); `asked_items` records what the sheet showed so
  "not asked" and "skipped" differ. The entity, mapper, contract and service carry every field.
- **Plan.** The per-slot question plan is config (`mezo.checkin.plan`) served by
  `GET /api/biometrics/checkin/plan`; a pure `CheckInPlanService` builds it and a pure
  `AdaptiveItemChooser` picks the question of the day (80 % need, 20 % random, seeded RNG in tests).
- **One renderer.** A new `CheckInText` renders any check-in for prompts; snapshot, daily summary,
  tools, meal coach and personal records all call it.
- **Consumers.** Each area plugs in at the anchors listed in spec §9 (flags, metrics, patterns,
  detectors, life goals, training readiness, day verdict, week, rings).
- **Frontend.** `CheckInSheet` is rebuilt to the prototype; `NapCheckinPage`, Napom lead card, ritual
  reflection step, Edzés today card, notifications and the Kapcsolat ring follow.

**Tech stack:** Spring Boot 3 / Java 21 / JPA / Liquibase (PostgreSQL), OpenAPI-generated DTOs,
React + TypeScript + react-query, Vitest + msw, Playwright layout specs.

## Global constraints

- **One release.** Owner decision: everything ships together. Slices below are for review/commit
  hygiene; merge to main only when all tasks are green (or behind no flag — there is no feature flag;
  the old sheet is replaced).
- **NULL is never a value.** No default anywhere; every reader treats NULL as "not answered". Legacy
  rows (`asked_items IS NULL`) are read as-is.
- **Scales.** All numeric items 1–10 (`CHECK` 1..10). Stress and soreness: 10 = worse. Pain =
  boolean gate + regions + intensity. Craving = value + kinds.
- **Copy.** Hungarian, business language, never moralizing; the exact strings are the prototype's.
- **Visual canon.** Üveg, dark only; Titanium sprites; the 9 new icons (`mood, rested, soreness, pain,
  motivation, hunger, craving, day, digestion`) move from the prototype into the shared sprite
  (`frontend/src/shared/ui/...` Icon3D sprite) — never inlined per page.
- **Contract pipeline, in order:** `npm run generate:api` in `api/` → maven generate-sources → FE
  `pnpm generate:api`.
- **Enums in OpenAPI use `enum:`** (pain regions, craving kinds, adaptive reason), never `pattern:`.
- **Flag keys ≤ 24 chars** and each needs the check-constraint migration.
- **Backend tests** with `-Dmezo.test.use-testcontainers=true`; anchor fixtures to the local day.
- **Frontend tests** in both modes with `CI=true`: `VITE_USE_MOCK` unset AND `VITE_USE_MOCK=false`.
- **Production data** is read-only for verification; no writes without the owner's OK.

### Task 2: Question plan + question of the day

**Files:** `CheckInItem`, `CheckInPlanProperties`, `CheckInPlanService`, `AdaptiveItemChooser`, controller endpoint, `application.yml` (`mezo.checkin.plan`), tests `CheckInPlanServiceTest`, `AdaptiveItemChooserTest`, `CheckInPlanApiIT`.

- [ ] Tests first:
  - the four slot plans from config match spec §2.2 (06:30 → 9 plan items, 10:00 → 7, 14:00 → 8, 20:00 → 11);
  - the adaptive item is never core, never already in the slot, `rested` only at 06:30, `day` only at 20:00;
  - with a seeded RNG, over 1 000 draws ~20 % are `random` (±3 %);
  - `need` picks the item with the fewest non-null answers in 14 days among items an active hypothesis / pattern pair / enabled detector waits on; no need → random;
  - the `why` sentence is Hungarian and names the item.
- [ ] Config shape: `mezo.checkin.plan.slots.{"06:30",…}.items: [...]`, `adaptive.random-share: 0.2`, `adaptive.need-window-days: 14`.
- [ ] Endpoint `GET /api/biometrics/checkin/plan?date&slotTime` → `{items:[{id,label,question,low,high,kind}], adaptive:{id,label,question,low,high,kind,why,reason}|null}`; the chosen adaptive item is stable for (user, date, slot) (seed = hash) so reopening the sheet does not reshuffle.
- [ ] Need sources: read active hypotheses + pattern pairs + enabled detector keys through a small `CheckInNeedSource` port (character/companion adapters), so biometrics does not depend on them directly.
- [ ] Run the three tests → green; commit.
