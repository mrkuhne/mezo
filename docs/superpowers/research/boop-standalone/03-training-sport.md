# 03 — Training & sport (gym mesocycles, in-workout logging, progression, running, sport, activity, skip/recovery)

Issue `mezo-r36n9.9`, mapper 03. Date 2026-11-10. Research only. Code wins over docs; drift is flagged.

## TL;DR

1. Training is the most complete domain in Mezo: ~16.5k lines of backend (`feature/train` + `progression` + `activity`), 61 train endpoints, ~190 FE test files, 116 backend test files. Core 4 (gym mesocycles + guided in-workout logging) is **exists & good**.
2. The gym engine is fully deterministic and strong: hypertrophy-drive set prescription per set (weight/reps/RIR from last identical-exercise session, Epley equal-effort, plate/machine-gap snapping), weekly per-muscle volume ramp (MEV/MAV/MRV, deload, early deload on grind), recovery comeback ramp. No LLM decides load.
3. In-workout flow is logging + a post-exercise debrief (pump 1–4, joint pain 1–3, workload 1–3) + closing note. **That feedback does not feed back into next week's load** — only reps/weight/RIR (and a "grind" signal) do. Feedback goes to the Character detectors (niggle map), a "flat feedback" proactive probe and chat tools.
4. Running is fully built (interval blocks, per-segment structure, RPE log) but **empty in production** (0 blocks, 0 logs); other sports are a 3+7-kind session log (19 rows) with schedule slots, one-off events, MET kcal estimate.
5. Training ↔ nutrition coordination exists **one-way and only at the energy level**: planned + logged sessions (net MET kcal) raise the day's kcal target and open pre/post-workout meal windows (`WorkoutWindowQueryService.movementOn`); goal engine reads weekly scheduled activity. **Nothing adapts the training plan to the weight goal or meal plan** (core 5 = mostly missing). Training reads no nutrition at all.
6. "AI re-examines the day and adjusts" (core 12) exists only in fragments: readiness LIGHTEN overlay from the morning check-in, advice-card `lighten_tomorrow` / `skip_sport_slot`, kímélő mode, comeback ramp. No live in-workout AI and no workout-length/exercise-swap suggestions.
7. Apple Health workouts land in `wearable_workout` and are used **only** by the Boop brief (yesterday's load → "forma" score). They are **not linked** to `workout_session` / `sport_session`; no dedup, no kcal credit (docs say "display + AI context only").
8. Boop S3 session-time move is an isolated override row (`workout_time_override`) read only by `BoopDayAssembler`; the plan, gym schedule, Fuel windows and notifications ignore it.
9. Production shape: 4 mesocycles, 2 templates, 27 completed gym instances (7 custom) over 2026-08-24 → 11-03, 535 sets, 155 feedback rows, 1 closing note, 19 sport sessions, 4 skips, 1 recovery period, 16 wearable workouts, 0 run data.
10. Reuse: the whole `/api/train/*` surface can be called by Swift as-is (OpenAPI generated); the heavy logic is server-side. FE-only logic worth knowing: rest timer, set-state model (`workoutState.ts`), warmup suggest, weekly bands, week/muscle load views, mock `judge` copy of skip policy. A watch/iPhone in-workout screen needs `GET workouts/today` + `POST sets` + `POST feedback` + `POST finish` and little else.

### 2.3 Progression (load) — deterministic engines

- `SetRecommendationService.prescribe(...)` (`service/SetRecommendationService.java:35-66`) + `ProgressionDecider.decide(...)` (`ProgressionDecider.java:38`): per exercise, finds the top working set of the most recent completed session of the same *identity* (catalog id else name — `ExerciseHistoryResolver`, `mezo-eq4w`), then: deload week → ~0.9× load, reps reset; reps ≥ rep_max → next real weight ≈ +2.5 % compound / +5 % isolation at equal-effort reps (Epley with RIR), or build reps past the range top when the jump exceeds 10 %; rep_min ≤ reps < rep_max → +1 rep (hold if the last set was a grind, RIR below target); reps < rep_min → drop weight if at/over target effort, else hold; first session seeds from `anchor_weight_kg`. `WeightSnapper` moves targets onto weights that exist on that machine (history ∪ plate grid − known gaps, `WeightGapService`). Warmups ramp down from the working target. Output `PrescribedSet[]` + `ProgressionSignal {lever WEIGHT|REP|HOLD|DELOAD, rationale}` per exercise. Switch `mezo.feature.hypertrophy-drive.enabled` (default on). Config `HypertrophyProperties`.
- `VolumeProgressionService.rolloverIfDue` (`:123`) — **weekly per-muscle set ramp**, called from `WorkoutService.getToday`: reads last calendar week's completed instances, per-muscle logged working sets and "grind" (RIR ≥ `grindRirGap` 2 under target); +`step` (2) sets on a productive week up to the tier ceiling, hold at ceiling, deload week = 0.5× / floor ⌈MEV/2⌉, early deload at MRV+grind. Idempotent per calendar week (`volumeRecompute.lastRun`). `WorkoutService.effectiveWorkingSets` then distributes each group's `currentSets` over that group's exercises (proportional to template sets, ≥1). Seeded from `mezo.volume.baselines` (RP table) at activate/create.
- Read-time overlays in `getToday` (template never edited): readiness LIGHTEN (hold-only, one set for care exercises), per-date `workout_day_adjustment` (advice-card lighten tomorrow), comeback ramp (see 2.6), deload.
- **Not the same as `feature/progression`**: that package is the **gamification XP/level/skill layer** (`ProgressionService.applyGym/applyRun/applySport`, `TraitCalculator`, `PerkCatalog`, `AchievementService`, `GrowthWeekService`, `LevelUpEventEntity`). Gym finish → `GymSignalCalculator` → XP per athletic skill → `levelUp` payload on finish response; run/sport the same. It does not change training loads.

### 2.6 Kihagyás / kímélő mód (training side)

- `planned_skip` (kind GYM|SPORT|RUN|MEAL, 9 reasons: ILLNESS, STOMACH, INJURY, TRAVEL serious; TIRED, NO_TIME, NO_MOOD, OTHER, NONE soft; NOT_HUNGRY for meals; free text for OTHER). "Skip first, reason after". `PlannedSkipPolicy.judge` (pure): serious = always excused; soft = first of the ISO week excused by a weekly free pass; ADVICE always excused. API `train-skip.yml`: `GET/PUT /skips`, `DELETE /skips/{id}`. Window today−7 .. end of ISO week. Central read `PlannedSkipService.verdictsBetween` is consumed by streak bridge, commitment, missed-workouts rule, meso adherence, quests, habits, notification anchors, fuel windows. Prod: 4 skips.
- `recovery_period` + `recovery_day_release` (`train-recovery.yml`): serious reason + duration estimate opens a period; planned sessions in it are virtually skipped/excused (protected days up to today+13); "Ma mégis edzek" releases one day lightened; "Jobban" ends it and `RecoveryReturnPolicy` decides CONTINUE (d ≤ 2) / RESUME (shift meso by whole weeks, 3–9 days) / STEP_BACK (≥ 10 days: shift back one week and −1 step on every muscle's sets, floor MEV); then the **comeback ramp** (1–2 sessions: sets −⅓, RIR ≥ 3, #1 ≈ 90 % load) read-time in `getToday`; undo same day; Prod: 1 period (2026-10-02).
- Fuel coupling: `RecoveryFuelMode` (ILLNESS/STOMACH → GUIDANCE, INJURY → MAINTENANCE, TRAVEL → ESTIMATE) switches the day's kcal target to unjudged/maintenance in `FuelDayService`; MEAL skips carry `planned_kcal`.
- Readiness (Check-in 2.0): `GET/POST/DELETE /api/train/readiness/today` — morning check-in answers (rested ≤ 4, soreness ≥ 7, motivation ≤ 3, pain regions → `PainRegionMap` → planned exercises) offer LIGHTEN/KEEP (`ReadinessAssessor`/`ReadinessService`, table `readiness_choice`).
- Not yet built per docs: S4 AI classification of `OTHER`, memory, repeated-"nincs kedvem" nudge.

## 3. How it works — main flows

### 3.1 Planning a workout block
1. FE wizard (`InterviewStep`): pick weekdays, weeks, muscle priorities (≤ 2 Emphasize) → `POST /meso-plans/generate` → skeleton from MEV/MAV/MRV landmark table, exercises filled from catalog deterministically, optionally re-picked by LLM, rationale string returned.
2. User edits days/exercises/sets/rep ranges/target RIR/anchor weight, sets per-weekday times (writes `PUT /gym-schedule`), saves as `meso_template` (`POST /meso-templates`), then `POST /meso-templates/{id}/start {startDate, status}` creates a `mesocycle` run: template days → `workout_session` template rows + `exercise` rows; `VolumeProgressionService.seedBaselines` births volume rows from the RP table; `MesocycleActivated` event published (goal probe).
3. Optionally attach the meso to a goal timeline (`GoalPlanLinkService`).

### 3.2 Starting and logging a session (set by set)
1. `GET /workouts/today[?templateSessionId]` (`WorkoutService.getToday:191`): resolve day = open instance > param > today's HU weekday label; auto-close stale instances; weekly volume rollover; deload detection from `phaseCurve[currentWeek-1]`; effective sets per exercise from the volume ramp; overlays (readiness LIGHTEN / day adjustment / comeback ramp); per exercise `SetRecommendationService.prescribe` → `prescribedSets` (warmups + working, each with target kg/reps/RIR) + `progression{lever,rationale}` + last-week reference + durable exercise note; also `completedWorkout`, `comeback`, `overloadSummary`.
2. Eligazítás (briefing) → `POST /workouts {templateSessionId}` (`startWorkout:705`): resumes an open instance (never duplicates), otherwise creates the instance; guards: one open workout at a time (409 `TRAIN_WORKOUT_OPEN_ELSEWHERE`), one completion per template day per Mon–Sun week (409 `TRAIN_DAY_DONE_THIS_WEEK`, not for custom); `started_at` set here only.
3. Each set: FE stepper pre-filled with the target; `POST /workouts/{id}/sets` (`logSet:751`) stores weight/reps/RIR/side/kind/note + the **target snapshot** (what was prescribed), then weight-gap learning, then decorative medals (failures swallowed). Edit/delete sets (`PUT/DELETE .../sets/{setId}`, active instances only). Skipping a whole exercise writes a `skipped` marker set. Extra/removed sets are client-state; swap/add exercise and "make it permanent for the meso" via `POST /workouts/{id}/exercises` + `plan-sets`. Client-only rest timer. Optimistic local state in `workoutState.ts` with server ids attached after the response.
4. After the last set of an exercise → **FeedbackModal** (3 vessel questions: pump, joint pain, workload; skippable) → `POST /workouts/{id}/feedback` (upsert per exercise). Per-exercise durable note (`PUT /exercises/{id}/note`) is preloaded next time.
5. Finish: confirm sheet (with a closing free-text note, auto-saved by `persistClosingNote`) → `POST /workouts/{id}/finish` (`finishWorkout:976`): status → completed, fill-if-empty `finished_at`/`closing_note`, derive `active_seconds` (gap-capped), gym XP + `levelUp`, medals, publishes `WorkoutFinishedEvent` → `TimingProfileListener` updates the learned timing profile (EWMA). Idempotent. Ceremony + review page (`GET /workouts/{id}`).

### 3.3 How the next week's load adapts (all deterministic)
- Per exercise, next session's target = function of the last identical-exercise working set (weight, reps, RIR) vs the rep range and target RIR (see 2.3). So adaptation is **per exercise, session to session**.
- Per muscle, volume changes **per calendar week** from last week's logged set counts and grind flags; the number of sets per exercise is re-derived from it; deload weeks per `phaseCurve`; recovery periods shift the calendar / step volume back.
- Inputs that matter: weight, reps, RIR, skipped markers, completion status. Inputs that do **not** move load: pump, joint pain, workload feedback, closing note, sleep, check-in energy (except via the readiness LIGHTEN offer), nutrition, bodyweight, wearable data.
- Today's readiness (morning check-in thresholds) and advice-card lightening are the only "day-of" dynamic inputs and are both one-way "lighter" (hold-only / fewer sets); there is no "push harder" counterpart.

### 3.4 Sport and run logging
Sport: Sport log sheet/page (kind, duration, RPE, sets or rounds, notes, optional kcal override) → `POST /sport-sessions` → MET kcal, XP, 3-kind volleyball shoulder strain etc. Run: active block → agenda by weekday/time → `RunLogSheet` → `POST /run-sessions`. Both feed `WorkoutWindowQueryService.movementOn` (kcal credit) and weekly load views.

### 3.5 Training ↔ nutrition / weight (what actually coordinates)
- `WorkoutWindowQueryService` (549 lines): for a day builds workout **windows** (gym slot times, sport slots/events, prescribed runs; skipped/recovery days dropped unless actually logged) used by Fuel's meal-slot planning and the AI meal coach (`MealCoachPrompt`: pre_workout / post_workout slots) and `DayMovement{plannedKcal, extraKcal, pendingKcal}` = BMR×NEAT base + every LOGGED session's net kcal, which `DayTargetProjector`/`FuelDayService` fold into the day's kcal target (so more training → more allowed food, no day-type pick any more).
- `WeeklyScheduledActivityService`: scheduled gym/sport/run EAT per day feeds `TdeeBootstrapService` / goal engine / `GoalPrescriptionCalculator` (activity-model version 3, migration runner recomputes goals).
- Recovery fuel mode and meal skips (above); `LoadFuelMismatchRule` flags high 7-day load with low kcal/sleep; `MesoContextAssembler` (companion) puts kcal/weight/sleep next to a closed meso in the AI eval.
- **Missing**: no logic changes training volume/frequency/intensity because of the weight goal (cut vs bulk), a calorie deficit, or the active diet plan; the meso generator ignores the goal (it only knows `hypertrophy`); training reads no nutrition. The Goal slice can only *attach* a meso/run block to a timeline.

## 4. Quality assessment

**Solid**
- The set recommendation + volume engine is mature, deeply specified and heavily tested: backend 116 test files in `feature/train` (pure unit tests for the decider/snapper/policy + ITs for contracts, persistence, consumers), 20 in progression; FE ~190 test files across `features/train` + `data/train`; layout specs `train-session`, `train-skip`, `train-kimelo`, `train-custom`. Mock-mode twins exist for everything.
- Honest-state discipline: null kcal not 0, derived stuff failing never rolls back the user's set (medals, timing), idempotent finish/skip/recovery, read-time overlays instead of template edits, per-user locks.
- Skip/recovery is a thoughtful, consistently propagated model (one central read, many consumers).
- Prescription snapshot (`target_weight_kg/reps` stored per set) enables honest "did you hit the plan" analytics.

**Half-built / gaps**
- Feedback (pump/pain/workload) is collected for every exercise (155 rows prod) but never closes the loop to load; the only use is detectors/AI context. Closing note: 1 row in prod — the owner barely journals in-workout.
- Cross-load engines "Sport→everything" / "Running→leg volume" are documented as **Phase 3 / static text** (`CrossLoadRow`, `RunCrossLoadCard` mock-only); sport/run load does not enter the weekly muscle volume ramp.
- Running: complete but unused; no distance/pace/GPS or heart-rate zones; no Apple Watch workout mapping into `run_session_log`.
- Hypertrophy-only generator; no strength/powerlifting/endurance/cut presets, no "personal trainer" reasoning, LLM only re-picks exercises.

## 5. Reuse for native iOS (Boop)

**Call as-is (OpenAPI-generated DTOs, owner-scoped):**
- Today/plan: `GET /api/train/workouts/today`, `GET /workouts?from&to`, `GET /workouts/{id}`, `GET /gym-schedule`, `GET /sport-schedule`, `GET /sport-events`, `GET /running-blocks`, `GET /mesocycles`, `GET /timing-profile`.
- In-workout loop (everything a phone or Watch needs): `POST /workouts` (start/resume), `POST .../sets`, `PUT/DELETE .../sets/{id}`, `POST .../feedback`, `POST .../skip`, `PUT /exercises/{id}/note`, `PUT /workouts/{id}/note`, `POST .../finish`. The server already computes targets, warmups, rationale, medals, XP, so the Swift client is mostly a stepper UI + rest timer.
- Sport/run logging: `POST /sport-sessions`, `POST /run-sessions`. Skip/recovery: `PUT/DELETE /skips`, `/recovery*`. Readiness: `GET/POST/DELETE /readiness/today`. Plan creation: `POST /meso-plans/generate` → `POST /meso-templates` → `/start`.
- Session move: `PUT/DELETE /api/boop/session-time`.

**Needs a Boop-shaped API (suggested):**
- A single "today's training" read for the brief/orb (planned session, readiness state, comeback, recovery, skip state, time) — today Boop's assembler composes it privately (`BoopDayAssembler.session`) and reads only title/time/exercise names + set counts.
- Apple Watch/Health reconciliation: map `wearable_workout` ↔ `workout_session`/`sport_session`/`run_session_log` (same day, overlapping time) with dedup and a kcal/HR enrichment of the logged session (avg HR, active energy). The wearable ingest currently stores raw rows only.
- A live-workout contract for Watch: lightweight set-log endpoint is fine, but start/finish + HealthKit workout session (HKWorkoutSession) coordination and heart-rate samples per set do not exist (no per-set HR column).
- Day-adjustment write API beyond `lighten_tomorrow` (shorten/lengthen, swap, add food-related adjustments) for core 12.

**Logic only in the web frontend that must move to backend or Swift:**
- `workoutState.ts` set/skip/extra/removed model and optimistic append/attach-id logic (Swift needs its own session model; extra/removed counts are client-only and lost on reload — only skipped markers persist).
- Rest timer (`useRestTimer`, `restTimer.ts`), `warmupSuggest.ts`, `weeklyBands`/`setBudget` (planning-time weekly set bands, client-only), `repEquivalence.ts` (FE twin of the Java Epley — needed for live "if I change weight, how many reps" in-session), body-map/week load derivations (`loadWeek`, `muscleWeek`, `weekZone`, `dayImpact`, `trainDayEnergy`), `mesoCompare`, `plannedSkips.judge` (mock-only twin of the policy; in real mode the server judges).

## 7. Open questions / risks

1. **What is the standalone Boop's training scope?** Full guided logging on iPhone + Watch (needs a HealthKit workout session, per-set HR, haptics, rest timer, offline queue) vs a thin "today's session + log after" version that keeps web logging. The server API supports the former; the Swift effort is the session model + rest timer + steppers.
2. **Source of truth for a workout**: manual log vs Watch-recorded workout. Needs a dedup/merge rule (time overlap + activity type) and a decision whose kcal/HR wins; today both exist separately and only manual feeds kcal targets.
3. **Should feedback (pump/pain/workload, closing note) drive load?** Today it doesn't; the owner's core 4/12 imply it should (e.g. high joint pain → swap/lighten; "too little work" → add a set). This is a new rule layer in `SetRecommendationService`/`VolumeProgressionService` and needs the owner's OK.
4. **Plan coordination (core 5)** requires a plan object that spans diet + training with a weight goal; decide whether it lives in `goal` (attach plans) or a new "plan" feature, and whether the meso generator should accept goal context (cut/bulk, deficit → fewer sets or maintenance volume).
5. **Running**: unused in prod — build it for the Watch (distance/pace/HR zones from HealthKit) or drop the block-builder UI? The interval-segment structure is reusable.
6. **Session-time move consistency**: if kept, `workout_time_override` should feed Fuel windows/notifications (or move into `gym_schedule` semantics), otherwise Boop and the rest of the stack disagree about when the session is.
7. **Single time per weekday** and no duration in `gym_schedule_slot` limits "shorter/longer workout" ideas; durations are `durationEst` on the template day only.
8. **Docs drift risk**: `docs/features/train.md` is 1330 lines of layered history; for the re-plan, treat the code and the `train.yml` contract as the source and write a lean Boop-specific training spec rather than extending it.
9. Prod data is the owner's personal data — fine for shape, but the 27-session / 3-per-week history is small; any new adaptive rule will have little data to validate against, so keep rules transparent and reversible (read-time overlays, as today).
