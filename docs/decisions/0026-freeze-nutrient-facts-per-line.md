# 0026 — Freeze the four nutrition-quality facts per line, superseding live-pantry scoring reads

- **Status:** Accepted
- **Date:** 2026-08-12
- **Driver:** `mezo-m6uv`
- **Spec:** [`docs/superpowers/specs/2026-08-11-recipe-meal-nutrient-freeze-design.md`](../superpowers/specs/2026-08-11-recipe-meal-nutrient-freeze-design.md) — note the spec's rounding rule (§2, one decimal, HALF_UP) is superseded by this ADR's Decision section; it was changed mid-implementation and the spec was not rewritten (specs are point-in-time by convention, `docs/README.md`).
- **Precedent:** the macro snapshot (`snapshot_kcal`/`snapshot_protein_g`/…) on `recipe_ingredient` (mezo-lns) and `meal_item` (mezo-arb) — this ADR extends the SAME freeze discipline to four fields that had been left out of it.

## Context

`recipe_ingredient` and `meal_item` have frozen their four macro facts (kcal/protein/carbs/fat) per line since the recipe and meal-logging slices shipped: a saved recipe or a logged meal keeps its own kcal even if the pantry item it was computed from is edited afterwards. The four nutrition-quality facts — fiber, sugar, salt, saturated fat — never got the same treatment. `mezo-7797` split them out into their own WHO/fat-quality/micro scoring dimensions, and wired that scoring to read them **live** off the current `pantry_item` row at scoring time:

- `RecipeService.fitLines` (`backend/src/main/java/io/mrkuhne/mezo/feature/recipe/service/RecipeService.java`) resolved the per-serving nutrition-quality facts from a `pantryById` map of live `PantryItemEntity` rows, using its own live `factFactor` (independent of the macro `factor`).
- `MealService` resolved them via a now-deleted trio — a `private record Facts(...)`, `pantryFacts(...)` (pantry-arm: live pantry row), and `recipeFacts(...)` (recipe-arm: replayed the persisted `recipe_overrides` envelope against live `recipe_ingredient` + live pantry rows via a helper `addFact`) — inside `MealService.toScoredLine`.

The result was two sources of truth for the same four numbers on any given line: a frozen macro snapshot that never moved, and a live-read nutrition-quality fact that moved whenever the underlying pantry item was edited — even for a recipe saved months ago or a meal already logged and scored. Concretely: editing a pantry item's salt content retroactively changed the score/breakdown of every past recipe and every already-logged meal that referenced it, while the exact same edit left their kcal/protein/carbs/fat numbers untouched, because those *are* frozen. This asymmetry, together with the numbers never being surfaced anywhere outside the scoring breakdown (buried across the Rost/WHO/Zsírminőség dimension rows, invisible whenever no breakdown existed — no kcal, LLM/flag off), is what a batch of four user bug reports converged on and what this change set out to fix (see the design spec's opening).

## Decision

The four nutrition-quality facts — `fiberG`, `sugarG`, `saltG`, `saturatedFatG` — are now **frozen per line** on `recipe_ingredient` and `meal_item`, exactly like the macro snapshot: four new nullable `numeric` columns on each table, captured from the live pantry item at write time (migrations `backend/src/main/resources/db/changelog/1.0.0/script/202608111200_mezo-m6uv_recipe_ingredient_nutrient_snapshot.sql` and `…/202608111210_mezo-m6uv_meal_item_nutrient_snapshot.sql`).

**This supersedes the live-pantry-read rule** that lived in `RecipeService.fitLines` and in `MealService`'s deleted `Facts`/`pantryFacts`/`recipeFacts`/`addFact` machinery. Both scoring paths now read the frozen snapshot with the SAME `amount / snapshotPer` factor the macro contribution already computes — `RecipeMapper.lineFactor` derives that one factor and both `contributionWithAmount` (macros) and `nutrientsWithAmount` (nutrients) consume it, so the arithmetic exists exactly once. `RecipeService.fitLines`'s separate live `factFactor` is gone with the live read it existed to scale. There is now exactly one route to these four numbers: the write-time freeze.

Null semantics carry over unchanged from the macro snapshot's "no fabricated zero" rule, extended honestly to partial sums: a line's field is `null` iff its source pantry item carried no value for it (never coerced to 0), and a rollup field is `null` iff **every** contributing line is `null` — otherwise it is the sum of the known ones. A line-level `—` in the UI is what makes a partial rollup self-explanatory.

**Rounding — this is what actually shipped, not what the design spec (written before implementation) still says.** The spec's original rule was one-decimal storage; it was replaced mid-implementation, on the user's ruling, once it became clear that rounding at the line level before summing turned a genuine 0.04 g salt contribution into a displayed 0.1 g, and that per-line rounding error compounded across every line of a multi-ingredient recipe or multi-item meal. What shipped instead: grams are **stored and summed at three decimals**, HALF_UP (`RecipeMapper.scaledGram`, `RecipeMapper.java:216`) — matching the migrations' own `round(…, 3)` backfill, so the freeze and the backfill agree on precision. One-decimal rounding is a **display-only** concern, entirely in the frontend formatter (`formatGram`, `frontend/src/shared/lib/grams.ts`): `—` for a null (no data), a genuine `0` still prints as `0`, and a positive value that would otherwise round to a misleading `0` prints as `<0,1` instead — "0" reads as "none", and printing it for a real-but-tiny value would be the same lie as printing it for a null.

The contract carries the numbers as one shared `Nutrients` schema — defined once in `api/feature/meal/meal.yml`, cross-fragment `$ref`'d from `api/feature/recipe/recipe.yml` (the `MealBreakdown` merge precedent) — exposed as an optional, all-nullable `nutrients` object on `RecipeResponse`, `RecipeIngredientResponse`, `MealResponse` and `MealItemResponse`.

Deliberately out of scope: **NOVA** and the pantry **category** stay LIVE reads on both scoring paths. NOVA is a discrete food-processing classification, not a summable "how much of X" fact, and freezing it per line needs its own `recipe_ingredient.snapshot_nova` column plus its own override-replay story (already-zeroed lines force a live NOVA recompute today — a related but separate concern, tracked as `mezo-4tzf`, filed before this change from the `mezo-ormb` review). Category (the plant-diversity scoring input) has no per-line value to freeze — a recipe line's category is inherently "whatever the pantry item currently is," and a recipe-arm meal line keeps its honest `null` category because a composite ingredient set has no single one.

## Consequences

- **A pantry-item edit no longer retroactively changes an existing recipe's or logged meal's nutrient values.** A fresh value requires re-saving the recipe — `recipe_ingredient` snapshots are re-resolved against the live pantry on every save, exactly the rule the macro snapshot already established (`RecipeService.java` — "Snapshots are re-resolved against the live pantry on every save"), now extended honestly to all eight frozen fields instead of just four.
- **Both backfills are an honest approximation, not a historical reconstruction.** They backfill existing rows from **today's** pantry values, rescaled to each line's own (already-frozen) `snapshot_per`; a pantry row that drifted since a recipe was originally saved contributes its present-day value to the backfilled snapshot, not the value that was true when the recipe was written — the migrations' own header comments say so, and so does this ADR. The `meal_item` recipe-arm backfill goes one step further and **ignores any per-line override envelope** a meal item may carry (`recipe_overrides` jsonb): replaying that envelope's historical amounts against the recipe's now-backfilled line snapshots is not reconstructable from what was actually persisted, so it instead sums the recipe's own backfilled `recipe_ingredient` rows ÷ servings, same as an un-overridden log.
- **A known narrow gap survives in both backfills.** Both migrations guard the rescale factor with `coalesce(nullif(serving_amount, 0), 1)`. If a pantry row's `serving_amount` was set when the line was originally frozen but is `NULL` on that row **today** (at backfill time), the guard divides by 1 instead of leaving the result `NULL`, silently producing a scaled-up value. This cannot happen for any row written *after* this change ships — a freshly-written snapshot's basis is derived from the very same `serving_amount` field at write time, so the two can never disagree. The gap is confined to the one-time backfill of pre-existing rows against a since-nulled `serving_amount`.
- **A frontend gate now over-triggers and needs narrowing (filed as `mezo-ax1m`).** `frontend/src/data/fuel/pantryImpact.ts`'s `movesRecipeScores` still treats an edit to fiber/sugar/salt/saturated-fat (or the macro basis `per`) as score-moving and fires the "Mezo újraértékeli a receptet…" re-evaluation banner. Since the freeze, editing those facts on a pantry item can no more move an existing recipe's score than editing its price can — only `category` and `nova` still feed a live read. Leaving the gate as-is is over-eager rather than wrong (no missed re-evaluation), but it is the exact "claiming a re-evaluation that didn't happen" honesty problem `mezo-uavr`/`mezo-b9gv` were written to prevent, so it is tracked rather than left as fold-lore.
- **`FuelMeal.fiberG` is populated from the wire as a side effect.** `mealApi.ts`'s `fromResponse` now maps `nutrients.fiberG` onto `FuelMeal.fiberG`, so the Fuel Mai hero's Rost ring (`keretHero.ts`, [ADR 0024](0024-fuel-keret-hero.md) §4) is live data in real mode. ADR 0024 shipped it as an honest `0%` in real mode because the wire carried no fiber field at all at the time; that gap is closed here as a consequence of the freeze, not by any change to the ring itself.
- **The scoring pipeline is simpler as well as more honest.** `RecipeService.fitLines`'s separate live-pantry `factFactor` is gone — the frozen basis is the same `snapshotPer` the macro factor already uses, so one factor now drives both kinds of number. `MealService`'s `Facts` record and its `pantryFacts`/`recipeFacts`/`addFact` trio are deleted outright, along with the `overrideMap` replay they needed just for the live read.

## Alternatives considered

- **Keep live reads, just surface the numbers on the contract.** Rejected: it would have fixed the *display* half of the four bug reports but left the retroactive-rewrite behavior untouched, and it would have shipped a `nutrients` field on `RecipeIngredientResponse`/`MealItemResponse` whose value could silently disagree with the number the scorer used a moment earlier for the same line — the two-sources-of-truth bug, merely made visible instead of fixed.
- **Freeze the four facts for display but keep scoring on the live read.** Rejected for the same reason under a different name: it still leaves a frozen `nutrients` field the user sees diverging from a live-read number the scorer actually uses, the moment a pantry item drifts after the recipe/meal was saved.
- **Freeze NOVA in the same pass.** Deferred, not rejected. NOVA needs its own `snapshot_nova` column and its own override-replay design — a line dropped to 0 already forces a live NOVA recompute today (the finding behind `mezo-4tzf`) — and it is a discrete classification, not a summable gram amount, so bundling it here would have doubled this change's surface for a fact that behaves differently. Tracked separately as `mezo-4tzf`.
