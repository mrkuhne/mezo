# 0017 — Living occurrence protocol + backend placement engine for the Fuel Stack

- **Status:** Accepted
- **Date:** 2026-08-03
- **Driver:** mezo-vx9v (Redesign Fuel Stack page: living protocol, occurrence-based placement, autosave)
- **Supersedes:** the mezo-09g-era decision recorded in [`2026-07-02-fuel-stack-protocol-water-design.md`](../superpowers/specs/2026-07-02-fuel-stack-protocol-water-design.md) §3 — "the protocol persists ONLY the selected pantry-item ids + a version/confidence header; ALL timing/slot placement is FE-computed by `buildProtocol()`, and a re-selection is applied via a whole-selection `POST /api/fuel/protocol` (activate) that supersedes the prior version."
- **Links:** design spec [`2026-08-03-stack-redesign-design.md`](../superpowers/specs/2026-08-03-stack-redesign-design.md), plan [`2026-08-03-stack-redesign.md`](../superpowers/plans/2026-08-03-stack-redesign.md), mockup [`2026-08-03-stack-redesign-mockup.html`](../superpowers/specs/2026-08-03-stack-redesign-mockup.html), living doc [`fuel.md`](../features/fuel.md) §2–§5/§9–§10.

## Context

The mezo-09g Stack/Protocol slice ([`2026-07-02-fuel-stack-protocol-water-design.md`](../superpowers/specs/2026-07-02-fuel-stack-protocol-water-design.md)) shipped a *selection* model: the backend's `protocol`/`protocol_item` tables recorded only which pantry items were selected plus a version/confidence header, and the FE's `buildProtocol(selectedIds, stash)` recomputed every slot's timing and "why" reasoning client-side from a ~9-item hardcoded name-needle table (kreatin/whey/D3/Mg/omega/koffein/AAKG/béta-alanin/PWO). Persisting a new selection meant pressing **"Bekapcsolás · ma"**, which called a whole-selection `POST /api/fuel/protocol` (`ProtocolActivateRequest{selectedPantryItemIds[], reason?}`) that superseded the prior version and bumped `protocol.version`.

Three problems surfaced once the page saw real use:

1. **Coverage.** `buildProtocol()`'s needle table only recognized ~9 hardcoded substrings. Any other supplement the owner added to the pantry landed nowhere — invisible on the Stack page, no slot, no feedback — because placement logic lived entirely on the FE with no server-side fallback (no rule table, no LLM, nothing).
2. **Mental model mismatch.** The selection lived in transient FE state until the user pressed an "apply/activate" button whose semantics ("re-version the whole protocol") never matched what the user was doing (ticking items on/off, wanting them just to *be* there). Edits felt inert until that button; there was no live "the stack IS what's on tick.
3. **One-item-one-slot.** `protocol_item` held one row per *selected item*, with no way to express "creatine 3× daily" or "an item split across two zones" — real supplement regimens routinely need multiple daily intakes of the same item.

The redesign additionally needed to survive **rest days** without the FE silently mis-showing a training-anchored item's zone, and needed the item-recognition problem solved **once, on the backend**, so every client (and any future automation) sees the same placement — not re-derive its own needle table.

## Decision

Replace the whole-selection/version model with a **single living protocol row per user, made of occurrence rows**, placed server-side.

1. **Occurrences, not selections.** `protocol_item` gains `slot_key` (one of 8 canonical zones: `wake|breakfast|pre_workout|post_workout|lunch|dinner|evening|bedtime`), `dose` (nullable override), `pinned`, `placement_source` (`rule|llm|user|fallback`), `placement_reason` (one Hungarian sentence), and `rest_day_fallback` (a zone key, `'skip'`, or null). One stack item can have **1..n occurrence rows** — multiple daily intakes are first-class, not a UI trick. A partial unique index (`protocol_id, pantry_item_id, slot_key` where not deleted) keeps one occurrence-per-zone-per-item unambiguous for the intake tick.
2. **The `protocol` row is always live — no version-supersede step.** `ProtocolService.ensureActive` lazily creates the single active row on the first occurrence write; every occurrence mutation (`addItem`/`patchItem`/`deleteItem`) `touch()`es that SAME row's `version` in place. There is no more whole-selection `POST /api/fuel/protocol` (activate) endpoint, no `ProtocolActivateRequest`, and no run-time supersede-and-recreate. `version`/`status active|superseded` stay on the entity as a cheap audit trail — `superseded` only ever describes a legacy pre-vx9v row, never a state this code writes going forward.
3. **Occurrence CRUD is the whole write surface:** `POST /api/fuel/protocol/items` (no `slotKey` → engine-placed; with `slotKey` → user-placed, `pinned=true`), `PATCH /api/fuel/protocol/items/{id}` (move / re-dose / `pinned:false` → re-run the engine), `DELETE /api/fuel/protocol/items/{id}`. Every edit persists immediately — there is no client-side draft and no apply button.
4. **Placement moves to the backend, as an ordered fallback chain — `PlacementEngine`:**
   1. **Deterministic rule table** (`PlacementRules.RULES`, Java, unit-tested, ordered, first match wins) — name-substring needles → zone + Hungarian reason + optional rest-day fallback + optional daily-total dosage hint.
   2. **The pantry item's own `timing` field** (`PlacementRules.zoneForTiming`) as a second deterministic signal.
   3. **An LLM fallback** for anything neither stage recognizes — one call via the **consumer-owned `StackPlacementLlm` port** ([ADR 0012](0012-consumer-owned-llm-ports.md): `feature/fuel` owns the interface, `feature/companion` supplies `StackPlacementLlmAdapter`, so `feature/fuel` never imports `feature/companion`), gated at the bean boundary on **both** `mezo.feature.stack-placement-llm.enabled` and the companion switch. The result (`slotKey`/`reasonHu`) is validated against the zone enum and persisted as `placement_source='llm'` — never re-called for that occurrence.
   4. **An honest `breakfast` fallback** (`placement_source='fallback'`) when the LLM stage is off, unavailable, or fails — never an error surfaced to the user.
   A lazy read-backfill in `ProtocolService.getView` runs this same chain for any pre-vx9v row still missing a `slot_key`, so no data migration needs to invent placements in SQL.
5. **Zone *times* stay entirely FE-computed — this invariant is explicitly carried forward, not changed.** The backend persists which zone an occurrence belongs to; it never persists or computes a clock time. The FE's pure `projectStackDay(occurrences, stash, intakes, wake, bed, mealsPerDay, blocks, weightKg?)` (replacing the retired `buildProtocol()`) maps each zone to today's actual time from the day's live anchors (sleep goal, meal windows, training blocks) and groups occurrences into zone cards. This is the SAME projection the Stack page, the Mai timeline (`useFuelTimeline`), and the notification schedule writer/preview all now share — one source of "what time is the pre-workout zone today," never three independent derivations.
6. **Rest-day handling is projection-only, not a persisted mutation.** On a day with no training block, `projectStackDay` regroups a training-bound occurrence into its rule's `rest_day_fallback` zone (or `'skip'` → rendered greyed-out, tick disabled, badged `ma nincs edzés → kimarad`) — the *persisted* `slot_key` is untouched, including for a pinned occurrence (a rest-day badge can coexist with `pinned=true`; the badge wins in the UI precedence, since it is the more load-bearing fact today). The next training day, the same occurrence projects back to its real zone with zero data movement.
7. **Multi-dose is manual, not auto-split.** The engine places exactly one occurrence per add. A user who needs "creatine 3× daily" adds two more occurrences by hand via "+ Még egy bevétel," each independently zoned/dosed. The rule table may carry a `daily_total_hint` (e.g. "ajánlott napi összmennyiség 15–20g — érdemes 3–4 bevételre osztani") surfaced in the item panel as a read-time-only hint (`PlacementEngine.dailyTotalHint`, never persisted) — the engine never auto-splits a dose across zones.

## Consequences

- **Every pantry supplement now gets SOME placement, always.** The four-stage fallback chain guarantees a `slot_key` for any item, closing the "invisible item" gap that motivated the redesign. An LLM-off, rule-table-miss item still lands somewhere explainable (`breakfast`, honest generic reason) rather than nowhere.
- **The Stack page has no apply/activate affordance left.** Every edit (tick, move, dose, add, remove) writes straight through occurrence-CRUD mutation hooks; the global mutation-error toast is the only error surface. This matches the "the stack IS the live protocol, always" mental model the old page fought.
- **One extra internal LLM seam, with no new user-facing failure mode.** `StackPlacementLlm` is the fourth consumer-owned-port seam (after scrape, meal AI-log, recipe breakdown) — but unlike the others it has no dedicated switch-off HTTP status: a companion-off day is invisible to the end user (a rule-table miss just lands in `breakfast` with a generic reason). This is a deliberate asymmetry — placement is an internal implementation detail, not a user-facing AI feature with its own on/off UX.
- **The contract is a breaking change, accepted without a compat shim** (single-user app, FE+BE ship together per the same commit): `POST /api/fuel/protocol` (activate) and `ProtocolActivateRequest` are removed outright; `ProtocolResponse.items` becomes a required field.
- **Backend and mock placement can drift for a genuinely new item.** The mock layer mirrors only the rule-table's cheaper timing-hint stage (`mockPlaceOccurrence`/`zoneForTiming`) — it has no name-substring table or LLM stage — so a brand-new mock-mode addition may land in a different zone than the real engine would choose. Accepted: the mock's SEEDED occurrences are hand-placed to match the real rule table exactly; only a live *runtime add* of an unrecognized item can diverge, and only in mock mode.
- **`buildProtocol()` and its needle-matching helpers are deleted outright**, not deprecated-in-place — `deriveBlocks`/`PRE_WORKOUT_STACK_LEAD_MIN`/`deriveProtocolAnchors`/`ProtocolAnchors` survive in the same file for callers that still want a block-list or `{wake,preWorkout,bedtime}` shape, but `deriveProtocolAnchors` currently has no production caller (test-only) now that all three real call sites compose `projectStackDay` directly.
- **Rest-day regrouping is invisible to any backend consumer** (companion tools, future automation) — `PlacementEngine`/`ProtocolService` only ever see the *persisted* zone, never the FE's rest-day-projected one. Any backend feature that needs "where does this item show up today" would need its own thin projection or a shared read seam — not built here (out of scope, no such consumer yet).

## Alternatives considered

- **Keep the selection/version model, just extend the rule table.** Rejected: extending `buildProtocol()`'s needle table doesn't fix the mental-model mismatch (an apply button for what should be a live list) or the one-item-one-slot limitation, and any future FE consumer would still need to re-derive the same rule table client-side.
- **Persist a computed slot *time* on the occurrence, refreshed by a cron/on-read job.** Rejected: this would create a second source of truth for fuel-slot times, duplicating the FE-owned "the FE is the single source of truth for fuel-slot times" invariant the Mai timeline and notifications already depend on (see [`fuel.md`](../features/fuel.md) §5, [`_platform-notifications.md`](../features/_platform-notifications.md) §5) — and it would need re-deriving on every anchor change (sleep goal edit, training reschedule) rather than falling out for free from a pure render-time projection.
- **Auto-split a high-dose item across multiple zones at add time.** Rejected for this slice (explicitly out of scope in the design): guessing a split invents information the user didn't provide; the daily-total hint surfaces the *recommendation* without pretending the engine knows how the user wants to break it up. Revisit once there is a stronger signal (e.g. logged-intake patterns) to base a split on.
- **Route rest-day regrouping through a persisted "effective zone" write** (recompute + save on the rest-day view). Rejected: this would need a cron or a write-on-every-read, and would make "did the user move this, or did rest-day logic move it" ambiguous in the stored data. Projection-only keeps the persisted zone as the single ground truth and the rest-day view as a pure, idempotent, always-correct-for-today function of it.
