### The header is the shell's, not the hub's

Until `mezo-atry`, `NapHubPage`'s `.nap-head` was copy-pasted verbatim into the Edzés, Fuel, Mezo and Én hubs — five near-identical blocks with drifting content. It now lives once, as **`AppHeader`** (`frontend/src/app/AppHeader.tsx`), mounted by `AppLayout` as the first child inside `ScreenContent` on every route except the three chrome-free ones (`/train/session`, `/me/sleep/night`, `/ritual` — the same `hideChrome` flag that also gates `TabBar` and `QuickLogFab`) and `/mezo/chat`, whose own conversation-control header is the single header on that route (`mezo-oq8z`). Since `mezo-8az6` the shell header **kitapad** (`position: sticky`, `top: 0` in the `.screen-content` scroller) instead of scrolling away with the page, and carries a napszak-követő aurora background (`HeaderAurora.tsx`). Since `mezo-oq8z` that aurora remains fully present after the 14px compact threshold (`useCondensedHeader`); only the spacing tightens, so the daypart color neither disappears nor turns into glass. The control row is 42px high with the header's clay icons enlarged by the same 2px; its aurora is a separate background layer extending 18px below the row with a visible mask fade from 70%, while every label and control stays on an unmasked foreground layer. `NapHubPage` itself renders no header at all any more. Six elements (the guide button only where the route has a guide), left to right:

1. **Kalauz „?"** — `.nap-roundbtn.nap-q`, rendered **only when the route has a registry entry** (`findKalauz(pathname)`, `frontend/src/features/tutorial/registry`), always the first button so the daypart switch's presence never shifts it. Opens the page's guide through `useTutorial().open(id)`; carries the `.nap-offnow` amber dot when the route is a T3 guide not yet seen. See [`tutorial.md`](tutorial.md).
2. **Szekció (clay spot + név)** — the mezo-8az6 replacement for the date eyebrow: the dátumot a telefon státuszsávja mutatja, a helyét az „épp melyik szekcióban vagyok" vette át (`app/headerSection.ts` — szekció-szintű, a path első szegmenséből, 115 route mellett tábla nélkül).
3. **Daypart switch** — a round clay button (`.nap-roundbtn`) carrying a daypart's clay icon (`i-hajnal` / `i-nap` / `i-alvas`). It reads `?dp=` **only on `/nap`**; on every other route it shows the real clock-derived daypart, since there is no page there to preselect a mosaic for. Tapping it opens the same three-icon `role="menu"` popover — its items are `role="menuitemradio"` with `aria-checked`, so the selection is exposed, not merely painted by the `.on` class (`mezo-atry` fix wave). Picking a daypart **always navigates to `/nap`**, carrying `?dp=` only when the pick differs from the clock-derived one (picking the clock's own daypart on `/nap` clears the param instead). The navigation **preserves every other query parameter** (`?day=`, `?medCycleDay=`, `?niggle=`, `?vulnerable=`, `?ritual=` — all app-wide scenario switches read by `useTodayScenario`) and uses `replace`, so daypart-tapping neither drops a scenario nor fills the history stack. The `?dp=`-or-clock resolution itself lives in **`logic/useDayFace.ts`**, shared verbatim with `NapHubPage`. The `.nap-offnow` dot — the ADR 0014 dual-signal ("hol tartok" vs "mit nézek") — appears **only on `/nap`**, and only when the shown daypart differs from the clock's.
4. **Mezo-messages circle** — a round button (`i-level` clay icon) with an unread-count `.nap-badge`, navigating to `/nap/uzenetek`. This is the tile that used to sit inside every daypart's mosaic (reggel/nap/este all carried a `Mezo` tile); `mezo-atry` moved it into the header instead, so it now appears exactly once per screen instead of once per daypart. The unread count is watermarked in `localStorage` (`lastSeenMessage`, key `mezo.msgseen.<date>`). **The badge and the page read ONE thread** — `MezoThreadProvider` (`frontend/src/features/today/MezoThreadProvider.tsx`), mounted by `AppLayout` around `ScreenContent`, is the single builder of `buildMezoMessages({ feed, demoBriefing, nudges })` and the single writer of the Életjel nudge log. This is not decoration: while the header built its own **nudge-less** thread and the page stamped the watermark with its own (nudge-bearing) last id, the header's `findIndex` could never match, so the badge fell back to the full count and **never cleared** (`mezo-atry` fix wave). The watermark is also React state in the provider, so the badge goes dark the moment the page marks the thread seen — not one navigation later.
5. **Notification bell** — a second round button with an unread-count `.nap-badge`, opening the `.nap-ntfpanel` **scrollable, full-width notification panel** (mezo-g9fz). It is a child of the `<header>` itself, not of the bell's wrapper — `left: 0; right: 0` against `.app-head` is what makes it full width — and it has three regions: a pinned head (`Értesítések` eyebrow + live unread count + `Mind olvasott`), a horizontally scrollable filter-chip row (`Mind` · `Olvasatlan` · the six categories of `features/notification/logic/category.ts`, each with its clay icon and count, only drawn when non-empty), and the scrolling list, capped at `max-height: min(600px, 74vh)` with sticky `Ma`/`Tegnap`/dated day labels, over an `Összes értesítés ›` foot → `/me/ertesitesek`, the notification **feed page** (`NotificationFeedPage.tsx`), not the preferences page. Read state here is the LIVE `readAt`, not the feed page's open-time snapshot: in the panel the un-highlighting IS `Mind olvasott`'s feedback. Source: `useNotificationFeed()` + `useNotificationFeedActions()`. The former gap here — the badge had no reachable path that ever called `markAllRead`, so it could never clear (`mezo-61w0`) — is closed twice over: opening the feed page fires `markAllRead()` once, and the panel's own `Mind olvasott` does it without leaving the page. A `.nap-ntfscrim` dims the page behind the panel while keeping the header lit (a stacking trap — see `_platform-notifications.md` §9). See [`_platform-notifications.md`](_platform-notifications.md) for the feed page itself.
6. **Day orb** — `.nap-avatar` rendering `DayOrb` (`frontend/src/shared/ui/DayOrb.tsx`) — since the Üveg foundation (`mezo-me75u.1`) a glass sphere holding a coral liquid that rises to the day's fill with a slow wave (formerly the bottom-filling variant of the `#s-orb` sprite), filled/tinted from `useDayOrbFill()` → **`/nap/napom/<today's ISO date>`** (`mezo-yjzhw.4` — the retired `/me/week/napok/<today>` target now redirects here). The orb *is* today, so it skips morning mode; the "A napom" tab (§3) is the entry that honours it instead. It is **not** a profile shortcut — that duplicated the bottom "Én" tab and was retired (`mezo-idz2`); this button is the header's daily status indicator instead, and its `aria-label` speaks the day's fill in words (e.g. "A mai napod · 3 a 6 jelből megvan"), not just in color.

**Popover + landmark contract** (`mezo-atry` fix wave, fixed once here instead of five times): the root is a real `<header>` element; both triggers carry `aria-haspopup="menu"`; either popover closes on **Escape**, on an **outside click**, on a pathname change, on re-tapping its trigger and on choosing an item; the bell menu's eyebrow line is `role="presentation"` (a bare `<span>` is not a valid `role="menu"` child) with the label moved onto the menu's `aria-label`. **Focus management is deliberately NOT here** — no focus trap, no roving tabindex; see §9.

**CSS:** the component still renders `className="nap-head app-head"` — it inherited the `.nap-head` flex row verbatim, plus a new `.app-head { padding-top: 6px; margin-bottom: 7px; }` rule that makes the gap under the header a uniform 13px on all five hubs (it used to be 13px on Nap alone and 11px on the other four, back when each hub hand-tuned its own copy).

### The Napközpont composition

1. **Five orbital actions:** Check-in opens the current unfilled slot (then another unfilled slot, or the overview if all complete); Gyors logolás opens `/nap/gyors`; Napló opens `JournalSheet`; Aktivitás opens `ActivityLogSheet`; Chat opens `/mezo/chat`. Check-in waits for successful hydration to avoid overwriting unseen records. **Visszaöltöztetés (mezo-ju4j6.10):** the five sculptural CSS graphics are clay symbols on icon shields (`i-checkin` · `i-kristaly` · `i-naplo` · `i-sport` · `i-mezo`), and the centre is **`NapCompanion`** — since **mezo-ju4j6.15** the **Boop** figure herself (lavender, the companion's own hue) over a need-coloured halo, alive with the gaze/brow/breath gestures; the Phase 6 clay Mezo symbol was the placeholder in that same slot. The Titanium mark and its live three.js scene (`TitanCompanion`/`TitanScene`) are gone, the package with them. The companion still opens `/nap/eletjel`, and the aura still carries the first three needs' colors, dimmed per band.
2. **Nutrition:** `NapFuelGraphic` displays actual consumed kcal in a light core and three independent 270° arcs for protein/carbs/fat against their own targets. **Since mezo-ju4j6.10 the macro vocabulary is the app-wide one** (owner 2026-09-18): `--macro-protein/carbs/fat` plus the clay `i-hus`/`i-gabona`/`i-avokado` faces — the same colour and symbol Fuel · Mai's rings use, instead of this page's former sky/amber/lavender beads. Macro buttons select gram/target detail; the core restores kcal. Zero, unknown target, loading and read failure are distinct. No duplicate water or check-in statistic strip.
3. **Personal observation:** `NapPersonalInsight` selects the first nonempty, non-rejected observation in the existing server order. `SafeMarkdown` renders the actual prose; expandable evidence explains its basis. Fresh/return both offer `Igen, ez igaz rám` / `Nem, ez nem stimmel` / `Beszéljük meg` through the shared reply contract, guarded against duplicate submissions; chat reuses the returned conversation or passes the observation as context. Empty/degraded/error states make no personal claims.
4. **Mai pillanatok:** the latest eight current-day check-ins, meals, journal notes and activities, sorted by known capture time. Unknown timestamps say “Ma”; scheduled slot times never masquerade as save times. Rows open their existing domain pages. Loading and partial read errors are visible.

The page scrolls. Rough-day mode quiets the decorative motion while preserving the same five entry points. Reduced-motion preferences stop CSS motion and select the existing static companion fallback. Shell header/navigation remain independently owned.

- **GOTCHA — the Észrevételek dot is DERIVED, not part of the unread snapshot.** The other two tabs' `.nap-mzdot`s come from the one-shot `dots` snapshot below; this one is recomputed every render from `useObservations()` — it lights when a `fresh` or `return` card has no `repliedChoice` and the tab is not active. It has to be: observations arrive asynchronously, and the snapshot effect is `null`-guarded so it can never pick them up. It also extinguishes for the right reason — the answered card carries `repliedChoice`, so the dot goes out because the work is done, not because a tab was visited. The observation list is keyed by `item.id`; today's server inbox selects the latest unanswered event per pattern rather than requiring the event to have occurred today.

- **Intervention-push deeplink** (`?n=<full uuid>&d=<card's own day>`, `mezo-b3pp.36`) — this is the page an `intervention`-kind push actually lands on ([`_platform-notifications.md` §3d](_platform-notifications.md) for the backend history: three defects — wrong route, no consumer, a truncated id — plus the cross-midnight date gap the push's card can carry). `NapMezoPage` reads `n`/`d` via `useSearchParams`. **The common case is same-day** (`d` names local-today): the linked row is already inside today's own thread, so nothing is fetched or prepended — the page just scrolls/highlights that existing row (matched by `n` against the thread's own `artifactId`s). Only when `d` names a day other than local-today (a card deferred across midnight, generated late and pushed the next morning) does it call `useCompanionFeed(d, { enabled })` — a second, per-date cache entry, fetched only when there is an `n` to look up (a bare `d=` with no `n` fetches nothing, and a past day's feed never polls — it cannot change) — finds the one `FeedMessage` matching `n`, and prepends it to the page's own `displayMessages` (rendered *alongside* today's thread, never replacing it, and never joining the shell's shared unread-watermark list; the hero's `N üzenet` count is `messages.length`, not `displayMessages.length`, so a cross-day deeplink doesn't inflate it). Either way the target row gets the identical `FeedbackChips` wiring as any other persisted row and is `scrollIntoView({block:'center'})`'d on mount, keyed on a stable id string (not asserted under jsdom — no real layout to scroll, but the effect's own single-fire behavior is asserted via a `scrollIntoView` spy). A stale or unknown id degrades silently: no extra card renders, nothing throws.

Full model in **[needs.md](needs.md)**.

## 3. Architecture & data flow

The single FE↔data boundary stays `frontend/src/data/hooks.ts`; every hook is dual-mode. What changed is the **shape of the composition**: there is no longer one composition root holding every hook for the whole screen. **Each page holds its own hooks** — the hub holds the hooks its heroes and tiles need, and each sibling page re-reads the subset it renders. The pure logic modules are shared and unchanged.

### The logic modules (`frontend/src/features/today/logic/`)

- **`dayFace.ts`** — the day model, **UNCHANGED** since `mezo-ly8c`: three wrap-aware windows off `useSleepGoal()`'s wake/bed anchor (mock: 06:15–11:45 / 11:45–19:15 / 19:15–06:15), the degenerate-anchor guard, `dayFace`/`faceWindows`/`faceOf` + `DAY_FACES`/`FACE_LABEL`/`FACE_EMOJI`. Nobody calls `dayFace()` directly any more: the `?dp=`-or-clock resolution is **`useDayFace.ts`**'s (below). `FACE_ICON` — the clay-icon table — lives in `app/AppHeader.tsx`, the only surface that draws a daypart glyph, and it reads `FACE_LABEL` from here; `FACE_EMOJI` survives for callers that still want an emoji.
- **`useDayFace.ts`** — `useDayFace() → { face, nowFace }`, the ONE place the daypart is resolved (`mezo-atry` fix wave). `nowFace` is `dayFace(useMinuteTick(), sleepGoal)`; `face` is `?dp=` **only when the pathname is exactly `/nap`**, else `nowFace`. Read by `app/AppHeader.tsx` and `NapHubPage` — they had independent copies of the guard, the call and the rule, which is exactly how two surfaces come to disagree at a daypart boundary.
- **`useMinuteTick.ts`** — the 60 s ticker, a **single module-level clock** behind `useSyncExternalStore` (`mezo-atry` fix wave; it used to start a fresh `setInterval` per mount, so two live consumers could sit up to 60 s out of phase and derive different dayparts at the same instant). Every consumer gets the *same* `Date` instance, so memos over it are stable too. One interval runs while at least one subscriber is mounted. Read by `AppHeader` (via `useDayFace`), `NapHubPage`, `MezoThreadProvider` and `EletjelPage`.
- **`needs.ts` / `needsInputs.ts` / `useNeeds.ts`** — the Életjel decay/refill engine, the app-data adapter and the live composition hook. Documented in full in **[needs.md](needs.md)**; the pages only render `needs.states` and dispatch the CTAs.
- **`mezoMessages.ts`** — `buildMezoMessages({ feed, demoBriefing, nudges })`, the day's message thread. For the Nap thread it is called **exactly once**, by `features/today/MezoThreadProvider.tsx` (the shell provider): `NapMezoPage` renders that thread and `AppHeader` counts it. Called directly, on their own domain threads, by Fuel's `FuelMaiPage`/`FuelMezoPage` and the Mezo hub. `NapHubPage` does not read it at all.
- **`MezoThreadProvider.tsx`** (`features/today/`, not `logic/` — it holds React state) — the single Nap-thread instance: `useCompanionFeed` + the labelled demo briefing + the Életjel threshold nudges (`deriveNudges`/`toNudgeMessage`, the `markNudgeShown` log write), plus the read watermark as state (`unread`, `markSeen()`). Mounted by `AppLayout` around `ScreenContent`, so the header (an earlier sibling of the `Outlet`) and the page (under it) share one list and one watermark. **Cost, accepted knowingly:** it pulls `useNeeds` — and with it the ~15 reads the ring engine composes — into the shell, so they fire once per app session on any chrome-bearing route rather than only on `/nap`. That was judged cheaper than two threads that can drift, which is what produced the never-clearing badge.
- **`questAction.ts` / `habitAction.ts`** — the smart-action dispatch tables, **unchanged**. `questAction(quest)` returns `water` / `checkin` / `activity` / a nav target; `habitAction(h)` returns `check` / `nav` / `meal-sheet` / `sleep-sheet` / `intention-sheet` / `intention-reflect` / `none`, and `habitHint(h)` the passive-row explainer. `questAction.ts` has no renderer left on `/nap` itself (the quest tile is DEFERred, C1) but is still live on `/nap/kuldetesek` and Growth's `MaStrip`.
- **`windDown.ts`** — the sleep-anchored windows and `minsToBed`/`fmtMinsToBed`/`isDarkWindow`. `minsToBed` now feeds the evening night-door label (C7) rather than an hero countdown; `isDarkWindow` drives the app-level circadian theme (`app/CircadianTheme.tsx`). **`windDownPhase` itself now has no consumer** (§9).
- **`todayItems.ts`** — the six-source normalizer. **Only `isFillableSlot` is still called in production** (by the check-in page, the quest page and the quick-log sheet); `buildTodayItems`/`itemsForFace`/`openCountByFace` and the dedup tables are intact and tested but unrendered (§9).
- **`itemIcon.ts`** — the emoji ladder, still tested, no renderer (§9). **`dayArc.ts` still belongs to ritual's recap** (`DayStoryStep.tsx`) — do not delete with anything Today-side.
- **`nextStep.ts` — RETIRED (`mezo-yjzhw.4`).** The hub's computed "next step" ladder never got a second importer besides its own test, and the spec resolved the long-standing "wire it or delete it" gotcha (§9) by deleting it: the evening Napzárás entry it worded moved to **`NapzarasCard`** on `NapHubPage` (from `NAPZARAS_CARD_FROM_HOUR`, see the "A napom" subsection below), and A napom's own "most érdemes" card gets its content from **`nextBestAction`** in `logic/napom.ts` instead — a different, day-page-scoped pure rule, not a revival of this one. `NapHubPage` renders no next-step ladder any more.
- **`napom.ts`** (`mezo-yjzhw.4`, spec 2026-09-24 §2–§3/§6) — A napom's pure rules, none calling an LLM: `dayReading(evaluation, day): string` (the live day's one-line reading), `nextBestAction(evaluation, day, now, ritualClosed): NextAction | null` (the "most érdemes" card: napzárás in its evening window unless today's ritual is closed → an undone workout → a missing check-in → nothing; `NapomPage` passes `useRitualDay(today).data.closed`), `doneCount(evaluation): number`, `isNapzarasCardWindow(now, ritualClosed): boolean` and its constant `NAPZARAS_CARD_FROM_HOUR = 20` (20:00 until midnight, unless the ritual is closed), and the morning-mode pair `isMorningMode(yesterday, storage?): boolean` / `markSeen(dateIso, storage?): void` (a `localStorage` key `napom.seen.<date>`, read/written inside try/catch, firing a `napom:seen` window event on write). `useMorningMode.ts` wraps `isMorningMode` in `useSyncExternalStore`, subscribed to that event plus `storage`, so the tab dot clears the instant yesterday's review is on screen rather than on some unrelated re-render.

### The composition

`NapHubPage` owns the current date (`useMinuteTick`), check-in slots/capture, the fuel day, today’s journal range and activities. Feature reads come only through `@/data/hooks`. `buildNapTimeline` is a pure domain-date filter/normalizer. `NapFuelGraphic` is presentational; `NapPersonalInsight` owns observations and reply state. The page conditionally mounts the existing capture sheets; no second persistence or chat engine exists. `useFuelDay` and `useActivities` expose additive error/retry state for honest aggregation.

The check-in hook exposes loading/error/retry. Real saves are awaited, and failed saves leave the draft available; only server-confirmed records enter the timeline. Mock overrides belong to one local date. Daily captures continue to invalidate existing domain queries.

Full-page siblings (`NapGyorsPage`, `NapMezoPage`, `NapRutinPage`, `NapKuldetesekPage`, `NapCheckinPage`, `EletjelPage`) keep their own hooks and routing.

## 7. How to extend it

**Extend Napközpont** — preserve the five stable capture actions. Add data through existing hooks, keep loading/error distinct from zero, and never introduce invented observation copy. Visual changes belong in scoped component/page CSS; honor reduced motion and 320px reachability.

**Add a whole new Nap sub-page** — copy `NapCheckinPage` as the smallest complete example: `MozaikPage tone` → `PageHead onBack` → `PageHero` → `PageBody principle` → `EntranceGroup` around `.rise` content. Hold your own hooks; do not thread data down from the hub.

**Add a new mezo-generated message source** — extend `logic/mezoMessages.ts`'s `buildMezoMessages` (or wire a new upstream hook into `NapMezoPage`). The home observation reads `useObservations`, independently of the messages thread. Test ordering/shape in `mezoMessages.test.ts`.

**Change the day model** — unchanged recipe: constants in `dayFace.ts` (`MORNING_LEAD_MIN` imported from `windDown.ts` on purpose); re-check `dayFace.test.ts` and, if the change touches `/nap`'s structure, `frontend/tests/layout/layout.spec.ts` (screenshot goldens are retired, `mezo-ryb6` — there is nothing left to regenerate).

**Add a clay icon or spot** — the sprites are copied verbatim from `docs/design_2.0/assets/`; add the symbol there first, re-copy, then widen `ClayIconName`/`ClaySpotName`. Never inline an emoji into a tile — the tile language is clay (ADR 0033).

**Promote a mock section to a real backend** — the check-in remains the working template (contract-first → backend package → Liquibase → ITs → dual-mode FE swap); see §4 and the references table in `CLAUDE.md`.

Relabelling or localizing the nudge eyebrow copy does nothing to which pane a card lands in — only `source` does; do not add a second, string-matching partition rule.
- **GOTCHA — `NapMezoPage`'s unread-dot snapshot is protected by its `dots !== null` one-shot guard, NOT by effect declaration order.** Both the snapshot effect and the `markSeen()` effect close over the SAME render's `unread` value — JS closures capture render-local bindings, and `markSeen()`'s call bumps the shared thread's watermark asynchronously, which only changes what `unread` equals on the *next* render, never retroactively inside the effects that already ran this render. So declaration order between the two effects is irrelevant to correctness: even the "wrong" order would freeze the identical pre-visit `unread` into `{ uzenetek, eletjelek }`. What actually makes the snapshot fire exactly once is the `dots !== null` early-return inside the snapshot effect itself — it is a one-shot guard against React's per-render effect re-run, not a defense against `markSeen()` racing ahead of it. Delete that guard (or otherwise let the effect run again after `dots` is set) and the "snapshot" would recompute every render against whatever `unread` currently is, which — once `markSeen()` has cleared it — would make the dots disappear on the very next re-render, not merely fail to appear at mount.
- **GOTCHA — `logic/dayArc.ts` still belongs to ritual's recap** (`DayStoryStep.tsx`). Do not delete it with anything Today-side. (Unchanged warning — the render layer has now swapped five times without this file moving.)
- **GOTCHA — `prototype.css` merges need a brace + comment check.** A union-merge cut the closing `}` off a `@media (prefers-reduced-motion)` block four times during the redesign, and once terminated a comment early on an inline `*/`; the second failed only at `pnpm build`, which vitest does not run. Never resolve a `.tsx` conflict by union (duplicated imports/JSX); CSS union is fine but must be brace-verified. And never pipe a gate into `tail` — the pipe swallows the exit code.
- **Deferred / follow-ups:**
  - **Napzárás is an F7.1 design round, not code** — the Este hero routes to the existing `/ritual` flow, which has not yet been redesigned into Mozaik.
  - **No anchor-mode (rough-day) Mozaik surface** — see the gotcha above; needs a design decision before an implementation issue.
  - **No `?vulnerable` / `?niggle` surface** — both switches are parsed and inert.
  - **Unrendered logic modules** — decide per module whether to delete (`itemIcon`, `seenMessages`, the unused `todayItems` exports) or to re-consume.
  - Older deferreds, still open: **focus management on the header popovers** — the `mezo-atry` fix wave gave both menus Escape, outside-click, `aria-haspopup`, `menuitemradio`/`aria-checked` and a real `<header>` landmark, but deliberately NOT a focus trap or roving tabindex (arrow-key traversal, focus return to the trigger); the weekly-load fact; the weekly-load fact; HRV (no source); real predictions/vulnerable/anchor signals (proactive epic); `questAction`'s unmapped `intention_focus_set`.
