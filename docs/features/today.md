# Today — Feature Documentation

> The Nap tab at `/nap` is the default landing page. **Napközpont** (`mezo-26fw0`) combines five immediate capture actions around the Titanium companion, actual daily nutrition, one grounded Mezo observation and a recorded-moments timeline. Existing shell navigation and sibling pages remain. Design: [approved Napközpont spec](../superpowers/specs/2026-09-17-napkozpont-design.md).

## 1. Summary

**Nap** is the daily capture hub and its full-page siblings under `features/today/pages/`. The stable orbital arrangement makes the five urgent actions directly reachable; deeper browsing stays in existing navigation.

| Route | Page | What it is |
|---|---|---|
| `/nap` | **`NapHubPage`** | the Titanium hub (`mezo-mhum`): companion block + one computed next step + six fixed tiles (the header above it is the shell's `AppHeader`, not the hub's — see below) |
| `/nap/gyors` | `NapGyorsPage` | the FAB's full-page quick-log picker — the shared `QuickLogSurface` grid, `variant="page"` |
| `/nap/uzenetek` | `NapMezoPage` | "Mezo · ma" — the day's companion thread as a page |
| `/nap/rutin` | `NapRutinPage` | the habit chains (`?dp=reggel\|este` preselects which group leads) |
| `/nap/kuldetesek` | `NapKuldetesekPage` | the day's quests as cards, with `Csere` — **DEFER** off the hub landing (manifest C1, `mezo-51ev`); the route and its notification/kalauz deep links still resolve |
| `/nap/checkin` | `NapCheckinPage` | the four check-in slots as a day overview |
| `/nap/eletjel` | `EletjelPage` | the six Életjel rings, each ring its own tile |

### The header is the shell's, not the hub's

Until `mezo-atry`, `NapHubPage`'s `.nap-head` was copy-pasted verbatim into the Edzés, Fuel, Mezo and Én hubs — five near-identical blocks with drifting content. It now lives once, as **`AppHeader`** (`frontend/src/app/AppHeader.tsx`), mounted by `AppLayout` as the first child inside `ScreenContent` on every route except the three chrome-free ones (`/train/session`, `/me/sleep/night`, `/ritual` — the same `hideChrome` flag that also gates `TabBar` and `QuickLogFab`) and `/mezo/chat`, whose own conversation-control header is the single header on that route (`mezo-oq8z`). Since `mezo-8az6` the shell header **kitapad** (`position: sticky`, `top: 0` in the `.screen-content` scroller) instead of scrolling away with the page, and carries a napszak-követő aurora background (`HeaderAurora.tsx`). Since `mezo-oq8z` that aurora remains fully present after the 14px compact threshold (`useCondensedHeader`); only the spacing tightens, so the daypart color neither disappears nor turns into glass. The control row is 42px high with the header's clay icons enlarged by the same 2px; its aurora is a separate background layer extending 18px below the row with a visible mask fade from 70%, while every label and control stays on an unmasked foreground layer. `NapHubPage` itself renders no header at all any more. Six elements (the guide button only where the route has a guide), left to right:

1. **Kalauz „?"** — `.nap-roundbtn.nap-q`, rendered **only when the route has a registry entry** (`findKalauz(pathname)`, `frontend/src/features/tutorial/registry`), always the first button so the daypart switch's presence never shifts it. Opens the page's guide through `useTutorial().open(id)`; carries the `.nap-offnow` amber dot when the route is a T3 guide not yet seen. See [`tutorial.md`](tutorial.md).
2. **Szekció (clay spot + név)** — the mezo-8az6 replacement for the date eyebrow: the dátumot a telefon státuszsávja mutatja, a helyét az „épp melyik szekcióban vagyok" vette át (`app/headerSection.ts` — szekció-szintű, a path első szegmenséből, 115 route mellett tábla nélkül).
3. **Daypart switch** — a round clay button (`.nap-roundbtn`) carrying a daypart's clay icon (`i-hajnal` / `i-nap` / `i-alvas`). It reads `?dp=` **only on `/nap`**; on every other route it shows the real clock-derived daypart, since there is no page there to preselect a mosaic for. Tapping it opens the same three-icon `role="menu"` popover — its items are `role="menuitemradio"` with `aria-checked`, so the selection is exposed, not merely painted by the `.on` class (`mezo-atry` fix wave). Picking a daypart **always navigates to `/nap`**, carrying `?dp=` only when the pick differs from the clock-derived one (picking the clock's own daypart on `/nap` clears the param instead). The navigation **preserves every other query parameter** (`?day=`, `?medCycleDay=`, `?niggle=`, `?vulnerable=`, `?ritual=` — all app-wide scenario switches read by `useTodayScenario`) and uses `replace`, so daypart-tapping neither drops a scenario nor fills the history stack. The `?dp=`-or-clock resolution itself lives in **`logic/useDayFace.ts`**, shared verbatim with `NapHubPage`. The `.nap-offnow` dot — the ADR 0014 dual-signal ("hol tartok" vs "mit nézek") — appears **only on `/nap`**, and only when the shown daypart differs from the clock's.
4. **Mezo-messages circle** — a round button (`i-level` clay icon) with an unread-count `.nap-badge`, navigating to `/nap/uzenetek`. This is the tile that used to sit inside every daypart's mosaic (reggel/nap/este all carried a `Mezo` tile); `mezo-atry` moved it into the header instead, so it now appears exactly once per screen instead of once per daypart. The unread count is watermarked in `localStorage` (`lastSeenMessage`, key `mezo.msgseen.<date>`). **The badge and the page read ONE thread** — `MezoThreadProvider` (`frontend/src/features/today/MezoThreadProvider.tsx`), mounted by `AppLayout` around `ScreenContent`, is the single builder of `buildMezoMessages({ feed, demoBriefing, nudges })` and the single writer of the Életjel nudge log. This is not decoration: while the header built its own **nudge-less** thread and the page stamped the watermark with its own (nudge-bearing) last id, the header's `findIndex` could never match, so the badge fell back to the full count and **never cleared** (`mezo-atry` fix wave). The watermark is also React state in the provider, so the badge goes dark the moment the page marks the thread seen — not one navigation later.
5. **Notification bell** — a second round button with an unread-count `.nap-badge`, opening the `.nap-ntfpanel` **scrollable, full-width notification panel** (mezo-g9fz). It is a child of the `<header>` itself, not of the bell's wrapper — `left: 0; right: 0` against `.app-head` is what makes it full width — and it has three regions: a pinned head (`Értesítések` eyebrow + live unread count + `Mind olvasott`), a horizontally scrollable filter-chip row (`Mind` · `Olvasatlan` · the six categories of `features/notification/logic/category.ts`, each with its clay icon and count, only drawn when non-empty), and the scrolling list, capped at `max-height: min(600px, 74vh)` with sticky `Ma`/`Tegnap`/dated day labels, over an `Összes értesítés ›` foot → `/me/ertesitesek`, the notification **feed page** (`NotificationFeedPage.tsx`), not the preferences page. It shows the newest **30** notifications (`Date.parse(occurredAt)`-sorted BEFORE the slice — the raw arrival order drew today's OLDEST rows, `mezo-tdzy`), each with its kind's clay icon + tint (`APP_NOTIFICATION_KIND_META`), a `.nap-ntf-when` clock (the day is carried by the group label, so `timeLabel()` not `notificationStamp()`), a `deeplink` tap target, and while `readAt === null` the `.nap-ntfrow.unread` wash, a `.nap-ntf-dot` and an `sr-only` „Olvasatlan". Read state here is the LIVE `readAt`, not the feed page's open-time snapshot: in the panel the un-highlighting IS `Mind olvasott`'s feedback. Source: `useNotificationFeed()` + `useNotificationFeedActions()`. The former gap here — the badge had no reachable path that ever called `markAllRead`, so it could never clear (`mezo-61w0`) — is closed twice over: opening the feed page fires `markAllRead()` once, and the panel's own `Mind olvasott` does it without leaving the page. A `.nap-ntfscrim` dims the page behind the panel while keeping the header lit (a stacking trap — see `_platform-notifications.md` §9). See [`_platform-notifications.md`](_platform-notifications.md) for the feed page itself.
6. **Day orb** — `.nap-avatar` rendering `DayOrb` (`frontend/src/shared/ui/DayOrb.tsx`), the bottom-filling variant of the `#s-orb` sprite, filled/tinted from `useDayOrbFill()` → `/me/week/napok/<today's ISO date>`. It is **not** a profile shortcut — that duplicated the bottom "Én" tab and was retired (`mezo-idz2`); this button is the header's daily status indicator instead, and its `aria-label` speaks the day's fill in words (e.g. "A mai napod · 3 a 6 jelből megvan"), not just in color.

**Popover + landmark contract** (`mezo-atry` fix wave, fixed once here instead of five times): the root is a real `<header>` element; both triggers carry `aria-haspopup="menu"`; either popover closes on **Escape**, on an **outside click**, on a pathname change, on re-tapping its trigger and on choosing an item; the bell menu's eyebrow line is `role="presentation"` (a bare `<span>` is not a valid `role="menu"` child) with the label moved onto the menu's `aria-label`. **Focus management is deliberately NOT here** — no focus trap, no roving tabindex; see §9.

**CSS:** the component still renders `className="nap-head app-head"` — it inherited the `.nap-head` flex row verbatim, plus a new `.app-head { padding-top: 6px; margin-bottom: 7px; }` rule that makes the gap under the header a uniform 13px on all five hubs (it used to be 13px on Nap alone and 11px on the other four, back when each hub hand-tuned its own copy).

### The Napközpont composition

1. **Five orbital actions:** Check-in opens the current unfilled slot (then another unfilled slot, or the overview if all complete); Gyors logolás opens `/nap/gyors`; Napló opens `JournalSheet`; Aktivitás opens `ActivityLogSheet`; Chat opens `/mezo/chat`. Check-in waits for successful hydration to avoid overwriting unseen records. Sculptural CSS graphics and the existing `TitanCompanion` provide the animated Titanium language. The companion still opens `/nap/eletjel`.
2. **Nutrition:** `NapFuelGraphic` displays actual consumed kcal in a metallic core and three independent 270° arcs for protein/carbs/fat against their own targets. Macro buttons select gram/target detail; the core restores kcal. Zero, unknown target, loading and read failure are distinct. No duplicate water or check-in statistic strip.
3. **Personal observation:** `NapPersonalInsight` selects the first nonempty, non-rejected observation in the existing server order. `SafeMarkdown` renders the actual prose; expandable evidence explains its basis. Fresh/return feedback follows the existing reply contract, guarded against duplicate submissions; chat reuses the returned conversation or passes the observation as context. Empty/degraded/error states make no personal claims.
4. **Mai pillanatok:** the latest eight current-day check-ins, meals, journal notes and activities, sorted by known capture time. Unknown timestamps say “Ma”; scheduled slot times never masquerade as save times. Rows open their existing domain pages. Loading and partial read errors are visible.

The page scrolls. Rough-day mode quiets the decorative motion while preserving the same five entry points. Reduced-motion preferences stop CSS motion and select the existing static companion fallback. Shell header/navigation remain independently owned.

## 2. User-facing behavior

- **Open the app →** lands on `/nap` (`router.tsx`'s index `Navigate`); mock renders synchronously. A bookmarked `/today`, `/today?dp=este`, `/today/anything` lands on `/nap` with its query string intact — `LegacyPathRedirect` does a `pathname.replace(prefix, to) + search`, `replace`d so the back button doesn't bounce.
- **Fixed chrome** is now the app shell's, not the page's: the single **`AppHeader`**, the 5-tab `TabBar` (Nap · Edzés · Fuel · Mezo · Én) mounted by `AppLayout` and all hidden on the three chrome-free full-screen flows (`/train/session`, `/me/sleep/night`, `/ritual`).
- **Mezo üzenetei** (`/nap/uzenetek`) — the day's whole companion thread as a page: a breathing-orb hero, one block per message (daypart clay spot + `HH:mm · eyebrow` + `SafeMarkdown` prose + `RefTag` refs + meta), never truncated, and a `Beszélgess Mezóval ›` CTA → `/mezo/chat`. The thread logic is the retired sheet's, verbatim: `buildMezoMessages({ feed, demoBriefing })` over `useCompanionFeed()`, with `resolveBriefing(scenario.dayState)` prepended as an honestly-labelled `Demo tartalom` card only while the feed carries no `morning` kind. **Rating a message** is unchanged: a 👍/👎 `FeedbackChips` row renders **only** on a bubble with an `artifactId` (a persisted `companion_message` row) — the demo card never gets chips (`mezo-kr9v`, §9). **The thread splits into tabs** (`mezo-ho9k`; a third joined them in `mezo-eq85.5`, see the next bullet): a `role="tablist"` segmented control (`.nap-mzseg`, the `mem-seg` pill idiom) right under the hero reads `Üzenetek | Életjelek | Észrevételek` and drives a `?tab=eletjelek|eszrevetelek` query param (`Üzenetek` is the default — no param, `{replace:true}`); the partition itself does not reshuffle or refetch the thread, it is a pure display split of the **same** list (`partitionMezoThread(messages)`) into companion messages vs. Életjel nudges. **Üzenetek** shows only its newest card expanded as a full bubble; every earlier one collapses into a one-line `.nap-mzrow` button (eyebrow + first paragraph preview + `▾`) that expands in place on tap — expansion is one-way, there is no re-collapse (YAGNI, matching the approved prototype). **Életjelek** opens with the `EletjelStrip` (six mini-ring cells, one tap → `/nap/eletjel`) followed by any Életjel nudge cards, or the honest line `"Minden gyűrű rendben — ma nincs teendő. ✓"` when there are none. **Unread dots** (`.nap-mzdot`) come from a mount-time snapshot, not a live count: on first render with a non-empty thread, the last `unread` messages are partitioned once into `{ uzenetek, eletjelek }` booleans and frozen in state; visiting a tab clears only that tab's dot, session-locally (§9 — the snapshot effect's declaration order relative to `markSeen()` matters). **The intervention-push deeplink (`?n=`) always forces the Üzenetek tab**, overriding even an explicit `?tab=eletjelek` — a deeplink target is always a companion message or the b3pp.36 intervention card, never a nudge, so it can only exist in that pane — and the linked/target row renders already expanded regardless of its position in the (now-partitioned) list. **Advice cards can carry actions (`mezo-d58h.5`).** An `advice`-kind message with an `artifactId` and a non-empty `actions` list renders them as a `role="group"` („Javasolt lépés") row of `.chip.brand` buttons; applying one (`useAdviceActions`, `data/today/adviceHooks.ts`) replaces the row with the **applied state** — never a disabled button, because a tapped action is a completed thing, not a greyed-out one. The applied state is driven by the **server's** `m.applied`, so a reload re-reads the same feed row and shows the same thing. Beyond the always-invalidated `['companionFeed']` prefix, each action key declares the extra query keys its apply invalidates (`ACTION_INVALIDATES`): `skip_sport_slot` → `sportSlotSkips` (the week agenda), `lighten_tomorrow` → `workoutToday` (the plan row it writes), `shift_sleep_anchor` → `sleepGoal`/`habitDay`/`fuelDay` — otherwise the card reads „done" while the surface it changed keeps rendering the pre-apply state until an unrelated navigation refetches it. Rule semantics, the catalog and the backend apply seam live in [`proactive.md`](proactive.md) §4.
- **Észrevételek — the third tab** (`?tab=eszrevetelek`, Reflexió S5 `mezo-eq85.5`) — where the reflection engine's self-discovered patterns finally reach the user. The pane reads `useObservations()` ([`insights.md` §5.9](insights.md)) and renders one `ObservationCard` per row of `GET /api/companion/observation`, **in the server's order** (fresh → return → watching → confirmed, newest first inside a group) — the FE never re-sorts. The card is the approved prototype's poster anatomy (`docs/design_2.0/prototypes/eszrevetelek.html` `#obsScreen`): eyebrow + clay disc (`sourceIcon`) + state pill (`ÚJ`/`FIGYELEM`/`GYŰLIK`/`BEÉPÜLT`), one Fraunces-italic sentence, the question line, evidence chips. **Only the event cards ask:** `fresh` offers three chips (`Igen, figyeld` / `Nem stimmel` / `Mesélj` → `watch`/`reject`/`talk`), `return` two (`Így van` / `Kivétel volt` → `watch`/`reject`), and `watching`/`confirmed` none — a row card is a status, not a question. Answering POSTs through `useObservationReply()` and swaps the chips for an acknowledgement line; because the backend reply is **not idempotent**, the chip group is disabled while that row's mutation is in flight and never returns after an answer. The acknowledgement is **optimistic with rollback**: a failed POST puts the chips back and shows `Nem sikerült elküldeni — próbáld újra.` — leaving a card acknowledged for a reply that never landed would tell the user Mezo remembered something it did not. `talk` navigates to `/mezo/chat?c=<conversationId>` when the backend seeded one. The `watching` card carries the numbers instead of prose (its wire `text` is empty by contract): an 8-slot tally of `✓`/`✕`/`·` **text glyphs** (never emoji), the `N / minN nap` progress bar with a live `aria-label`, and a `Laborfüzet ›` link to `/mezo/patterns/<hypothesisKey>` when the row has one. The footer line — `Ma még {n} észrevétel fér a keretbe · 22:00 után csendben maradok` — mirrors the backend's `mezo.companion.reflection.notice` budget, which is **not on the wire**: `n = 2 − today's fresh cards`, clamped at 0, with the `2` and the `22:00` living in one `OBSERVATION_BUDGET` constant beside the mock seed (`data/insights/observations.ts`). Keep them in step with the backend config by hand.
- **GOTCHA — the Észrevételek dot is DERIVED, not part of the unread snapshot.** The other two tabs' `.nap-mzdot`s come from the one-shot `dots` snapshot below; this one is recomputed every render from `useObservations()` — it lights when a `fresh` card has no `repliedChoice` and the tab is not active. It has to be: observations arrive asynchronously, and the snapshot effect is `null`-guarded so it can never pick them up. It also extinguishes for the right reason — the answered card carries `repliedChoice`, so the dot goes out because the work is done, not because a tab was visited. And **the observation list is keyed on `item.id`, never deduped by `patternId`**: a `monitoring` row that also produced an observation today legitimately appears twice, once as the event card (event id) and once as the watching row card (pattern id). That is the feed's intent.

- **Intervention-push deeplink** (`?n=<full uuid>&d=<card's own day>`, `mezo-b3pp.36`) — this is the page an `intervention`-kind push actually lands on ([`_platform-notifications.md` §3d](_platform-notifications.md) for the backend history: three defects — wrong route, no consumer, a truncated id — plus the cross-midnight date gap the push's card can carry). `NapMezoPage` reads `n`/`d` via `useSearchParams`. **The common case is same-day** (`d` names local-today): the linked row is already inside today's own thread, so nothing is fetched or prepended — the page just scrolls/highlights that existing row (matched by `n` against the thread's own `artifactId`s). Only when `d` names a day other than local-today (a card deferred across midnight, generated late and pushed the next morning) does it call `useCompanionFeed(d, { enabled })` — a second, per-date cache entry, fetched only when there is an `n` to look up (a bare `d=` with no `n` fetches nothing, and a past day's feed never polls — it cannot change) — finds the one `FeedMessage` matching `n`, and prepends it to the page's own `displayMessages` (rendered *alongside* today's thread, never replacing it, and never joining the shell's shared unread-watermark list; the hero's `N üzenet` count is `messages.length`, not `displayMessages.length`, so a cross-day deeplink doesn't inflate it). Either way the target row gets the identical `FeedbackChips` wiring as any other persisted row and is `scrollIntoView({block:'center'})`'d on mount, keyed on a stable id string (not asserted under jsdom — no real layout to scroll, but the effect's own single-fire behavior is asserted via a `scrollIntoView` spy). A stale or unknown id degrades silently: no extra card renders, nothing throws.
- **Napi küldetések** (`/nap/kuldetesek`) — **DEFERred off the hub landing since the Titanium rebuild** (manifest C1, `mezo-51ev`; the page and every deep link into it are unaffected, only the hub's own tile is gone). Quest cards with the slot's clay icon, title, why, an `+N XP` pill, a quiet state line and up to two buttons: the context-aware smart action (`+250 ml`, `Check-in`, `Naplózz`, or navigation) and `Csere · N maradt` while the reroll budget lasts. ADR 0010's tone is enforced in copy: an offered quest reads *"folyamatban · a logjaidból záródik magától"* (or *"az edzésből záródik magától"* for `gym_session_done`); there is no failure state and no countdown. A check-in action is omitted when no slot is fillable, so the page never renders a dead control.
- **Rutin** (`/nap/rutin`) — the habit chains. `?dp=reggel|este` decides which chain group leads; the other follows below with its own group header. The hero group gets a `StatStrip`: `tökéletes N/30` · `lánc-erő N% · 28 nap` · `+N XP ma`. Tick semantics are the Today dispatcher's, verbatim: a MANUAL row checks/unchecks through `useHabitActions`, a DERIVED row opens its log surface via `logic/habitAction` (`LogFlowPage`, `SleepLogSheet`, `IntentionSheet`, `ReflectSheet`, or a nav), and a row whose action is `none` renders a **non-interactive** tick — nothing self-completes. `habitHint(h)` still replaces the anchor copy on a passive row, so `bed_on_time` and an out-of-window `wake_on_time` read as "this ticks by itself", not as broken. A successful check emits `buildHabitRewardToast` on the `toastBus` (level-up inline in the same card, never the full-screen overlay). See [habit.md](habit.md).
- **Check-in** (`/nap/checkin`) — the four canonical slots as rows in one card: a `done` slot carries its measured values as tinted `MCells` (Energia · Stressz · Testi · Mentális), the **next fillable** slot is the hot row with a `Kitöltöm` button that opens the real `CheckInSheet` measurement flow, and every other slot is muted with `később esedékes` and **no** values — the page is the day overview, the sheet stays the flow. Principle line: *"A kimaradt slot nem vész el — Pótold bármikor, a társ nem büntet."*
- **Életjel** (`/nap/eletjel`) — the six needs rings, promoted out of the old `NeedsRow`. Hero = the segmented six-arc ring (`needRingGradient`, the same gradient the hub tile paints) + the animated average `%`. Below it, six tiles: eyebrow + clay icon + a mini conic ring + the `%`, red/critical tinted with `.ej-warn`. Each tile dispatches **exactly** what the retired `onNeedCta` did — Étel → the unified `LogFlowPage`, Víz → an immediate `+2,5 dl`, Alvás → `SleepLogSheet`, Mozgás → `/train`, Kapcsolat → the next fillable check-in slot — and **Rend is deliberately non-interactive** (it has no log surface, the `NeedRingSheet` doctrine). **Honest state:** while `needs.isPending`, *nothing* numeric renders — no ring, no percentage, no `—` placeholder. Full model in **[needs.md](needs.md)**.
- **Scenario deep-links** (dev/demo affordances): `?dp=` and `?day=good|medium|rough` still work (`?day=` selects the demo-briefing variant that feeds the message thread). `?ritual=waiting|open|done` is still parsed and still consumed by the ritual surface. **`?niggle=`, `?vulnerable=` and the rough-day anchor melt no longer have a Today surface at all** — their renderers were deleted (§9).
- **Sleep duration is HOURS on the wire.** `SleepEntry.duration` is `7.5`, not `450` — the Reggel hero renders it through `fmtHours` (hours → minutes → `h:mm`), producing `7:30`. This bit the implementation (§9).

## 3. Architecture & data flow

The single FE↔data boundary stays `frontend/src/data/hooks.ts`; every hook is dual-mode. What changed is the **shape of the composition**: there is no longer one composition root holding every hook for the whole screen. **Each page holds its own hooks** — the hub holds the hooks its heroes and tiles need, and each sibling page re-reads the subset it renders. The pure logic modules are shared and unchanged.

### The logic modules (`frontend/src/features/today/logic/`)

- **`dayFace.ts`** — the day model, **UNCHANGED** since `mezo-ly8c`: three wrap-aware windows off `useSleepGoal()`'s wake/bed anchor (mock: 06:15–11:45 / 11:45–19:15 / 19:15–06:15), the degenerate-anchor guard, `dayFace`/`faceWindows`/`faceOf` + `DAY_FACES`/`FACE_LABEL`/`FACE_EMOJI`. Nobody calls `dayFace()` directly any more: the `?dp=`-or-clock resolution is **`useDayFace.ts`**'s (below). `FACE_ICON` — the clay-icon table — lives in `app/AppHeader.tsx`, the only surface that draws a daypart glyph, and it reads `FACE_LABEL` from here; `FACE_EMOJI` survives for callers that still want an emoji.
- **`useDayFace.ts`** — `useDayFace() → { face, nowFace }`, the ONE place the daypart is resolved (`mezo-atry` fix wave). `nowFace` is `dayFace(useMinuteTick(), sleepGoal)`; `face` is `?dp=` **only when the pathname is exactly `/nap`**, else `nowFace`. Read by `app/AppHeader.tsx` and `NapHubPage` — they had independent copies of the guard, the call and the rule, which is exactly how two surfaces come to disagree at a daypart boundary.
- **`useMinuteTick.ts`** — the 60 s ticker, a **single module-level clock** behind `useSyncExternalStore` (`mezo-atry` fix wave; it used to start a fresh `setInterval` per mount, so two live consumers could sit up to 60 s out of phase and derive different dayparts at the same instant). Every consumer gets the *same* `Date` instance, so memos over it are stable too. One interval runs while at least one subscriber is mounted. Read by `AppHeader` (via `useDayFace`), `NapHubPage`, `MezoThreadProvider` and `EletjelPage`.
- **`needs.ts` / `needsInputs.ts` / `useNeeds.ts`** — the Életjel decay/refill engine, the app-data adapter and the live composition hook. Documented in full in **[needs.md](needs.md)**; the pages only render `needs.states` and dispatch the CTAs.
- **`mezoMessages.ts`** — `buildMezoMessages({ feed, demoBriefing, nudges })`, the day's message thread. For the Nap thread it is called **exactly once**, by `features/today/MezoThreadProvider.tsx` (the shell provider): `NapMezoPage` renders that thread and `AppHeader` counts it. Called directly, on their own domain threads, by Fuel's `FuelMaiPage`/`FuelMezoPage` and the Mezo hub. `NapHubPage` does not read it at all.
- **`MezoThreadProvider.tsx`** (`features/today/`, not `logic/` — it holds React state) — the single Nap-thread instance: `useCompanionFeed` + the labelled demo briefing + the Életjel threshold nudges (`deriveNudges`/`toNudgeMessage`, the `markNudgeShown` log write), plus the read watermark as state (`unread`, `markSeen()`). Mounted by `AppLayout` around `ScreenContent`, so the header (an earlier sibling of the `Outlet`) and the page (under it) share one list and one watermark. **Cost, accepted knowingly:** it pulls `useNeeds` — and with it the ~15 reads the ring engine composes — into the shell, so they fire once per app session on any chrome-bearing route rather than only on `/nap`. That was judged cheaper than two threads that can drift, which is what produced the never-clearing badge.
- **`questAction.ts` / `habitAction.ts`** — the smart-action dispatch tables, **unchanged**. `questAction(quest)` returns `water` / `checkin` / `activity` / a nav target; `habitAction(h)` returns `check` / `nav` / `meal-sheet` / `sleep-sheet` / `intention-sheet` / `intention-reflect` / `none`, and `habitHint(h)` the passive-row explainer. `questAction.ts` has no renderer left on `/nap` itself (the quest tile is DEFERred, C1) but is still live on `/nap/kuldetesek` and Growth's `MaStrip`.
- **`windDown.ts`** — the sleep-anchored windows and `minsToBed`/`fmtMinsToBed`/`isDarkWindow`. `minsToBed` now feeds the evening night-door label (C7) rather than an hero countdown; `isDarkWindow` drives the app-level circadian theme (`app/CircadianTheme.tsx`). **`windDownPhase` itself now has no consumer** (§9).
- **`todayItems.ts`** — the six-source normalizer. **Only `isFillableSlot` is still called in production** (by the check-in page, the quest page and the quick-log sheet); `buildTodayItems`/`itemsForFace`/`openCountByFace` and the dedup tables are intact and tested but unrendered (§9).
- **`itemIcon.ts`** — the emoji ladder, still tested, no renderer (§9). **`dayArc.ts` still belongs to ritual's recap** (`DayStoryStep.tsx`) — do not delete with anything Today-side.
- **`nextStep.ts`** (Titanium, `mezo-mhum`) — `nextStep(inputs): NextStep`, the hub's ONE computed ladder: este napzárás → reggel intention → reggel morning-habit → check-in stale → water < 60% → workout planned-not-done → life-goal step → journal fallback. Pure, no hooks; `NapHubPage` composes its inputs from the hooks it already holds (`ritualDay.closed`, `intention`, `morningHabitPending`, `checkinStale`, `fuel.consumed.water`/`targets.water`, `today.workoutType`/`workoutDone`, `goalStep`). Returns `{ title, sub, icon, kind: 'route'|'intention', to }` — `kind: 'intention'` is the one rung with no route, it opens `IntentionSheet` instead.

### The composition

`NapHubPage` owns the current date (`useMinuteTick`), check-in slots/capture, the fuel day, today’s journal range and activities. Feature reads come only through `@/data/hooks`. `buildNapTimeline` is a pure domain-date filter/normalizer. `NapFuelGraphic` is presentational; `NapPersonalInsight` owns observations and reply state. The page conditionally mounts the existing capture sheets; no second persistence or chat engine exists. `useFuelDay` and `useActivities` expose additive error/retry state for honest aggregation.

The check-in hook exposes loading/error/retry. Real saves are awaited, and failed saves leave the draft available; only server-confirmed records enter the timeline. Mock overrides belong to one local date. Daily captures continue to invalidate existing domain queries.

Full-page siblings (`NapGyorsPage`, `NapMezoPage`, `NapRutinPage`, `NapKuldetesekPage`, `NapCheckinPage`, `EletjelPage`) keep their own hooks and routing.

### The Mozaik primitives (`frontend/src/shared/ui/mozaik/`)

Owned by the design system, not by Today, but Today is their first and densest consumer:

- **`Tile`** — `{ wash, icon, eyebrow, line?, dot?, delayMs?, onClick?, aria-label? }`; renders `.mz-tile .mz-w-<wash> .rise` with `--d` as the stagger delay, a `<button>` when clickable. Eight washes: `coral · sage · sky · gold · lav · rose · white · most`.
- **`Mosaic`** — the two-column grid. The hero tile lives **outside** it.
- **`MozaikPage` / `PageHead` / `PageHero` / `PageBody`** — the tile → own-page scaffold: tone gradient, back chip, hero recipe (name, then icon + big number in one row), body + the quiet `principle` line.
- **`StatStrip`/`StatCell`**, **`MCells`** (tinted mini-cells), **`CollapsibleStrip`** (thin reference strip whose closed header already carries the summary).
- **`motion.tsx`** — `EntranceGroup` (arms `.mz-play` once per mount, replays on `replayKey`) and `useCountUp` (~30 fps ease-out, instant under `prefers-reduced-motion`).

Tokens are the **`--mz-*`** family in `frontend/src/styles/prototype.css` — washes, two-layer + colored shadows, cell bg/ink pairs, page tones, muted/soft ink. See [`_platform-design-system.md`](_platform-design-system.md) and ADR 0033.

## 5. Integrations

Nap is an **aggregation surface** — its value is the seams. The seams survived the redesign; only where they surface moved.

- **→ Train** — *live shared data + navigation*. The edzés tile renders `today.workoutType` (composed by `useToday` off `useTrain()`) and routes to `/train`. **The hub no longer renders the gym hero's done / in-progress / sport-done states** — `useToday` still carries `workoutDone`/`workoutDoneSets`/`workoutInProgress`/`workoutOpenSets`/`loggedSportKinds`, but the tile shows only the session's name (done-state and set count on the evening stat strip); the full session state lives on the Edzés tab now (§9).
- **→ Fuel** — *shared data + shared write surfaces*. The étkezés tile reads `useFuelDay(date)` for the kcal/protein number and `useFuelPreview()` for the `now` meal window (merged in as its coral highlight, manifest B4). The víz tile writes through `useWaterActions` (in place, plus undo). `EletjelPage`'s Étel CTA and `NapRutinPage`'s `protein_breakfast` branch both open **`LogFlowPage`** — Fuel's unified log flow (the `LogMealSheet` + `AiLogSheet` merge, F3.2). **Stack moved off the hub tile** (manifest C5) — it is reachable through the FAB's `/nap/gyors` quick picker (`NapGyorsPage`'s Stack tile → `/fuel/stack`) and its own full surface is unchanged.
- **→ Me / sleep & weight & goal** — the sleep anchor (`useSleepGoal`) is still the root dependency: one clock drives dayparts, the evening countdown, Napzárás and the circadian theme. `useSleep().lastNight` feeds the sleep tile, `useWeight()` the companion's morning context chip. `useLifeGoalToday` (manifest C6) feeds the ladder's goal rung when a daily step exists.
- **→ Mezo (was Insights)** — the `/insights` → `/mezo` promotion (ADR 0032). `NapMezoPage`'s CTA routes to `/mezo/chat`; the shared `FeedbackChips` component still comes from `features/insights/components/`, deliberately not forked.

- **→ Biometrics backend (real)** — `useCheckins` read+write from the hub, the check-in page, the quest page and the Életjel page. The companion's context snapshot reads the latest check-in ([companion.md §5.5](companion.md)).

The Este hero's CTA routes to `/ritual`; `logic/useNeeds.ts` reads **yesterday's** `useRitualDay` for the 💗 lélek refill, gated on `closed && closedAt`. Today touches exactly three `RitualDay` fields (`closed`, `closedAt`, `window`) — the ritual's own prose is its surface, not this one's. [ritual.md](ritual.md).

## 7. How to extend it

**Extend Napközpont** — preserve the five stable capture actions. Add data through existing hooks, keep loading/error distinct from zero, and never introduce invented observation copy. Visual changes belong in scoped component/page CSS; honor reduced motion and 320px reachability.

**Add a whole new Nap sub-page** — copy `NapCheckinPage` as the smallest complete example: `MozaikPage tone` → `PageHead onBack` → `PageHero` → `PageBody principle` → `EntranceGroup` around `.rise` content. Hold your own hooks; do not thread data down from the hub.

**Add a new mezo-generated message source** — extend `logic/mezoMessages.ts`'s `buildMezoMessages` (or wire a new upstream hook into `NapMezoPage`). The hub tile only reads `messages.length`, so it needs no change. Test ordering/shape in `mezoMessages.test.ts`.

**Change the day model** — unchanged recipe: constants in `dayFace.ts` (`MORNING_LEAD_MIN` imported from `windDown.ts` on purpose); re-check `dayFace.test.ts` and, if the change touches `/nap`'s structure, `frontend/tests/layout/layout.spec.ts` (screenshot goldens are retired, `mezo-ryb6` — there is nothing left to regenerate).

**Add a clay icon or spot** — the sprites are copied verbatim from `docs/design_2.0/assets/`; add the symbol there first, re-copy, then widen `ClayIconName`/`ClaySpotName`. Never inline an emoji into a tile — the tile language is clay (ADR 0033).

**Promote a mock section to a real backend** — the check-in remains the working template (contract-first → backend package → Liquibase → ITs → dual-mode FE swap); see §4 and the references table in `CLAUDE.md`.

### The DayOrb tone axis — where its regression net actually lives (`mezo-x5va`, `mezo-tzid`)
The orb's **height** (how many of the day's signals are recorded) and its **tone** (colour saturation, from the 6-dimension daily evaluation) are guarded at four separate layers, each with a stricter instrument than the one below: `features/today/logic/dayOrbTone.test.ts` (the provisional day score — the `>= 2 DONE` gate excludes `rhythm`, the weighted sum includes it, and both are asserted separately), `dayOrbFill.test.ts` (score → intensity across the 45/92 floor/ceiling), `useDayOrbFill.test.tsx` (the evaluation response → intensity wiring, with `useDayEvaluation` mocked so it runs identically in both modes) and `shared/ui/DayOrb.test.tsx` (intensity → the **exact** `stop-color` hexes).

**Screenshot goldens never covered the tone axis and are retired anyway** (`mezo-ryb6`, 2026-09-07 — `tests/visual/` is gone, `tests/layout/` replaced it with structural Playwright specs, no PNG baselines). Even while the goldens existed, `mezo-x5va`'s rewrite of the orb's colour derivation moved **zero pixels** on any baseline: the pale↔full shift stayed under `pixelmatch`'s 0.2 per-pixel threshold. The hex assertions above are the instrument for this axis; a layout spec (structural, no pixels) could never have caught it either. The one gap the four layers left was the **composition** — an `AppHeader` that passed a constant instead of `dayOrb.intensity` would keep all four green — and `frontend/src/app/AppHeader.dayOrbTone.test.tsx` closes it by reading the rendered header's `.dayorb stop` colours for a strong, a weak and an absent evaluation.

**Three test gotchas worth inheriting:**
1. **The wall clock is pinned.** `useMinuteTick` is mocked to a fixed `13:42`, because `setFace` *deletes* `?dp` when the clicked face is already the now-face — on a CI runner whose clock lands in the este band, a `dp=este` assertion would pass vacuously. This exact flake failed a real CI run.
2. **Shared external stores for in-place writes.** Several hooks read `useFuelDay` (the page *and* the needs sim), so a per-instance `useState` stub lets `logWater` update the wrong instance; the water test uses one hoisted store with `useSyncExternalStore`.
3. **Sport-slot isolation includes the active mesocycle.** `useDayOrbFill.test.tsx` pins one clock
   for the tested weekday/date and overrides both the sport schedule and active mesocycle. Clearing
   only `/gym-schedule` is insufficient: `useTrain` derives a planned gym day from the active
   mesocycle even when that day has no standalone time slot, so a Thursday runner can add an
   unrelated sixth denominator signal to a sport-only assertion.

## 9. Decisions, gotchas & deferred

- **App startup (`mezo-qducz`):** the app-root `StartupSplash` reuses the Dashboard's
  lazy Titanium geometry through the non-interactive `TitanArtwork` export in
  `TitanCompanion.tsx`. `TitanMark` uses per-instance SVG gradient IDs so the splash and
  Dashboard fallback can coexist. The splash has one slow scale pulse with three distinct
  light flashes and reveals the app after 3 seconds including fade, measured from the first
  rendered frame. During lazy loading the startup artwork is blank instead of flashing its
  2D fallback. `TitanScene` accepts `decorations={false}` for this core-only startup variant
  (no orbital rings/beads, core ring, particles or ground glow); the Dashboard retains the
  default scene. Its `onReady` callback fires after the first composed frame, and
  `onUnavailable` selects the static terminal fallback on renderer/context failure. Desktop previews
  use the existing phone frame; real mobile fills the display. The existing `/` → `/nap`
  landing is unchanged.
  Reduced-motion/missing-WebGL browsers get the existing SVG; an artwork chunk failure
  is contained by an error boundary. See [platform startup behavior](_platform-design-system.md#9-decisions-gotchas--deferred).

The standing `AppHero` identity/XP chrome is gone from this screen (the orb avatar replaces it). - **GOTCHA — `SleepEntry.duration` is HOURS, not minutes.** The wire value `7.5` means seven and a half hours. `NapHubPage.fmtHours` converts (`hours × 60 → h:mm`) to print `7:30`; the sibling `fmtHm` takes **minutes** and is what `minsToBed` feeds. Each of the five still has its own colocated test, which is why they read as live at a glance. Keep-or-delete is an open follow-up (a bd issue for the controlling round files it) — do not delete on a hunch mid-pass. (This warning has now survived five render-layer swaps.)
- **GOTCHA — a feedback chip may ONLY sit on a persisted artifact** (`mezo-b3pp.15`, closes `mezo-kr9v`). The thread mixes bubble kinds and only a **feed row** carries a `companion_message` uuid; the demo-briefing card is a labelled `Demo tartalom` stand-in with no row anywhere. `NapMezoPage` gates on `m.artifactId != null`. Do not "complete" the UI by giving the demo card an id: a vote that lands on nothing (or on a fabricated uuid) is the false affordance `mezo-kr9v` was filed about, and it would poison the training data with opinions about copy the app wrote client-side.
- **GOTCHA — feed chips are real-mode-only in practice, and that is deliberate.** `useCompanionFeed`'s mock mode returns `[]` ([`proactive.md` §5.4](proactive.md)), so mock's thread is the demo card alone — not votable. Chips therefore never appear in mock-mode tests.
- **GOTCHA — `MezoMessageItem.id` is NOT the artifact id.** `id` is the feed KIND (a React key, stable within the day); `artifactId` is the row uuid and the vote key. Deliberately separate; do not collapse them.
- **GOTCHA — the Üzenetek/Életjelek tab split's partition key is `MezoMessageItem.source === 'eletjel'`, not the "Életjel" eyebrow text.** `toNudgeMessage` (`needsNudges.ts`) is the one place that sets `source: 'eletjel'`; `partitionMezoThread` (`mezoMessages.ts`) reads that field, and `NapMezoPage` renders whichever tab a card's `source` puts it in. Relabelling or localizing the nudge eyebrow copy does nothing to which pane a card lands in — only `source` does; do not add a second, string-matching partition rule.
- **GOTCHA — `NapMezoPage`'s unread-dot snapshot is protected by its `dots !== null` one-shot guard, NOT by effect declaration order.** Both the snapshot effect and the `markSeen()` effect close over the SAME render's `unread` value — JS closures capture render-local bindings, and `markSeen()`'s call bumps the shared thread's watermark asynchronously, which only changes what `unread` equals on the *next* render, never retroactively inside the effects that already ran this render. So declaration order between the two effects is irrelevant to correctness: even the "wrong" order would freeze the identical pre-visit `unread` into `{ uzenetek, eletjelek }`. What actually makes the snapshot fire exactly once is the `dots !== null` early-return inside the snapshot effect itself — it is a one-shot guard against React's per-render effect re-run, not a defense against `markSeen()` racing ahead of it. Delete that guard (or otherwise let the effect run again after `dots` is set) and the "snapshot" would recompute every render against whatever `unread` currently is, which — once `markSeen()` has cleared it — would make the dots disappear on the very next re-render, not merely fail to appear at mount.
- **GOTCHA — `logic/dayArc.ts` still belongs to ritual's recap** (`DayStoryStep.tsx`). Do not delete it with anything Today-side. (Unchanged warning — the render layer has now swapped five times without this file moving.)
- **GOTCHA — `prototype.css` merges need a brace + comment check.** A union-merge cut the closing `}` off a `@media (prefers-reduced-motion)` block four times during the redesign, and once terminated a comment early on an inline `*/`; the second failed only at `pnpm build`, which vitest does not run. Never resolve a `.tsx` conflict by union (duplicated imports/JSX); CSS union is fine but must be brace-verified. And never pipe a gate into `tail` — the pipe swallows the exit code.
- **Deferred / follow-ups:**
  - **Napzárás is an F7.1 design round, not code** — the Este hero routes to the existing `/ritual` flow, which has not yet been redesigned into Mozaik.
  - **No anchor-mode (rough-day) Mozaik surface** — see the gotcha above; needs a design decision before an implementation issue.
  - **No `?vulnerable` / `?niggle` surface** — both switches are parsed and inert.
  - **Unrendered logic modules** — decide per module whether to delete (`itemIcon`, `seenMessages`, the unused `todayItems` exports) or to re-consume.
  - Older deferreds, still open: **focus management on the header popovers** — the `mezo-atry` fix wave gave both menus Escape, outside-click, `aria-haspopup`, `menuitemradio`/`aria-checked` and a real `<header>` landmark, but deliberately NOT a focus trap or roving tabindex (arrow-key traversal, focus return to the trigger); the weekly-load fact; the weekly-load fact; HRV (no source); real predictions/vulnerable/anchor signals (proactive epic); `questAction`'s unmapped `intention_focus_set`.
