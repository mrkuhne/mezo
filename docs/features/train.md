# Train — Feature Documentation

> The six-tab strength + conditioning area (plan, execute, log, analyze). **Status: ✅ done (FE mock + FE real + Spring Boot backend)** — the only gaps are clearly-flagged Phase-3 AI/analysis features. Lives under the **`Edzés`/Train** tab at route `/train` (sub-nav defined in `frontend/src/features/train/pages/tabs.ts`).

---

## 1. Summary

Train is the largest mezo domain: a seven-tab area for planning and executing strength work and conditioning. It covers periodized **mesocycles** (`Mesociklus`), the active week's **gym split**, full-screen **workout execution** with per-set logging, an **exercise catalog + per-exercise records** explorer, **sport** (`Röplabda` — volleyball, cross, and TRX, 0..n scheduled slots per day, `mezo-05v6`) scheduling/logging, and structured **interval running** (`Futás`) plans. A `Mai` tab surfaces all three rhythms (gym + sport + running) for **one selected day at a time** via a `DayStrip` navigator (default: today; `mezo-9bbc`), with the detailed Mon–Sun agenda split out to a sibling `Heti` tab.

**Status per layer — all ✅ done:**

- **FE mock** (Phase 1): synchronous static fixtures, every tab renders without a backend.
- **FE real** (Phase 2): each read/write swapped to `/api/train/*` behind the same hooks; no signature change.
- **Backend** (Phase 2): full `feature/train/**` Spring Boot slice over Postgres — mesocycles, workout execution, sport, exercise catalog/records, running.

**Phase-3-planned (🟣, flagged throughout, do NOT assume live):** `niggleWarning`, PR detection (the current toast is a scripted demo), the live **cross-load → volume recompute engine** (Sport AND Running cross-load are still static; since `mezo-ly27` the **static `sportMuscleLoad.ts` heuristic is its FE interim** on the Gym `MuscleWeekSheet` — this is a DIFFERENT thing from the weekly performance ramp below, which IS live), `shoulderLoadTrend`, sport `jumpCount`/`intensity`/`team`/`season` capture, gym-schedule **`duration`** (the gym-time **schedule is now live** — see §4 `GymScheduleSlot`; only per-day duration stays out of scope), copy-week, and the active-workout **Voice** tool (still no UI at all, Phase 3). **Progressive Overload Plan 2 SHIPPED** (design spec `2026-07-25-progressive-overload-design.md`, above; PR #80 + the Phase B arc surface, `mezo-hi9m`): the performance-driven **weekly volume ramp** toward MRV is a real engine now — `VolumeProgressionService.rolloverIfDue` writes `MuscleGroupVolumeLogEntity.currentSets` + a `volumeRecompute` audit live, per calendar week — and the read-only **`Mezociklus áttekintő`** volume-arc surface + the Mai/Gym entry chips are live too, §2/§4. **Progressive Overload Plan 3 SHIPPED too** (`mezo-gj42`) — completing the progressive-overload checklist alongside Plan 1 (`mezo-5pfe`, the RIR-aware, deload-aware intensity engine + the in-workout `ProgressionBanner`/prep-chip signal): a deterministic (non-LLM) daily **`overload` challenge** surfaces the day's biggest recommended jump as a proactive workout-challenge card — a guaranteed +1 alongside the existing LLM-generated PR/Depth/Volume ones, §2. Mechanism/evaluator/display live in [proactive.md §HBWI](proactive.md). **The cross-load → volume engine is a separate, still-Phase-3 gap** — the weekly ramp above reacts to logged performance (reps/RIR) within Train itself, NOT to Sport/Running load; do not conflate the two. Also worth knowing: the mock's rich `volumePerMuscle`/`volumeRecompute` **prose** provenance is still fuller than what the real engine writes — the engine's `volumeRecompute.changes[]` is a terse per-muscle change list (`"+2 sets"`/`"tartás"`/`"deload"` + a one-line HU reason), not narrative. **The old inert `90s` timer chip is gone, not deferred** — Napiv S5 (`mezo-8141`) replaced it with a real rest countdown (since `mezo-xt65` an **in-card CTA-morph bar**, §2), whose 150s/90s duration is a **hardcoded** per-exercise-type heuristic (`restTimer.ts`), not a data field; a configurable per-exercise rest duration would need a new backend field (Phase 2 backlog candidate, not Phase 3).

## 2. User-facing behavior

**Since the gamified-header slice (`mezo-k7rn`, 2026-07-18), `TrainSection` renders the shared `AppHero` identity/progression header** — every Train sub-page inherits it exactly like the pre-existing `.pghead-np` per-page headers below it. **Since the compact-header redesign the same afternoon (`mezo-ugqb`), `TrainSection` also passes a `SubNavDropdown` as `AppHero`'s `utilities` prop** (`TrainSection.tsx` — `items={TRAIN_TABS}`, `accent="var(--coral-deep)"`); Train's sub-nav is no longer its own row/component, just this one prop. `AppHero` itself is domain-free platform chrome (avatar + XP ring/level badge, equipped title, label-less 🔥/⚡/🪙 counters). See [growth.md](growth.md) for the account-progression domain and [`_platform-design-system.md` §1a](_platform-design-system.md) for the `.apphero`/`SubNavDropdown` CSS families.

The sub-nav (`TRAIN_TABS`, `frontend/src/features/train/pages/tabs.ts`, rendered via the shared `SubNavDropdown`) has seven tabs: **`Mai`** (`/train`), **`Heti`** (`/train/week` — the detailed weekly agenda split out of Mai, `mezo-9bbc`, see §2), **`Gym`** (`/train/gym`), **`Sport`** (`/train/sport`), **`Futás`** (`/train/futas`), **`Gyakorlatok`** (`/train/exercises`), **`Mesociklusok`** (`/train/mesocycles`). Six full-screen sibling routes have no sub-nav: active workout (`/train/session`), the done-day review (`/train/review/:workoutId`, `WorkoutReviewPage`), mesocycle planner/builder (`/train/mesocycles/new`, `/train/mesocycles/:id`), the running-block builder (`/train/futas/:id`), and the **custom-workout composer** (`/train/custom/new`, `/train/custom/:id`, `CustomWorkoutBuilderPage` — `mezo-ws2x`, see the `Saját edzés` subsection below). **Since Napiv S4 (`mezo-8141`) the tab label reads `Gym` (was `GYM`)** — a copy-only change (the route/id are untouched). **`TrainSubNav.tsx` and the `.np-pills`/`.np-pill` pill-nav CSS it rendered are deleted (compact-header redesign, `mezo-ugqb`)** — the chip shows the active tab's label (`"Gym ▾"`) and tapping it opens a popover menu instead of a pill row; see [`_platform-design-system.md`](_platform-design-system.md) §3/§5 for the primitive. **Every Train page still opens with a `.pghead-np` page-head** (an `.over` eyebrow line + `h1`, optionally a `.pgact-np` pill action chip) in place of the generic `.page-header`/`Eyebrow`/`PageTitle` idiom described in the design-system doc.

### `Mai` — the one-day view (`pages/TrainTodayPage.tsx`)
**A one-day page over a `DayStrip` navigator (`mezo-9bbc`), replacing the old ~2.5-viewport weekly scroll (re-measured at exactly 1.00 viewports — 956px scroll height at 440×956 — via the visual-suite's own mock fixture/clock-pinning; this is a snapshot of one fixture state, not a hard ceiling, so treat "≈1 viewport" as the design target rather than a universal guarantee).** `.pghead-np` header (`Edzés · {shownDay} · W{n}`, or just `Edzés · W{n}` with no resolvable day) + `h1` (`Mai nap` while today is shown, else the shown day's HU label, with a `← Ma` `.pgact-np` chip back to today) → the horizontal **`DayStrip`** (`components/DayStrip.tsx` — `role="tablist"`, one `.daychip` `role="tab"` per weekday: `MA`/day-number + per-session `SessionTone`-coloured dots + a done-count/`pihenő` line, pre-derived by the pure `logic/dayStripItems.ts`) → the Mezociklus áttekintő entry card (unconditional) → the **shown day's** hero card(s) in time-of-day order — a coral `.trainhero` gym hero **only while today is shown** (the unchanged three-state gate below), or a read-only-capable `.todaycard` gym/sport/run card on any other day (`components/TodaySessionCard.tsx`, **one card per scheduled sport slot**), plus — on any day, today included — one permanently-logged gym-tone `.todaycard` per **completed custom (saját) instance** of that day (`SAJÁT · MEGVAN` tag, no state chip, `DoneBar` → `/train/review/{id}`; `mezo-9bbc` final review, so a day whose only session was a saját workout is no longer mis-rendered as a rest day) — → a **today-only open-instance resume card**, gated to a day with no gym schedule slot (a started-but-unfinished custom/meso-less workout would otherwise have no resume affordance anywhere on Mai, since the gym hero above only covers a scheduled gym day — `mezo-ws2x` Finding 4; `todaySession.openWorkout` + `workout` from `/today`'s open-wins resolution) → a rest-day card when nothing is scheduled on the shown day **and** no such open instance is showing (today's copy offers "+ Saját edzés"; a non-today rest day is copy-only, "Ezen a napon nincs tervezett edzés.", no CTA; the two cards are mutually exclusive by construction) → the **today-only** morning-training nudge. **The weekly list (`WeeklyDayRow` `.dayrow` cards), the `LoadTiles` weekly-load summary, and the provenance note moved to the sibling `Heti` page** (`/train/week`, see the subsection right below) — Mai renders none of the three any more; nothing was dropped, only relocated. `TrainTodaySkeleton` mirrors **this** shape (page-head → a 7-chip `.daychip`-geometry `DayStrip` placeholder → the gym-hero block), not the weekly timeline that moved to Heti, so the loading→content swap does not reflow (`mezo-9bbc` final review). Mai's no-meso ghost likewise no longer promises a „Heti terv” section — only the hero ghost + the dashed "+ Saját edzés" row remain.

**Selected-day state — the URL is the single source of truth (`mezo-9bbc`).** `selectedDay: string | null` (`null` ⇒ today) is **derived from `?day={0..6}` on every render** (a `DAY_ORDER` index — the Heti drill-in contract, below), never mirrored into component state; a `DayStrip` tap and the `← Ma` chip both write it back via `setSearchParams(…, { replace: true })` (day-hopping inside Mai is a view switch, not a history step the back button should unwind chip by chip). Deriving rather than seeding is what keeps URL and view in sync in **both** directions: a reload or a back step keeps the day you were on, and tapping the `Mai` sub-nav entry from `/train?day=5` — which drops the query **without remounting the route element** — snaps the page back to today. Hostile input still resolves to today: `null`/`''` skip `Number()` entirely (`Number(null) === Number('') === 0` would silently pin every plain `/train` visit to Monday), and non-integer/out-of-range values are rejected; an unparseable value is left in the URL untouched. `shownDay = selectedDay ? agenda.find(day===selectedDay) ?? todayRow : todayRow`. 

**Which day is "today" — one date-based derivation (`mezo-9bbc` final review).** `todayRow = agenda.find(isToday) ?? agenda.find(date === localDateString())`, and `todayIso = todayRow?.date ?? localDateString()` feeds **all** of the page's date math (`sessionState`, `loggedSportOn`, the retroactive `date` threading). The **flag wins** because mock mode's "today" is a fixture flag pinned to `Csü` (`data/train/train.ts`) while the clock is whatever day it really is — reading the clock for the date math while the agenda's today came from the flag made every card on that row compute against the wrong calendar day (on any real weekday but Thursday the mock run card merged in by `todayRuns` read `TERVEZETT`/`ELMARADT` and lost its log CTA; the frozen visual clock, a Thursday, was the one day this was invisible). The **calendar fallback** covers real mode, where `deriveGymSchedule`/`toSportSchedule` only stamp `isToday` on a day that also has a gym/sport slot (§9): a true rest day or a run-only day flags no row at all, and without the fallback today's own agenda row — its rest copy, its completed custom instances — was simply missing. `isTodayShown` is date-based for the same reason, `selectedDay === null || (shownDay?.date ?? todayIso) === todayIso`; the old flag test rendered today as "not today" whenever you tapped today's **own** chip on a rest/run-only day (or drilled in from Heti's today row), which showed the weekday instead of „Mai nap”, offered a pointless `← Ma`, suppressed the morning nudge, and — functionally — dropped both the `+ Saját edzés` CTA and the in-progress custom-workout resume card, leaving no way to start or resume a custom workout from Mai. Switching days is a pure client-side re-render over the already-fetched week agenda — **no refetch**. `todayRuns` (the running hero's date-based prescribed sessions, `runSessionsForDay(activeRunningBlock, todayIdx())`) only merges into the shown day while today itself is shown; a non-today selection uses the agenda's own day-of-week-matched `running` list instead — the mock fixture's `isToday` flag (pinned to Csü) and the real calendar date are intentionally two different clocks (§9).

**Session-card anatomy (`mezo-lruy`).** All three modalities share one rhythm — tag → time → title → fact pills → full-width CTA — so gym, sport and running read as one family instead of three bespoke layouts: the gym `.trainhero` keeps its coral gradient + `.chip-np` pills; **`TodaySessionCard`** (`.todaycard`, `.todaycard-{tone}` modifier, `logged` state class) is its lighter surface-card sibling for the recurring/prescribed sessions AND, since `mezo-9bbc`, for a **non-today gym day** too (`ctaLabel` omitted ⇒ read-only, e.g. a day with no `gymDayTarget`) — a `.todaycard-top` row opens with a 44px `.todaycard-icon` shield (the modality emoji, swapped for a ✓ check glyph once `.logged`) beside a `.todaycard-head` block: a `.typetag-{tone}` tag (**five tones** — `gym`/`sport`/`cross`/`trx`/`run`, `SessionTone` in `logic/sportKinds.ts`; appends `· MEGVAN` once logged) + `.todaycard-time` (hidden once logged) + a display `.todaycard-title`; while still unlogged, a trailing `.todaycard-state` chip carries one of exactly **four** `sessionState` labels (`MOST`/`MA`/`ELMARADT`/`TERVEZETT`, `logic/sessionState.ts`'s `SESSION_STATE_LABEL`) — **a logged card shows none of them**, its eyebrow reading only `{tag} · MEGVAN` instead. Below the head: the slot's facts as `.metapill`s (sport: `perc` · role · location; running: RPE target · rounds; non-today gym: exercise count · duration), then a full-width `.todaycard-cta` (log / start) — or, once logged, the shared `DoneBar` in place of the pills+CTA entirely — accent-tinted per modality through the `--tc-accent`/`--tc-wash` custom-property pair. **On Heti**, each session is its own padded `.s` block inside a `WeeklyDayRow` `.dayrow` day card: a `.dayrow-head` label row (day + `MA` marker + chevron) over `.s-top` (type tag + `.s-title` + the `kész`/`log`/`folyamatban` chip) and `.s-meta` fact pills.

**Convergence, ordering & done-state.** Where gym, sport (volleyball/cross/TRX), and running converge. Both **Mai's hero cards** (for the shown day) and **Heti's weekly rows** (`WeeklyDayRow`) order **by time-of-day** rather than a fixed gym→sport→running modality order — a morning run renders above an evening gym; untimed sessions sort last. Both surfaces order through the same pure helper `daySessions(day)` (`features/train/logic/agenda.ts`), which flattens a day's `{gym, sport[], running[], custom[]}` — `WeeklyAgendaDay.sport: VolleyballSession[]` (`components/WeeklyDayRow.tsx`) holds **0..n slots per day**, each carrying its own `sport: volleyball|cross|trx` (resolved via `sportOf(slot)`, `logic/sportKinds.ts`) — into typed `AgendaItem`s carrying `timeOfDay` and sorts ascending (null/`''` → `'99:99'` last, then stable by modality). The union's **fourth member, `kind: 'custom'`** (a completed saját instance; untimed, so it always sorts last) was added in the `mezo-9bbc` final review so Mai's one-day view stops losing an already-shipped session type: it drives Mai's `SAJÁT · MEGVAN` card and a gym-tone `DayStrip` dot (`toneOf` maps `custom → 'gym'`, and Mai's `isDone` predicate returns `true` for it by construction). **`WeeklyDayRow` filters the member back out** (`daySessions(agenda).filter(kind !== 'custom')`) because it already renders completed saját instances in its own trailing block — that path is untouched. The Mon–Sun agenda itself is built once by the shared pure `buildWeekAgenda` (`features/train/logic/weekAgenda.ts`, lifted out of `TrainTodayPage` unchanged, `mezo-9bbc`) and consumed by both `TrainTodayPage` and `TrainWeekPage`. Gym time comes from the standalone gym schedule (§4 `GymScheduleSlot`); running time from each session's `timeOfDay`. On **Mai** you can log a sport (volleyball/cross/TRX) or running session inline via the shared `SportLogSheet`/`RunLogSheet` — since Task 9 (`mezo-9bbc`) this works on **today or any past day** of the shown week, not just today: each card's CTA is driven by the same three-way `sessionState` read as its `stateLabel` (above) — `planned` (a future day) ⇒ no CTA, read-only; `missed` (a past, unlogged day) ⇒ **`Pótold`**; `now`/`today` ⇒ the original copy (`Logold a session-t`/`Naplózd a futást`). Both sheets declare an optional `date?: string` prop, but **only `SportLogSheet`'s Mai wiring actually omits it on today** — `date={shownIso === todayIso ? undefined : shownIso}` — because `SportSessionCreateRequest.date` is optional and the server defaults to now when the body has no date (`sheets/SportLogSheet.tsx`); `RunLogSheet` (`sheets/RunLogSheet.tsx`) is wired to **always** receive `shownIso` from Mai (`date={shownIso}`, never omitted there) because its contract has no server-side default — `date` is resolved client-side regardless of whether the prop was passed, `date ?? localDateString()`, never the old UTC-shifting `new Date().toISOString().slice(0,10)` (which mis-logged a late-evening/early-morning run onto the wrong day in CET). The omission semantics matter at other call sites too: `SportPage`'s own log CTA and `RunningPage`'s own log CTA both omit `date` entirely (today-only, no retroactive path there), relying on the same optional-prop/internal-default behavior each sheet already has — Mai is simply the one call site that supplies a non-today value. A logged past session's `DoneBar` stays tappable, re-opening the sheet against that same past date. **Mock mode honours the same `date`** (`data/train/trainHooks.ts` — `logSportMutation`'s mock branch appends `huMonthDayDow(req.date ?? localDateString())`, mirroring `runningHooks`' already-correct spread of the body): it used to hardcode today, so in the PWA demo a `Pótold` appended the session to **today** — the past day kept its `ELMARADT`/`Pótold` and today's card wrongly flipped to `MEGVAN` (`mezo-9bbc` final review). The sport CTA also **pre-selects the tapped slot's sport** (`SportLogSheet`'s `initialSport` prop, driven by `setSportLogSport(k)`); on **Heti**, tapping a non-gym session instead **drills into Mai with that day selected** (`/train?day={index}`, see below) rather than logging inline — Heti gained no retroactive-logging affordance of its own. **Once a session is logged, its hero/row flips to a `done` state — matched by date AND sport**, so a mixed day (e.g. a noon TRX slot + an evening volleyball match) flips each slot independently (`loggedSportOn(iso, k)`/`sportDoneOn`, day-parameterized since `mezo-9bbc` — the shown day's `iso`, not always today): the `.todaycard-state` label chip disappears and the type tag gains a `· MEGVAN` suffix instead, and the fact-pills + CTA are swapped out entirely for the shared `DoneBar`'s sage summary of the logged effort (volleyball: `RPE {n} · {n}p · váll {n}`; cross/TRX: `RPE {n} · {n}p` — no `váll`; running: `RPE {n}` (+ ` · {n} kör` when the round count is known); **gym**: a **three-state gate**, today only — see the gym-hero gating paragraph below). The `DayStrip` chips carry the same done-state, pre-computed per session by `dayStripItems(agenda, isDone)` into a `doneCount`/`dots` pair. Ghosts entirely when there is no active mesocycle ("+ Tervezz mesociklust") on **both** Mai and Heti — Mai's ghost still offers a dashed "+ Saját edzés" row below its own placeholder, since a custom workout needs no meso at all (`mezo-ws2x`, see the `Saját edzés` subsection below).

**Mezociklus áttekintő entry card (Progressive Overload Plan 2 Phase B, `mezo-hi9m`).** Directly under the `DayStrip`, an active meso renders a `🗓 {shortTitle} · {phase} · W{n}/{N} →` entry card that opens the read-only `Mezociklus áttekintő` overview (`/train/mesocycles/:id/overview`, see the subsection below) — hidden entirely without an active mesocycle; unconditional on which day is shown.

**Morning-training nudge (`mezo-67rb`, `MorningTrainingCard`) — today only.** When a gym slot falls **after** the wake-derived window end, a gentle sage `.mtr` card offers moving the offending slot(s) into the morning window. The window is `morningWindow(useSleepGoal().goal.wakeTime)` = **[wake + 60′, wake + 6h]** (`features/train/logic/morningWindow.ts`, the FE mirror of the backend `mezo.habit.workout-window-hours`); a slot *earlier* than the start is still morning training, so only `time > end` offends. „Áthelyezés a reggeli ablakba" is a **one-tap `saveGymSchedule` replace-all** (offenders land on the window start, the rest pass through; mock also `setQueryData(['train','gymSchedule'])` for parity), and „Maradjon így" **content-key-snoozes** it in `localStorage` (`mezo-morning-training-snooze`, keyed on wake + the offending slots so any wake/schedule change re-arms the card). Since `mezo-9bbc` the card only mounts while `isTodayShown` — selecting another day hides it. No red, no streak pressure — the ADR 0010 tone. See [`_platform-design-system.md`](_platform-design-system.md) §3 for the `.mtr` family.

**Gym-hero done-day gating (`mezo-cd8s`) — today's three-state hero, unchanged by `mezo-9bbc`.** The gym hero is a **three-state gate** driven by today's instance, not by `weekDoneDates`, and only ever renders while today is shown: (1) **no instance** → the `Indítsuk →` start CTA (`openSession` → `/train/session`); (2) an **open** (started, unfinished) instance (`todaySession.openWorkout`) → a `● Folyamatban` eyebrow chip + a `Folytassuk → · {n} szett kész` resume CTA, `n` = the non-skipped set count; (3) a **completed** instance (`completedTodayWorkout` — since the cross-day start (`mezo-p7rp`) the resolved day's most recent finished instance **of the current Mon–Sun week**, not just today's) → a success-tinted `Kész · {n} szett — Megnézem →` button that opens the read-only review `/train/review/{completedTodayWorkout.id}` (`WorkoutReviewPage`, renders the shared `WorkoutSummary` in `closed` mode). Both `todaySession`/`completedTodayWorkout` come from `/today` and are **real-mode only** (null in mock → the hero is always `Indítsuk →`, byte-identical to Phase 1). **Since `mezo-p7rp` the `/today` day resolution is `open instance > ?day= param > weekday label`** (§4) and the session route accepts **`/train/session?day={templateDayId}`** (`ActiveWorkoutPage` threads `useSearchParams` → `useTrain({ workoutDay })`) — this is how a non-today direct-start (Heti weekly row / Gym day-card, `mezo-bxpg`) pins its template day; the open instance winning resolution means the hero's `Folytassuk` and a hard reload resume a cross-day session too. **A non-today gym day on Mai** (`mezo-9bbc`) is a plain read-only-capable `TodaySessionCard`, not the three-state hero: title/exercise-count come from the meso template (`activeMeso.days`, since `MesoDay` has no `title` — its human label is `type`) rather than `/today` (which only describes today), `logged` comes from `gymDoneDates`, and the CTA (`Kezdjük el`, omitted when `gymDayTarget` resolves to `null`, e.g. a rest template day) routes via the same `gymDayTarget` helper Heti uses. **On Heti**, a completed (`kész`) weekly gym row — today OR a past day this week — is **tappable → opens its review**: `WeeklyDayRow`'s gym branch routes its click to `onReviewGym` when `gymLogged`, else `onStartGym` when today, else `onOpenGymDay`; `TrainWeekPage` resolves the per-date instance id from `useWeekWorkouts()` (this Mon–Sun week's completed summaries mapped date→id, `workoutIdByDate`) and passes `onReviewGym` only for dates present in that map. Today's not-yet-completed gym row also shows a `folyamatban` chip while an instance is open (`gymInProgress = a.isToday && todaySession.openWorkout`). ## 3. Architecture & data flow

The whole area flows through **two hooks**, both re-exported from the single data boundary `frontend/src/data/hooks.ts:202-203`:

```
View (features/train/**)
  → useTrain()      (data/train/trainHooks.ts)   |   useRunning()  (data/train/runningHooks.ts)
    → isMockMode()  (@/data/_client/mode → VITE_USE_MOCK !== 'false')
       ├─ MOCK: TanStack Query initialData = static fixtures (data/train/train.ts, data/train/running.ts)
       │        writes no-op (useTrain) OR emulate the server via queryClient.setQueryData (useRunning)
       └─ REAL: api client (data/train/trainApi.ts, data/train/runningApi.ts) over apiFetch → /api/train/*
            → TrainController.java (implements generated TrainApi)
              → {Train,Workout,Sport,ExerciseCatalog,ExerciseRecord,Running}Service
                → repositories → Postgres
```

**Invariants of the seam:**
- **Mock mode is synchronous** (`initialData` set) so the first render equals the Phase-1 static return — preserved for the visual baselines and component tests. **Real mode has NO static fallback**: an empty backend surfaces as `null`/`[]` and every view ghost-guards (the "T0 clean slate" rule, `2026-06-11-train-write-clean-slate-design.md`). The full rationale is in the comment block at `frontend/src/data/train/trainHooks.ts:166-173`.
- **Mode is read inside hook bodies, never at module scope** (`frontend/src/data/_client/mode.ts`), so tests stub per-case with `vi.stubEnv`.

#### Set recommendation engine — hypertrophy drive + progressive overload (`mezo-dhdr` + `mezo-5pfe`)
`SetRecommendationService.prescribe(createdBy, ex, deloadWeek)` (`feature/train/service/SetRecommendationService.java`) computes the per-set targets that `getToday` attaches as `prescribedSets`, and — since Progressive Overload Plan 1 (`mezo-5pfe`) — the structured `progression: ProgressionSignal` per exercise. It resolves the exercise's **top working set** of the most recent completed session where the exercise's **identity** was trained (catalog id, else exact name — the shared `ExerciseHistoryResolver`, `mezo-eq4w`; formerly template-day + row-scoped, which a day edit's row swap silently reset), then **delegates the lever/weight/rep decision to a new pure `ProgressionDecider`** (`service/ProgressionDecider.java` — no Spring, no DB; unit-tested directly via `ProgressionDeciderTest`). The **RIR-aware, deload-aware double-progression matrix** (SUPERSEDES the earlier reps-only rule of "reps < rep_min → drop the increment; reps in range → hold"): `slack = loggedRIR − targetRIR` (a **null logged RIR is treated as on-target**, `slack = 0`, neutral — an un-rated set never triggers a false grind-hold or a false pass).
  - **Deload week** (see below) → **regress** regardless of reps/RIR: ~0.9× the last working weight (plate-snapped), reps reset to `rep_min`.
  - `reps ≥ rep_max` → **+weight**: bump by the type increment (plate-snapped), reps reset to `rep_min`.
  - `rep_min ≤ reps < rep_max` → **+rep** (build toward `rep_max`) — **unless** the last set was a **grind** (`slack < 0`, i.e. the logged RIR came in under the target), in which case the engine **holds/consolidates** the same weight instead of adding a rep.
  - `reps < rep_min` → **−weight** (drop by the increment, plate-snapped) when the athlete was **at or over target effort** (`slack ≤ 0`); otherwise **hold** — the load was too heavy but the effort wasn't there either, so the engine waits rather than moving the wrong way.

  On the **first session** (no working-set history) it still seeds from `anchor_weight_kg` (or leaves the target **null** with no anchor) exactly as before, and `progression` is **null** — there is nothing to compare against yet. **Weightless/bodyweight history** (a logged set with no weight) still progresses on reps only (`progression.lever = 'rep'`, unchanged behavior). **Plyometric / bodyweight exercises are weightless** — the engine returns null target weights (reps/RIR only), which the FE renders as a reps-only stepper. Warmup sets are generated by ramping the working target down through the configured `warmupRamp` — and are **emitted even when the base weight is unknown** (first session, no anchor; `mezo-eerq`): their target weight is simply null, keeping the prescribed list aligned with the recipe's set count so the FE never loses the `B{n}` labels / RIR suppression on a first session. The method returns a `Prescription(sets, rationale, progression)` record (`service/Prescription.java`, now 3 fields) — the set list, the human-readable `rationale` shown in the active workout, and the structured signal the FE renders as `ProgressionBanner`/the prep chips (§2). `WorkoutService.getToday` tallies each exercise's `progression.lever` into the day-level `overloadSummary` (`weightUp`/`repUp`/`hold`, `deload` folded into `hold`). It reads **completed-instance history only**, so a live (open) session never feeds back into its own prescription → the recommendation is **stable across a mid-workout resume** (§9).
- **Deload-week detection** (`WorkoutService.getToday`, `mezo-5pfe`; index fixed by `mezo-hi9m` DA1): `deloadWeek` is derived from `activeMeso.getPhaseCurve().get(activeMeso.getCurrentWeek() - 1)` equalling `"Deload"` (case-insensitive) — **`currentWeek` is 1-based, `phaseCurve` is 0-indexed**, so the lookup is `currentWeek - 1` (`WorkoutService.java:172-177`; a pre-existing off-by-one against a 0-based index was corrected here). **Bound-checked and null-safe** — no active meso, no phase curve, or `currentWeek - 1` outside `[0, phaseCurve.size())` all resolve to **not deload** rather than throwing, so a meso whose `currentWeek` has drifted past its own curve length degrades gracefully instead of 500ing. `VolumeProgressionService.isDeloadPhase` applies the same corrected 1-based lookup independently (see below).
- **Config** (`mezo.hypertrophy.*` → `HypertrophyProperties`, `feature/train/config/HypertrophyProperties.java`): `plateStep` (2.5 — rounding granularity for computed kg, also used by the deload 0.9× snap), `defaultIncrement` (2.5 — fallback), a per-type `increment` map (compound 5.0 / isolation 2.5), and the `warmupRamp` (`List<Ramp(pct, repsFactor)>`). `@Validated` record, wired in `application.yml` under `mezo.hypertrophy:` — never `@Value`. No new config was added for Plan 1 — the RIR/deload logic reuses these existing tunables.
- **Switch:** the whole engine is gated by `mezo.feature.hypertrophy-drive.enabled` via the `HypertrophyDriveGate` `@ConditionalOnProperty` marker bean (`feature/train/HypertrophyDriveGate.java`; key constant `FeaturesConfiguration.HYPERTROPHY_DRIVE_SWITCH`). Off → `WorkoutService` skips the engine and returns null `prescribedSets`/`rationale`/`progression`, and `overloadSummary` is null, so the FE logs ad-hoc with no progression UI at all.
- **Downstream consumer (Progressive Overload Plan 3, `mezo-gj42`):** the deterministic
  `OverloadChallengeGenerator` (proactive-owned) reads this same per-exercise `progression` off
  `getToday` to pick the day's biggest jump for a proactive `overload` challenge — no new engine logic
  here; see [proactive.md §HBWI](proactive.md).

#### Volume progression — weekly per-muscle set ramp (Progressive Overload Plan 2, `mezo-hi9m`)
`VolumeProgressionService.rolloverIfDue(createdBy, activeMeso)` (`feature/train/service/VolumeProgressionService.java`) is called as one of the first steps of `WorkoutService.getToday` (right after the active meso is resolved, before the deload check and the effective-set distribution below — `WorkoutService.java:119-121`), gated by an `ObjectProvider<VolumeProgressionGate>` (present only when `mezo.feature.volume-progression.enabled=true`, **default on**, mirroring `HypertrophyDriveGate`/`ClosingBlockGate`). It performs the **weekly rollover**: a real write path for what used to be seed-only `currentSets`/`volumeRecompute`.
- **Idempotent per calendar week:** `MesoWeeks.clampWeek(startDate, weeks)` (a shared, package-visible `startDate`-anchored 1-based week helper, also used by the arc endpoint below) computes the week containing today; if it hasn't advanced past `meso.volumeRecompute.lastRun` ("W{n}"), the call is a no-op — safe to invoke on every `getToday`.
- **Otherwise, per `MuscleGroupVolumeLogEntity` row** (one per muscle group on the meso): it reads the **previous** calendar week's COMPLETED instances, collapses each logged exercise's 21-token zone to its coarse **`MuscleGroup`** (`service/MuscleGroup.java` — pure, `chest`/`back`/`shoulder`/`biceps`/`triceps` are dash-prefix-collapsed from the finer zones; `quad`/`ham`/`glute`/`calf`/`core` and legacy coarse tokens pass through unchanged), and derives per-group `loggedLastWeek` (working-set count) + `grind` (any exercise whose most-recent logged working set landed ≥ `grindRirGap` RIR below its `targetRir` — the recovery-proxy signal, since the engine has no direct cross-load input yet). It then runs **`VolumeDecider.decide`** (`service/VolumeDecider.java` — pure, Spring-free, unit-tested via a dedicated test): week 1 → `MEV`; deload week or already-at-`MRV`-and-grinding → `round(prevSets × deloadFraction)` floored at `⌈mev/2⌉`; productive (logged ≥ target, not grinding, below `MRV`) → `+step`; else → **HOLD**. The result is persisted onto `currentSets` + appended as a `ProvenanceEnvelope.Adjustment` (`kind: "pattern"`) on the row's existing `source` — the baseline MEV/MAV/MRV is untouched, only a new adjustment is appended.
- The mesocycle's `currentWeek` advances to the new calendar week and `volumeRecompute` gets a fresh `{lastRun: "W{n}", nextRun: "W{n+1}", trigger: "weekly-rollover", changes: [...]}` — `changes` is a terse per-muscle `{muscle, change, reason, deload}` list (e.g. `"+2 sets"` / `"tartás"` / `"deload"`), NOT the richer free-text prose the mock/seed fixtures carry (be honest about that gap when describing this to a reader expecting mock-parity prose).
- A muscle group with no volume-log row on the meso is simply skipped, never fabricated.
- **Effective per-exercise working sets (same `getToday` call, DA6):** once the rollover has run (or on a week where it was already up to date), and only when the switch is on and the meso has volume-log rows, `WorkoutService.effectiveWorkingSets` distributes each muscle group's `currentSets` across **today's** same-group exercises — proportional to each exercise's template `workingSets`, remainder to the largest, never below 1 — and this **derived** count overrides `TodayExercise.workingSets` (the template row itself is untouched). This effective count is what's threaded into the hypertrophy-drive engine: `SetRecommendationService.prescribe(createdBy, ex, deloadWeek, effectiveWorkingSets)` — the 4-arg overload, the only caller being `getToday`. Switch off, or no volume-log rows on the meso → every exercise keeps its template `workingSets` unchanged (byte-identical to pre-Plan-2 behavior).
- **Config** (`mezo.volume.*` → `VolumeProperties`, `feature/train/config/VolumeProperties.java`, `@Validated` record): `step` (2 — sets added on a productive week), `deloadFraction` (0.5 — deload/at-MRV-grind target as a fraction of the previous week's sets), `grindRirGap` (2 — RIR-below-target gap counted as a grind).
- **Switch:** `mezo.feature.volume-progression.enabled` (`FeaturesConfiguration.VOLUME_PROGRESSION_SWITCH`, default **true**) via the `VolumeProgressionGate` marker bean (`feature/train/VolumeProgressionGate.java`).
- **Read-only companion — the volume-arc endpoint:** `GET /api/train/mesocycles/{id}/volume-arc` (`operationId getMesocycleVolumeArc`, `TrainController.getMesocycleVolumeArc`) → `VolumeArcService.arc` (`feature/train/service/VolumeArcService.java`) returns `MesocycleVolumeArcResponse { mesocycleId, title, currentWeek, weeks, startDate, endDate, status, phaseCurve[], muscles: MuscleVolumeArc[] }`; each `MuscleVolumeArc { muscle, region, mrv, weeks: VolumeArcWeek[] }` (`region` = a FE color-family key — coral/sky/lav/rose/sage/amber — resolved from a fixed `MuscleGroup → region` table); each `VolumeArcWeek { week, phase, planned, actual, isCurrent }` where `planned` is a scaffold projection (week 1 = MEV, deload weeks = `round(mrv × deloadFraction)`, else ramps by `step` up to a ceiling of `MRV` — independent of what `VolumeDecider` actually decided that week) and `actual` is the aggregated logged **working**-set count per `MuscleGroup` per `startDate`-anchored meso-week (a new `ExerciseSetRepository.aggregateWorkingSetsByMuscleAndDate` query, bucketed via `MesoWeeks.weekOf`) — **`null` for any week beyond `currentWeek`** (nothing logged yet). This endpoint is **read-only, ownership-filtered via `OwnershipGuard`, and deliberately NOT gated** by the volume-progression switch (a harmless read that never mutates state) — it renders even if the rollover itself is switched off. FE consumption: §2 `Mezociklus áttekintő`.

#### Closing block — fix zárás (`mezo-z2ul`)
`ClosingBlockService` (`feature/train/service/ClosingBlockService.java`) **lazily ensures the configured closing exercises at the END of every non-empty template day of the active meso** — by default **Dead Hang** (2 × 45–60 mp; weightless `plyo` type → reps-are-seconds, kg-stepper hidden on the FE) and **45° Back Extension** (2 × 12–15). Triggered from `WorkoutService.getToday` behind the `ClosingBlockGate` `@ConditionalOnProperty` marker bean (`mezo.feature.closing-block.enabled`; key constant `FeaturesConfiguration.CLOSING_BLOCK_SWITCH`; mirrors `HypertrophyDriveGate`). **Idempotent** by catalog id OR case-insensitive name (a manually added copy counts, nothing duplicates); **empty (rest) template days are skipped** so the block never turns a rest day into a workout; a day-edit that strips the rows self-heals on the next `getToday`. Config: `mezo.closing-block.exercises` — `ClosingBlockProperties` (`feature/train/config/`), a `@Validated` record list of `{slug, workingSets, repMin, repMax, targetRir}` where `slug` references a **master catalog row** (a missing slug logs a warning and is skipped, never a 500). The appended rows are **ordinary catalog-linked template exercises** (`warmupSets 0`, server-side `createdBy`), so logging, records, history and prescriptions work unchanged — **no API contract change, no DDL** (the new `dead-hang` master entry ships via `content/exercise-catalog.json`; `back-extension-45` already existed). ITs: `ClosingBlockIT` (append/idempotency/multi-day/rest-day/manual-duplicate) + `ClosingBlockSwitchOffIT`.

#### Lazy auto-close of stale instances (`mezo-cd8s`)
`WorkoutAutoCloseService` (`feature/train/service/WorkoutAutoCloseService.java`) **settles abandoned workout instances** so a session left open on a past day never lingers as `active`. Invoked as the **first statement** of `WorkoutService.getToday` (before the closing-block ensure and the meso lookup, so stale instances settle even when there is no active meso). A SEPARATE `@Transactional` bean because `getToday` is a plain read and a same-class `@Transactional` self-invocation would bypass the proxy (mirrors `ClosingBlockService`). For each of the owner's `active` instances dated **strictly before today** (`WorkoutSessionRepository.findByCreatedByAndStatusAndDateBeforeAndTemplateSessionIdIsNotNull`): it becomes **`completed`** when it carries **≥1 non-skipped logged set** (the work counts — feeds `findDoneInstanceDates`, `lastWeekRefs` and the prescription engine), else **`skipped`** (a started-but-empty session never counts as done). **Idempotent** (a settled instance is no longer `active`, so a re-run is a no-op) and **always on** — no feature gate, **no DDL/contract change**. After it runs, only a **today-dated** instance can still be `active`, so the open-instance resume lookup below can never resurrect last week's abandoned session. IT: `WorkoutAutoCloseIT` (past-active-with-set → completed / past-empty → skipped / today-active → untouched).

#### Done-state = completed status + workout-detail review (`mezo-cd8s`)
The gym "done that day" signal changed from **≥1 non-skipped logged set** to **`status = 'completed'`** (an explicitly finished — or lazily auto-closed — instance): `WorkoutSessionRepository.findDoneInstanceDates` (→ `weekDoneDates`) and `findDoneInstancesBetween` (→ Insights `listWorkouts` + the companion `get_recent_workouts` tool, §5) both switched their predicate to `s.status = 'completed'`, so a started-but-unclosed instance with logged sets is **no longer** counted (the auto-close settles stale ones, above). `lastWeekRefs` and `SetRecommendationService` already read completed-only history — unchanged. The same shift flows to every consumer of `findDoneInstanceDates`/`findMesoDoneInstanceDates` (QuestEvaluator, `TrainingCommitmentCalculator`/discipline trait, Insights weekly counts, companion tools, habit, proactive) — the agreed semantic root of the four fixes; the origin-agnostic-vs-meso-only split between those two finders is a later addition (`mezo-ws2x`, below).
- **`completedWorkout` on `getToday`** — after the auto-close, `WorkoutService.getToday` resolves the most recent `completed` instance of today's template day **dated today** (`findFirstByCreatedByAndTemplateSessionIdAndStatusAndDateOrderByCreatedAtDesc`) onto `WorkoutTodayResponse.completedWorkout` (null when none). One extra read, no second endpoint — drives the Mai Kész/Megnézem hero, `GymPage`'s day-card tap resolution (§2, direct-start flow) and the `/train/session` → review redirect (§2).
- **`GET /api/train/workouts/{id}` → `WorkoutDetailResponse`** (`WorkoutService.getWorkoutDetail`, a pure read, no `@Transactional`): the done-day review data source (weekly rows + Mai "Megnézem"). It looks up the owned **instance** (`ownedInstanceOrThrow`, instance-only) → joins the template day's exercises (`ExerciseRepository.findByCreatedByAndWorkoutSessionIdInOrderByOrderIndexAsc` on the instance's `templateSessionId`) with this instance's logged sets grouped per exercise; a skip-marker set flips the exercise's `skipped` flag and is excluded from `sets` (non-skipped, `setIndex` order). A foreign/missing id **or a template row** (`templateSessionId == null`) → **404 `TRAIN_WORKOUT_NOT_FOUND`**. ITs: `WorkoutDoneSemanticsIT` (completed counts, active-with-sets does not), `WorkoutDetailContractIT` (happy / 404 foreign / 404 template / skipped flag).

#### Saját edzés — custom workout templates (`mezo-ws2x`)
A custom (meso-less) workout template is an ordinary `workout_session` TEMPLATE row (`template_session_id IS NULL`) with **`origin='custom'`**, `mesocycleId` null, empty `dayLabel` (not weekday-bound), and its title in `type` — so the whole instance machinery (start/log/finish/records/prescriptions/"last week") works on it unchanged.
- **`workout_session.origin`** (`202607231811_mezo-ws2x_workout_session_origin.sql`) — TEXT `NOT NULL DEFAULT 'meso'`, CHECK `meso|custom` (`WorkoutSessionEntity.origin`). `WorkoutService.startWorkout` copies the template's origin onto the new instance (`instance.setOrigin(template.getOrigin())`), so every instance carries its template's provenance.
- **CRUD lives in `TrainService`** (`TrainService.java` — **supersedes the design spec's dedicated `CustomWorkoutService` naming**; a deliberate deviation, helper reuse — `toExerciseEntity`/`toDay`/`videosByCatalog` already live there). `GET /api/train/custom-workouts` (`listCustomWorkouts`, oldest-first), `POST /api/train/custom-workouts` (`createCustomWorkout` — new template, `origin='custom'`), `PUT /api/train/custom-workouts/{id}` (`updateCustomWorkout` — rename + full soft-delete+reinsert exercise replace, same pattern as `replaceDayExercises`), `DELETE /api/train/custom-workouts/{id}` (`deleteCustomWorkout` — soft delete only; completed instances + their sets survive, feeding records/history exactly like a soft-deleted meso day). All four are owner-scoped via `ownedCustomTemplateOrThrow` (missing/foreign/meso-origin/instance row → 404).
- **DTOs:** `CustomWorkoutResponse {id, name, exercises: GymExercise[]}`, `CustomWorkoutUpsertRequest {name, exercises: GymExerciseInput[]}` — the exercise shape is the same recipe DTO the meso day editor uses.
- **D5 guard exception:** `WorkoutService.startWorkout`'s "once per week" completion guard (`TRAIN_DAY_DONE_THIS_WEEK`) is **skipped for `origin='custom'` templates** — a custom day is repeatable any number of times per week. **D6 (one open workout at a time, `TRAIN_WORKOUT_OPEN_ELSEWHERE`) still applies**, unchanged and origin-agnostic.
- **`getToday` is meso-independent for custom days:** the open-instance and `?templateSessionId=` day-resolution branches (`WorkoutService.getToday`) now resolve **without** an active meso — only the weekday-label fallback (no open instance, no param) still requires one, and the closing-block ensure only runs when a meso exists. This is what lets a custom workout start and resume with zero meso in the account.
- **`completedWorkout` suppression:** `getToday` sets `completedWorkout` (→ the FE review-redirect gate) to **null for `origin='custom'` days**, however many times the day was finished this week — a custom day never gates back into a forced review, staying freely repeatable.
- **`WorkoutSessionRepository` splits into two finders (final-review fix, `mezo-ws2x`)**: `findDoneInstanceDates` stays **origin-agnostic** (its original, pre-`ws2x` semantics — any completed instance, meso or custom) and a NEW `findMesoDoneInstanceDates` adds `AND s.origin = 'meso'`. Only **plan-adherence** signals — the weekly ✓ marks (`WorkoutService.doneDatesThisWeek` → `weekDoneDates`), `QuestEvaluator` (`gym_session_done`), and the discipline trait (`TrainingCommitmentCalculator`) — read the meso-only finder, so **custom completions never tick these three**. Everywhere else that reads "was a gym session done that day" as a **real-load** signal — `HabitEvaluator` (`training_done_today`), `ContextSnapshotAssembler` (the companion `[Edzés]` block), `MetricWindowEvaluator` (the proactive volume-trend window) — stays on the origin-agnostic finder, so a custom session counts there exactly like a meso one. (An interim over-reach briefly put the meso-only filter on all six call sites; the split above is the corrected, spec-adjudicated state.) **`findDoneInstancesBetween` stays origin-agnostic** (unchanged) — Insights `listWorkouts` and the companion `get_recent_workouts` tool count custom sessions like any other (§5).
- **`WorkoutSummaryResponse` carries a required `origin` (`meso|custom`) + `title`** (`TrainMapper.toWorkoutSummary` — `origin` via an `OriginEnum.fromValue(...)` expression mapping, the same idiom as `status`; `title` sourced straight from `type`), so the FE's weekly agenda and `useWeekWorkouts` can distinguish + label custom rows without a second fetch.
- ITs: `CustomWorkoutIT` (13 tests — CRUD, ownership, D5-skip, D6-kept, meso-independent start/getToday, origin propagation, the `findDoneInstanceDates`/`findMesoDoneInstanceDates` split).

## 6. How to use it (consume)

Import from the single boundary `@/data/hooks`; never reach into `trainHooks.ts`/`runningHooks.ts` directly.

```tsx
import { useTrain, useRunning } from '@/data/hooks'

function MyWidget() {
  const {
    mesocycles, activeMeso, workout, gymSchedule, gymSlots, sport,
    exerciseLibrary, exerciseRecords, workoutPending, todaySession,
    // imperative writes:
    createMesocycle, activateMesocycle, closeMesocycle, saveDayExercises,
    startWorkout, logSet, saveWorkoutFeedback, finishWorkout,
    logSportSession, saveSportSchedule, saveGymSchedule,
    createCatalogExercise, updateCatalogExercise, deleteCatalogExercise, setExerciseVideo,
  } = useTrain()

  const {
    runningBlocks, activeRunningBlock, runSessions, runningPending,
    saveRunningBlock, activateRunningBlock, closeRunningBlock,
    deleteRunningBlock, logRunSession,
  } = useRunning()

  // ALWAYS ghost-guard real mode (no static fallback) and check *Pending before redirecting:
  if (workoutPending) return null
  if (!activeMeso) return <GhostState />
  // ...
}
```

- Reads return `null`/`[]` in real mode when the backend is empty — render a ghost, never assume data.
- Writes are imperative callbacks that `mutate` + invalidate the relevant query key; most accept an optional `{ onSuccess }`. In mock mode `useTrain` writes **no-op** while `useRunning` writes **emulate the server** via `queryClient.setQueryData` (so the `Futás` flows are interactive without a backend).
- **Backend consumer:** inject the relevant `*Service`; all methods take `UUID createdBy` first (from `CurrentUserId`). Use generated `api.dto` types only.

## 7. How to extend it

Adding a Train endpoint/field/sub-tab is **contract-first + dual-mode + both-test-modes**. The obligations are non-negotiable.

**Add or change an endpoint/field:**
1. Edit `api/feature/train/train.yml` (path + schema) FIRST. Follow `docs/references/api_contract_conventions.md`.
2. Merge + regenerate: `cd api/generate && npm run generate:api`; then `cd frontend && pnpm generate:api`. Backend types regenerate during `./mvnw generate-sources`.
3. Backend: implement the method on `TrainController` (delegate to a `*Service`). Follow `docs/references/java_package_structure.md` (`feature/train/{controller,service,repository,entity,dto,mapper}`) and `spring_patterns.md` (constructor DI via `@RequiredArgsConstructor`, method-level `@Transactional` on writes only, derived→JPQL→native repositories, MapStruct).
4. New table → Liquibase changeset `{YYYYMMDDHHMM}_{bd-id}_{desc}.sql` per `docs/references/liquibase_conventions.md` (UUID PK `gen_random_uuid()`, explicit `pk_/fk_/uq_/ck_/idx_` names, soft-delete columns). Seed data in Java `@Profile("demodata"|"demofixtures")` — never SQL. Add the table to `ResetDatabase`'s TRUNCATE list and add/extend a `*Populator` (`docs/references/integration_test_framework.md`).
5. New configurable value → `application.yml` under the `mezo:` root (`docs/references/configuration_conventions.md`), never `@Value`.
6. Errors → `SystemRuntimeErrorException` + a `SystemMessage` code (`docs/references/error_handling.md`).
7. Frontend: add the client method to `data/train/trainApi.ts`/`data/train/runningApi.ts`, wire a query/mutation in `trainHooks.ts`/`runningHooks.ts` **with both branches** — mock (no-op for `useTrain`, or `setQueryData` for `useRunning`) and real. Keep the boundary cast idiom (`as Mesocycle` style) consistent and use `satisfies` on request bodies. Ghost-guard the new read in every view.

**Add a Train sub-tab:** add an entry to `TRAIN_TABS` (`frontend/src/features/train/pages/tabs.ts`), add the route + a `pages/<X>View.tsx`, and surface its data through `useTrain`/`useRunning` (or a new hook re-exported from `data/hooks.ts`).

**Swap a mock-only feature to real** (e.g. a future cross-load engine): produce the data server-side, replace the static fixture branch in the hook with the API client call, and drop the `crossLoad: null` ghost — keeping the mock branch byte-identical to Phase 1.

## 9. Decisions, gotchas & deferred

**Key decisions** (see linked specs): mock parity vs clean-slate real mode (`2026-06-11-train-write-clean-slate-design.md`); running as a mesocycle-mirroring slice with typed-jsonb plan structure (`2026-06-14-train-running-slice-design.md`); on-the-fly records aggregation (no materialized table) over soft-deleted rows (`2026-06-12-exercise-records-design.md`); catalog as master content loaded in every profile (`2026-06-12-exercise-catalog-design.md`).

**Gotchas:**
- **Mock parity contract is the single most important rule:** mock returns byte-identical Phase-1 statics (synchronous `initialData`); real has no fallback → views MUST ghost-guard.
- **`useTrain` mocks no-op; `useRunning` mocks emulate** (`setQueryData`). Asymmetric on purpose.
- **Real-mode run-block create inserts synchronously into the cache** (`runningHooks.ts:52-63`, **mezo-11m**): on a `create` success the new block is written into `['running','blocks']` directly (no async invalidate that would race the read-after-write), so navigating straight to the builder no longer crashes on an `undefined` structure. Updates + mock mode still invalidate. The builder also guards `!draft.structure` with a `Betöltés…` placeholder (`RunningBlockBuilderPage.tsx:97-99`).
- **Run-builder edits auto-save (no Save button):** a 600 ms debounce (`RunningBlockBuilderPage.tsx:65-69`) plus a flush-on-back (`backToList`, `:71-74`); `dirty` is a `JSON.stringify` diff of the draft vs the loaded block (`:57-60`). The re-seed effect keys on `block?.id` only so a refetch never clobbers in-progress edits.
- **Template vs instance** both live in `workout_session`: template = `template_session_id IS NULL`; instance carries date/status/back-link. `listMesocycles`/`getToday` filter to templates; `logSet`/`finish` operate on instances.
- **Single-active invariant** for both mesocycles and running blocks (enforced server-side on activate AND on meso create-as-active).
- **Records resolve over soft-deleted exercises** via native query — day-edits soft-delete template rows but must not erase history.
- **Warmup sets (`kind='warmup'`) are excluded from every "real work" reader** (hypertrophy drive, `mezo-dhdr`): `ExerciseRecordService` (e1RM / best-set / session-volume), `WorkoutService.lastWeekRefs`, and the `GymSignalCalculator` progression XP all count **working sets only**, so a warmup ramp never inflates a PR, a "Múlt hét" reference, or earned XP. Correspondingly the recommendation engine reads **completed-instance history only** — the open live session is invisible to its own prescription, which is what makes the prescription **stable across a mid-workout hard-reload resume** (§4 engine subsection).
- **`ProgressionDecider` is a pure, Spring-free static method** (`decide(RefSet ref, repMin, repMax, targetRir, inc, plateStep, deloadWeek)`, `feature/train/service/ProgressionDecider.java`, `mezo-5pfe`) — no DB, no Spring wiring, unit-tested directly (`ProgressionDeciderTest`) rather than through an integration test; `SetRecommendationService` is the only caller, and the decider's precondition (`ref.weightKg() != null`) is enforced by the caller — the weightless/first-session/anchor-only branches never reach it. **A grind beats reps-in-range in the lever priority**: an athlete who hit `rep_min..rep_max` reps but logged a harder-than-target RIR (`slack = loggedRIR − targetRIR < 0`) gets **HOLD**, not the naive reps-only rule's **+rep** — RIR silently overrides the rep count in exactly this one branch. **A null logged RIR is neutral (`slack = 0`), never a grind** — an un-rated set can still earn a `+rep` or `+weight` lever exactly as if it had hit the target RIR.
- **Ownership errors:** foreign/missing → **404** (indistinguishable); `logSet` on a completed instance → **409**.
- **`phase_curve text[]` is `List<String>`** (not `String[]`) for Hibernate dirty-checking.
- Day-edit save (`MesoExercises.tsx`) fires `saveDayExercises` only when the day carries a real row `id`; mock fixtures have no id → local-only. **Exercise reorder is real** (the `SortableList` primitive, drag + ▲▼): the builder remaps the day's exercises and persists via the same `saveDayExercises` full-list PUT (array order = the contract); the planner (`MesocyclePlannerPage` steps `Gyakorlatok`/`Set & rep`) reorders its local draft `program` only (saved wholesale at the end).
- **Planner draft lives at page level behind a regeneration guard (`mezo-n46i`).** `program` state, program *generation*, and every draft mutation (`addExercise`/`removeExercise`/`reorderExercises`/`renameDay` + the new recipe patcher `updateExercise`) sit in `MesocyclePlannerPage`, not in `Step3Program`. Generation runs inside a `useEffect` gated by an input **signature** (`generatedFor` ref keyed on `goal|split|days|selectedDays`): it only (re)generates when that signature actually changes, so **program edits survive a step round-trip** (e.g. `Gyakorlatok`↔`Split + napok` or the `Gyakorlatok`↔`Set & rep` back-and-forth) while a real input change still regenerates. `Step3Program` (the `Gyakorlatok` review) is presentational over `{goal,name,weeks,days,program,onAdd,onRemove,onReorder,onRename}`; it keeps only `expandedDay`/`pickerDay` local and auto-expands the first training day **exactly once per generation** via a `hadProgram` ref (an edit's array-identity change never re-opens a collapsed day — the `mezo-xnq` guard). The `Set & rep` step (`Step4Recipe`) consumes the same page-level draft mutations — `updateExercise` as `MesoDayTabsEditor`'s `onChange` recipe patcher, plus add/remove/reorder — over the day-tabbed editor. Added-exercise ids use `crypto.randomUUID()` (never `Date.now()`).
- **Gym time is a *standalone* schedule, not a meso-day field** (Option Y, `2026-06-15-gym-schedule-times-design.md`): `GymScheduleSlot` persists across mesocycles; the meso decides *whether* you train that weekday, the slot decides *when*. `deriveGymSchedule` joins them by weekday — a slot with no meso gym day shows nothing; a meso gym day with no slot renders with `time: null` (graceful). PUT is **replace-all** (delete-then-insert the whole week).
- **`Mai` orders by time-of-day, not modality** — `daySessions` (`features/train/logic/agenda.ts`) is the single ordering helper shared by `WeeklyDayRow` and `TrainTodayPage` heroes; untimed (null/`''`) sort last (`'99:99'` sentinel), ties stable by modality. `TrainTodayPage` builds today's hero from a `daySessions` pass, with run-only-today handled via a **synthetic** agenda day (no gym/sport but a running session) so the run still gets a hero; a fully empty today shows "Ma pihenőnap".
- **`GymPage`'s "Időpontok" entry is always visible** (since `mezo-4t43`): in mock mode `saveGymSchedule` no-ops, so a local optimistic `gymOverride` keeps the edit visible in-session (not persisted across reload); real mode persists via `PUT` + `['train','gymSchedule']` invalidation. Mock mode renders gym times from the static `gymScheduleMock` slots (`data/train/train.ts`). The **mesocycle planner Step 2** is the primary editor of the same standing schedule.
- **`Mai` done-state matching is asymmetric** (`TrainTodayPage.tsx`) — there is **no schedule↔log link** for sport, so "logged" is matched by **the shown day's date AND sport, per slot** (`mezo-05v6` generalized this from a volleyball-hardcoded match; `mezo-9bbc` then generalized "today's date" to "the shown day's date" so the same match works on any past day): `loggedSportOn(iso, k) = sport.sessions.find(s => s.sport === k && s.date === huMonthDayDow(iso))` for the hero (called with `shownIso`, today's date when today is shown), `sportDoneOn(date, k)` for the weekly rows (the mapped `SportSession.date` is the HU display string, so we compare against the target date formatted the same way) — a mixed day (e.g. a TRX slot + a volleyball slot) flips each slot independently since each carries its own `k`. Running **does** carry the prescribed tuple back, so it matches on `blockId + weekNumber + sessionKey` (`runLoggedFor(key)`), ignoring date. **Gym** has no client-readable per-day completion, so the backend computes it: `GET /api/train/workouts/today` returns `weekDoneDates` — the ISO dates this Mon–Sun week whose gym instance is **`status = 'completed'`** (`WorkoutService.doneDatesThisWeek` → `WorkoutSessionRepository.findDoneInstanceDates`; **completed-only since `mezo-cd8s`**, not the old ≥1-logged-set — a started-but-unclosed session is settled by the lazy auto-close, §4). `TrainTodayPage` derives `loggedGym = weekDoneDates.includes(today)` for the hero, and per-row `gymLogged`/`isSportLogged(slot)` (matched against each weekly row's computed calendar `date`, the latter also against the slot's sport) so **past** completed days are marked, not just today. **The done-state stores nothing new — it is a pure read-derivation over already-persisted sessions/sets.** In real mode the log itself is persisted to Postgres (`POST /api/train/sport-sessions` → `SportService.create` → `sport_session` table, §4); the flip then happens after `logSportMutation`/`logRunSession` **invalidate→refetch** the session query from the backend (the DB is the source of truth — the same data the Sport `Napló` reads). The `setQueryData` cache-append is **mock-only** (the `mock ? … : …` arm in `trainHooks.ts`): it exists so the UI flips without a backend in tests/prototype, was a silent no-op before, and **never** substitutes for the DB in real mode — mock `sport.week` stats are also not recomputed on append (real mode re-derives them). A timezone edge exists: the backend stamps the log date server-side, so the flip relies on the server "today" matching the browser's local date.
- **Retroactive logging (`mezo-9bbc`, Task 9) is client-date-only.** A past-day "Pótold" log changes exactly one thing over a normal today-log: the sheet sends the selected day's ISO `date` in the request body instead of omitting it (`SportLogSheet`)/instead of today's `localDateString()` (`RunLogSheet`) — see the date-wiring paragraph above. Nothing else about the write path is date-aware: ownership (`created_by`) is still stamped server-side from the security principal exactly as on any other write, and XP/level-up resolution runs through the same `onSuccess: r => showLevelUp(r?.levelUp)` handler regardless of which day the log is dated to. There is no backend distinction between "logged live" and "logged retroactively" — the DB just stores whatever `date` the client sent.
- **Napiv S4 tab rename + pill sub-nav (`mezo-8141`).** The `GYM` tab is now labelled **`Gym`** (`TRAIN_TABS`, `pages/tabs.ts`) — copy-only, no route/id change. `TrainSubNav` switched from the generic `.subnav-item`/`.active` (`--brand-glow` underline) idiom to the coral `.np-pills`/`.np-pill` pill nav (`.on` active state, tinted via the `--pill-accent` custom property, defaulting to `var(--coral)`); Train was the first domain off the old idiom, Fuel (`--sage`) and Me (`--lav`) adopted the same pill markup in S6/S7. **Both `TrainSubNav` and `.np-pills` are since retired (compact-header redesign, `mezo-ugqb`, 2026-07-18)** — Train's sub-nav is now a `SubNavDropdown` popover fed by the unchanged `TRAIN_TABS` array, mounted via `AppHero`'s `utilities` prop (see §2 above).
- **`weeklyLoad` (`logic/weeklyLoad.ts`) headlines the Futás load tile with the week's dominant running style by intensity** — `sprint` > `pyramid` (`piramis`) > `steady` (`tempó`). Each `RunPrescribedSession.kind` (`sprint|pyramid|steady` per `train.yml`) maps to its own short lowercase Hungarian label; a `steady`-only week now reads `tempó` rather than collapsing into `piramis` (fixed in S8, `mezo-mifi`; the raw `.value` string is rendered verbatim by `LoadTiles`).
