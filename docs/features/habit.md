# Habit — Morning & Evening Routine Engine

> Two fixed habit-stacking chains — a **morning** and an **evening** routine — surfaced on Today (`/today`) as rows on their own **daypart face** (Reggel / Este) and as a **„Rutin"** tab on the `/me/growth` page. **Status: ✅ done** (backend + FE real + FE mock). Driving spec: [`2026-07-19-morning-evening-routine-habit-engine-design.md`](../superpowers/specs/2026-07-19-morning-evening-routine-habit-engine-design.md); driving ADR [0010](../decisions/0010-gamified-growth-xp-feedback-not-payment.md) (XP is feedback, not payment). bd `mezo-d1jb`.

## 1. Summary

**Habit** is a lean habit engine built on habit-stacking psychology: two **fixed identity chains** — 9 MORNING + 6 EVENING catalog habits (incl. the two **intention** habits added by `mezo-a686` — `daily_intention` MORNING / `intention_reflect` EVENING, see [intention.md](intention.md); the two habits added right after morning sunlight — `morning_pushups` „50 fekvőtámasz" / `morning_video` „Reggeli videó" with a clickable external `linkUrl`; and `evening_ritual` „Napzárás", DERIVED off the sleep-anchored closing ritual — see the [ritual design spec](../superpowers/specs/2026-07-24-daily-closing-ritual-design.md)) — each item anchored to an existing routine ("fogmosás után", "vacsora után"). Most completion is **DERIVED** over data the user already logs (sleep, weight, supplement intakes, training, meals) — a habit is **never self-claimed where a real signal exists** — with four MANUAL exceptions (morning sunlight, 50 push-ups, the morning video, evening wind-down). Each habit maps to a **LIFE skill** and earns a small deterministic XP (5–15) through a new idempotent **`HABIT` progression source** — the quest/activity twin. Consistency is a gentle trailing-28-day **habit strength** ratio (a lapse fades, never zeroes) plus a quiet **perfect-day** celebration — **no hard streak, no break-punishment** (the [ADR 0010](../decisions/0010-gamified-growth-xp-feedback-not-payment.md) tone: `missed` renders dim and silent, no red).

It is deliberately the **quest pattern's mirror, not a quest extension** (spec [D2](../superpowers/specs/2026-07-19-morning-evening-routine-habit-engine-design.md)): quests are rotating *offers* (reroll, adaptive difficulty, expiry), habits are *fixed chains* — same machinery (catalog JSON + per-day table + evaluator over pure reads + lazy read-time evaluation), different psychology. The data model is general (chain/position/anchor/mode/metric) so a later custom-habit expansion needs no redesign; v1 ships exactly the two fixed chains.

Status per layer: **backend** ✅ (`feature/habit` — catalog, `habit_day` table, evaluator, service + nightly close job, controller, `HABIT` progression source), **FE real** ✅ (Today's face rows + the Rutin tab over the real endpoints), **FE mock** ✅ (deterministic seed day + summary; mock check also moves the account XP total). Design decisions are spec §2 **D1–D9**; the catalog table is spec §3; the three evaluation-closure classes are **D7**.

## 2. User-facing behavior

**Today — rows on their own daypart face** (`mezo-j7u4`, [ADR 0014](../decisions/0014-today-daypart-faces.md)). **`RoutineCard` is deleted.** The chains are no longer a card of their own: each habit is a shared **`ItemRow`** inside its face's merged `TodoCard` — the MORNING chain under „REGGELI RUTIN" on the 🌅 **Reggel** face, the EVENING chain under „ESTI RUTIN" on the 🌙 **Este** face. **Since `mezo-n5e9.2` this bucketing is catalog-driven, not a hardcoded map:** `logic/todayItems.ts` reads each habit's owning chain (`chain.daypart`/`chain.title`) out of the live `useHabitCatalog()` catalog (a `chainKey → HabitChainInfo` lookup built once per render) instead of the retired `CHAIN_FACE`/`CHAIN_GROUP` maps, so a **custom chain created through the routine editor** (§2's "Rutin szerkesztő" below) buckets onto the right face automatically — including a **DAY**-daypart chain, which lands on the ☀️ **Nap** face (a slot the old two-map design had no room for). A habit whose chain is missing from the catalog (a stale row, or the real-mode catalog not yet resolved) is simply skipped — the same "unknown chain" semantics the retired hardcoded guard gave. What survived, what changed:

- **Each row** shows the HU title with the `anchorCopy` cue as its subtitle, a MANUAL **`Pipa`** or a DERIVED **`Logolás`** pill (never self-completing — ADR 0010; the CTA map is still `features/today/logic/habitAction.ts`), and the row's `xp` — which now **absorbs a deduplicated quest's XP** where the two describe the same act (`todayItems.ts`'s `DEDUP_PAIRS`: `morning_weigh_in`↔`weight_logged`, `morning_workout`↔`gym_session_done`, `wake_on_time`↔`sleep_target`, `protein_breakfast`↔`protein_target` — the habit row wins and the quest stops rendering as a second row). The `+N XP` chip per row and the per-row status mark are gone as separate elements; `ItemRow`'s `done` state carries completion (`✓` shield, flattened row).
- **The MORNING chain also has a hero.** Its **first open step** is promoted into `FaceHeroCard`'s `.fhc-next` row (progress bar + `{done} / {total}`) with that step's own action; **steps 2..n stay ordinary actionable rows** in the `TodoCard`, so a skipped middle step can still be ticked in any order. The evening chain has **no** hero — every step is already an actionable row, so nothing needed promoting.
- **A row with a `linkUrl`** (e.g. `morning_video`) renders a small trailing **`↗`** link **beside** its `Pipa`, never instead of it — `ItemRow` never nests the `<a>` inside the row's own `<button>` (it splits into an inner `.itemrow-hit` + the link as a sibling). Promoted into the hero, the same link renders as `.fhc-next-link`.
- **`bed_on_time` stays deliberately passive** (`mezo-o5hx`): tomorrow's sleep log decides it (E4), so `habitAction` returns `'none'` — and Today's `servableAction()` predicate therefore **strips its action entirely** and substitutes `habitHint`'s explainer („holnap reggel, az alvásnaplódból derül ki") as the row's subtitle, so the button-less row reads as „this ticks by itself" rather than as broken. That is the same guarantee the old `.hab-note` line gave, now enforced one layer up for **every** source (see [today.md §9](today.md)).
- **`evening_ritual` is filtered out of the evening rows entirely** — the Este face's `RitualCard` hero already owns the Napzárás act with a stronger, window-aware affordance, so showing the row too would be exactly the duplication the re-composition removed (`FaceEvening.tsx`'s `OWNED_BY_RITUAL_HERO`). Its `habitAction` `nav` mapping is unchanged and still routes to `/ritual`; it simply has no row on Today. The row is still rendered by Growth's Rutin tab.
- **The `wind_down` habit keeps its SECOND surface** — `WindDownBanner` on the Este face still carries its own `Pipa` over the same `['habitDay', date]` cache (§5), and it renders **above** the ritual hero inside the dim/winddown window.
- **In-flight writes withdraw controls rather than dimming them.** While `useHabitActions().pending` is true, every habit row's pill and the chain hero's CTA fall back to inert copy, so a double-tap cannot fire a second mutation — and quest/fuel/check-in rows on the same card **stay tappable** (the guard is scoped to `action.kind === 'habit'`).
- **The midday collapsed-summary toggle is gone** (`.rt-*`, `mezo-km27`). It existed so a missed morning habit could be logged retroactively at midday; that is now the general rule — **act-anywhere**: selecting the Reggel pill at 22:00 gives every morning row its live `Pipa`. Nothing was lost, the affordance became structural.
- **Chain completion fires one quiet celebration toast per chain** — via `toastBus`, from `features/today/logic/useChainCelebration.ts` (a `wasComplete` ref guards re-fires, so an already-complete chain chimes once on mount). **Since `mezo-n5e9.4`** this is no longer two hardcoded calls: `TodayPage` computes progress for **every active chain** of a face's daypart (`chainProgress(chainKey)`, sourced from `useHabitCatalog().chains` — no more literal `'MORNING'`/`'EVENING'` filtering) and each face mounts `features/today/components/ChainCelebrations.tsx`, which fans that list out into one `useChainCelebration` call per chain (a variable-length list can't drive a variable number of hook calls directly, so each chain gets its own always-unconditional child instance, keyed by chain id). **Copy stays the exact fixed strings for the two seed chains** (`🌅 Tökéletes reggel` / `🌙 Tökéletes este`, byte-parity required) — any other chain (a custom one from the editor, on any daypart including DAY) celebrates as **`✨ {title} kész`**. The morning face's hero (`FaceHeroCard`'s `.fhc-next`) is likewise promoted from the **first ACTIVE MORNING-daypart chain by position**, not a hardcoded `'MORNING'` chainKey — a second morning chain (or none at all, mid-catalog-load) no longer breaks it; a second/other chain of any daypart still gets its own celebration even though it isn't the hero.
- **Level-ups** produced by the read (or a manual check) ride the shared `LevelUpProvider` overlay via `useLevelUp().showLevelUp`, with the **HABIT** source meta (`A rutin épít.` / chip ☀️) in `features/progression/logic/levelUpMeta.ts`. The consume-once effect moved from `RoutineCard` into `TodayPage`.
- **Honest ghost:** with no habits (switch off in real mode, or real mode before the day resolves) the chain simply contributes no rows — `TodoCard` itself ghosts (`null`) on an empty face, and `FaceHeroCard`'s progress reads `0 / 0`. No skeleton, no seed leak.

**Growth — „Rutin" tab** (`features/me/components/RoutinesTab.tsx`): the **2nd** segment of the `/me/growth` segmented control — order **Skillek · Rutin · Napló · Kitüntetések** (`GrowthPage.tsx:77-80`). It is the overview/statistics surface (daily interaction stays on Today) and is now **date-navigable + read-only** (no check/log affordance here — see the deferred note below): a top **`DayNavigator`** (`shared/ui/DayNavigator.tsx`) steps the viewed day with `‹ prev | tappable date | next ›`, the centre label opening a themed calendar popover (`DatePicker`); it defaults to **today**, reads „Ma" on today, and disables `next` at today (no future). **Since `mezo-n5e9.2` the chain cards themselves are catalog-driven**, not two hardcoded MORNING/EVENING calls: one card per **active** `useHabitCatalog()` chain, in editor position order, titled from `chain.title` (the seed titles read „Reggeli rutin"/„Esti rutin" — the old hardcoded „Reggeli lánc"/„Esti lánc" copy is gone) — so a third (or DAY-daypart) chain created via the editor gets its own card automatically; an inactive chain renders no card at all, even with habits still on it. The view branches on the selected day:
> - **Today** (unchanged): the two **perfect-day counters** (`Tökéletes reggelek · 30 nap` / `Tökéletes esték · 30 nap`) over one chain card per active chain, each habit rendered with its status mark, title, and a **28-day strength bar** (`{pct}%`, or `—` under the min-sample).
> - **Past day** (day-focused): a compact per-day **summary chip** (`Reggel {k}/{n} · Este {k}/{n}` + `+{XP} XP`) over the same chain cards rendered as **status-only rows** — no strength bars (strength is a rolling metric, not a per-day fact).
> - **Empty past day:** a quiet ghost — „Nincs rutinadat erre a napra".
>
> Pure FE (no backend/API change — it just re-keys `useHabitDay(date)` on the picked day). Reads `useHabitDay(date)` (per-day statuses) + `useHabitSummary()` (strengths + perfect days, aggregate — today branch only) + `useHabitCatalog()` (which cards render, §2 above). **Retroactive yesterday-logging from this tab is DEFERRED** (bd `mezo-x9c2`): the past view is read-only, daily check/log stays on Today. Note the two are not the same affordance — since the daypart faces, Today lets you tick **any of today's** habits from any face („act-anywhere"), but still only today's; this tab is where other days are *viewed*.
>
> **Editor entry — „Szerkesztés" (`mezo-n5e9.2`):** a trailing `cta-ghost` „✏️ Szerkesztés" button sits beside the `DayNavigator`, **today view only** (a past-day view stays read-only-clean, since it is looking at history, not the live catalog) — `useNavigate()` to `/me/routines/edit` (the routine editor, below).

### Rutin szerkesztő — the routine editor (`/me/routines/edit`, `mezo-n5e9.2`)

The full CRUD surface over the catalog the backend admin API (§4) exposed — a **full-screen sibling route** (the `me/goals/new` idiom: no Me sub-nav chrome), entered from the Rutin tab's „Szerkesztés" button above.

- **`RoutineEditorPage`** (`pages/RoutineEditorPage.tsx`): a back-link to `/me/growth` + `PageTitle` „Rutinok szerkesztése", then one **card per catalog chain** (position order, from `useHabitCatalog()`): a header row (daypart emoji + title + an active `Toggle` + an ✏️ button opening `ChainEditSheet` in edit mode), a **`SortableList`** (`@/shared/ui/SortableList` — drag or ▲▼ buttons, the `MesoEditor.tsx` idiom) of the chain's defs, and a „+ Új habit" row opening `HabitEditSheet` in create mode for that chain. A bottom „+ Új rutin" CTA opens `ChainEditSheet` in create mode. Reordering a `SortableList` calls `reorderChain(chain.id, newDefIds)` directly (no local staging state). **Inactive chains render dimmed** (`.card.is-inert`, opacity only — every control inside stays interactive, so a paused chain can still be tuned before re-activating it). While the real-mode catalog hasn't resolved yet (`isPending` + an empty catalog) the page shows a `GhostState` instead of an empty list.
- **Each def row** (`HabitDefRow`, page-local): title, an `{xp} XP` chip, a `MANUAL`/`DERIVED` mode chip, and its own active `Toggle` — as a sibling of the row's own button (never nested inside it, `ItemRow`'s no-button-in-button doctrine) — tapping the title opens `HabitEditSheet` in edit mode for that def.
- **`ChainEditSheet`** (`sheets/ChainEditSheet.tsx`, `{chain?, onClose}`): a title input + a three-way daypart `Chip` picker (🌅 Reggel / ☀️ Napközben / 🌙 Este). Create → `createChain({title, daypart})`; edit → `updateChain(id, {title, daypart})` (both fields ARE updatable post-creation — `HabitChainUpdateRequest` carries `title`/`daypart`/`position`/`isActive`, unlike the def side below). **Delete** is offered only for an **EDITABLE existing chain** — a non-seed (custom) chain with zero defs — mirroring the backend's own two 409 guards (`HABIT_CHAIN_SEED` checked before `HABIT_CHAIN_NOT_EMPTY`, §4); otherwise an inline explainer replaces the button („Az alap rutinok nem törölhetők." / „Csak üres rutin törölhető.") so nothing dead-ends into a 409 the user never saw coming.
- **`HabitEditSheet`** (`sheets/HabitEditSheet.tsx`, `{chainKey, def?, onClose}`): title, „miért" (textarea), horgony-szöveg, an XP `±` stepper (5–15, step 5 — the catalog's own XP granularity; **not** `@/shared/ui/Stepper`, whose actual shape is a multi-dot wizard progress indicator unrelated to a bounded numeric value — the SleepGoalSheet `±`-chip idiom is reused instead), and a link URL input, in both modes. **CREATE only** additionally offers: a skill picker (options from `useProgressionProfile().life`, falling back to the static `LIFE_SKILLS` list only while the profile hasn't resolved yet — never a stranded-empty picker), a mode toggle (Pipa/MANUAL default ↔ DERIVED), and — when DERIVED — a metric select from `logic/habitMetricPalette.ts`'s `HABIT_METRIC_PALETTE` (the eleven `HabitEvaluator.SUPPORTED_METRICS`, minus `"manual"`, with HU labels — kept in sync with the backend list by a doc-comment pact, not a shared source). **EDIT mode renders mode, metric, AND skill as read-only chips**, not just mode/metric: `HabitDefUpdateRequest` (§4) has **no** `skillKey` field either, so all three are contract-immutable once a def exists, not only the two the original design note called out — an editable skill picker in edit mode would silently drop a re-pick on save, which this avoids. Save → `createDef`/`updateDef`; the CTA disables while any catalog mutation is `pending`.
- **Errors surface globally** — every sheet's save/delete call is a plain mutation call with no local try/catch; a rejected write (mock throws the same `HABIT_CHAIN_SEED`/`HABIT_CHAIN_NOT_EMPTY`/`HABIT_REORDER_MISMATCH`/`HABIT_DEF_UNKNOWN_CHAIN` codes real 409s would) rides the app-level `MutationCache.onError` toast (`app/providers/QueryProvider.tsx`) — no per-sheet error UI needed.

## 3. Architecture & data flow

The domain is the **`QuestService` mirror**: a static catalog → one per-day table → a pure-read evaluator → the shared progression award tail.

```
TodayPage (face rows + chain hero) / RoutinesTab
  → useHabitDay(date) / useHabitActions(date) / useHabitSummary()   (@/data/hooks)
      mock: habitMock seed (+ awardGamificationEvent on check)
      real: habitApi → GET /api/habit/day/{date} | POST/DELETE /api/habit/{key}/check | GET /api/habit/summary
              → HabitController → HabitService
                    ├─ getDay: lazy row-per-catalog-entry (today only) → closePast → evaluateIntraday
                    ├─ check/uncheck: MANUAL, today only
                    └─ summary: 28d strength + 30d perfect days
              → HabitCatalogService → habit_chain / habit_def (lazy seed bootstrap, mezo-n5e9.1)
              → HabitEvaluator (pure reads: sleep/weight/intake/train/meal/goal)
              → ProgressionService.applyHabit / revertHabit  (source_type = HABIT)
              → habit_day (Postgres)
```

- **Lazy per-user catalog bootstrap** (`HabitCatalogService.ensureCatalog`, `mezo-n5e9.1`, ADR [0019](../decisions/0019-user-editable-habit-catalog-propose-only-ai.md)): the catalog is no longer static JSON read at request time. `HabitCatalog` is now only the fail-fast-validated **seed** source; the first catalog-touching call for a user — `getDay`, `check`/`uncheck`, or any of the admin endpoints (§4) — imports the two seed chains + any seed def the user has never had into `habit_chain`/`habit_def`, race-guarded the same way as `ensureRows` below. A def the user has soft-deleted is **never** reimported: `HabitDefRepository.findAllKeysEver` is a single deleted-inclusive native probe that tells "never had it" apart from "deleted it", with no short-circuit — a future seed-JSON addition still imports for existing users. The nightly `HabitJob`'s `closePast` deliberately does **not** trigger this bootstrap for a user with zero stale `habit_day` rows, so a dormant account accrues no writes. **`summary` is deliberately NOT a bootstrap point** (`@Transactional(readOnly = true)`, mezo-n5e9.1 review finding 3): it's read on every companion chat turn (`ContextSnapshotAssembler`/`PracticeTools`), so materializing 17 rows there would write a catalog for every dormant account on every chat message; a user with no catalog gets an honest empty summary instead, and `getDay` is the real bootstrap point. The routine editor (backend + editor UI done since `mezo-n5e9.2`, §2/§4; the AI suggester remains, `mezo-n5e9.3` — spec [2026-08-05-routine-editor-design.md](../superpowers/specs/2026-08-05-routine-editor-design.md)) is the write side over this same catalog.
- **Lazy day materialization** (`HabitService.getDay`/`ensureRows`): the first **today** read inserts one `pending` `habit_day` row per catalog entry, guarded against the cron race by the **partial-unique index** + a `DataIntegrityViolationException` catch that re-reads the winner's rows. A non-today read never creates rows (past days are read as-is). `ensureRows` **reconciles**, not just first-materializes (mezo-n5e9.1 review finding 1 — critical): it inserts a row for every active def with none yet for the date, not only when the day has zero rows, so a def created through the admin API *after* today already materialized still gets a row on the next touch — the gap used to 500 `check()` (a bare `.orElseThrow()` on a never-created row) for exactly that sequence.
- **Three evaluation-closure classes** (spec [D7](../superpowers/specs/2026-07-19-morning-evening-routine-habit-engine-design.md), the metric sets live in `HabitEvaluator`):
  - **INTRADAY** (`INTRADAY_METRICS` — M1 `sleep_wake_window`, M3 `weight_logged_today`, M4 `stim_intake_today`, M5 `training_done_today`, M6 `breakfast_protein`, + the two intention metrics `intention_focus_set` / `intention_reflected` (`mezo-a686`); MANUAL M2/E3 nominally here but skipped): re-evaluated on **every today-read** (`evaluateIntraday`); a `pending → done` transition on this read carries its level-up out on the response. **Since `mezo-u6jx` M3/M4 and M5's run branch are date-presence** — a live log for the date is enough, no wall-clock compare against the log's own `created_at`/`taken_at` (the retired `weigh-in-cutoff`/`morning-window-end`/`workout-window-hours`); see the [honest-derivation fix spec](../superpowers/specs/2026-08-05-habit-honest-derivation-fix-design.md).
  - **END_OF_DAY** (`END_OF_DAY_METRICS` — E1 `no_stim_after`, E2 `last_meal_before`): decidable only once the day is over, so they stay `pending` during the day and close on the **nightly `HabitJob`** or the next-day read (`closePast → closeByEvaluation`).
  - **BED_NEXT_DAY** (`METRIC_BED_NEXT_DAY` = E4 `bedtime_next_day`): completes on the read/close that first sees **the next morning's** sleep log; if the **next-day-noon** deadline passes first (`today.isAfter(habitDate+1) || now > 12:00`), it closes quietly `missed`.
- **`closePast`** (called by both the today-read and the cron) flips every stale `pending` row: END_OF_DAY/intraday metrics get one last honest evaluation, E4 gets the deadline logic, unknown/stale catalog keys close quietly `missed`.
- **Completion** (`complete`) stamps `done_at`/`xp_awarded`/`source`, saves, then — when the `ProgressionGate` is available (`ObjectProvider`) — calls `ProgressionService.applyHabit` (idempotent per `habit_day.id`), passing the row's own `habit_date` as the award's business date (`HabitSignal.occurredOn`, `mezo-huzd` — the same row-borne-date convention QUEST/ACTIVITY signals use for the `level_up_event.occurred_on` column). Since checks are today-only (`requireManualToday`, below) this coincides with the grant instant in v1 — no observable behavior change, just plumbing consistency for whenever a source gains backdating. Award amounts are the catalog XP (deterministic, ADR 0010).
- **Manual path:** `check` flips a MANUAL `pending → done` (today only) and awards; `uncheck` (same-day, MANUAL, `done`) reverts via `revertHabit` — it **soft-deletes** the `level_up_event` and **directly decrements** the skill row (the `moveActivityXp` precedent, no new event), so a re-check can cleanly re-award.
- **Read-triggered heartbeat:** the FE day read runs `staleTime: 0` in real mode (`useHabitDay`) so the server re-evaluates derived completion on every mount/focus — the READ *is* the evaluation trigger, mirroring `useDailyQuests`. Because the READ is the *only* trigger, **every write that can satisfy a DERIVED metric must invalidate `['habitDay']`** so the row re-derives without waiting for a remount. The weight/sleep/meal/gym/run log mutations do this (`mezo-pquo` — they previously did not, so a fresh log left the `✓` stale until the surface remounted), alongside the intention/ritual/sleep-goal/fuel-settings paths that already did; **since `mezo-u6jx` the supplement-intake log/undo (`useStackActions`, [fuel.md](fuel.md) §5) joins the fan-out too** — a stim intake can satisfy `stim_intake_today` (M4) or affect `no_stim_after` (E1), so it invalidates `['habitDay']` on every log/undo. The same log mutations also nudge `['dailyQuests', date]` for the twin quest metrics (`weight_logged`, `sleep_target`, `protein_target`/`own_recipe_meal`, `gym_session_done`).

## 4. Data model & API

**Table `habit_day`** (migration [`202607192100_mezo-d1jb_create_habit_day.sql`](../../backend/src/main/resources/db/changelog/1.0.0/script/202607192100_mezo-d1jb_create_habit_day.sql), the `daily_quest` sibling): `id uuid pk`, `created_by`, `is_deleted`/`created_at`, `habit_date date`, `habit_key varchar(40)`, `status varchar(8)` (`ck_` `pending|done|missed`), `done_at timestamptz`, `xp_awarded int` (`ck_` ≥ 0), `source varchar(7)` (`ck_` null|`DERIVED`|`MANUAL`). Identity: **partial unique** `uq_habit_day_user_date_key (created_by, habit_date, habit_key) where is_deleted = false` (+ `idx_habit_day_user_date`). The **same migration** relaxes the released `level_up_event.source_type` CHECK additively: `+= HABIT`.

**Schema change #2 — `level_up_event` partial-unique** (migration [`202607192130_mezo-d1jb_level_up_event_partial_unique.sql`](../../backend/src/main/resources/db/changelog/1.0.0/script/202607192130_mezo-d1jb_level_up_event_partial_unique.sql)): the habit **un-check** is the **first** source to soft-delete a `level_up_event` and later re-award with the same `(created_by, source_type, source_ref_id)`. The original plain unique constraint spanned soft-deleted rows, so the re-insert would collide — this converts it to the house-standard **partial unique** index (`where is_deleted = false`): one *live* award per source ref, soft-deleted rows ignored. GYM/RUN/SPORT/QUEST/ACTIVITY keep identical live-row idempotency.

**Catalog storage — DB-backed since `mezo-n5e9.1`** (ADR [0019](../decisions/0019-user-editable-habit-catalog-propose-only-ai.md), spec [2026-08-05-routine-editor-design.md](../superpowers/specs/2026-08-05-routine-editor-design.md)): two new per-user tables replace "the catalog is a fixed JSON file".

## 5. Integrations

All inbound edges are **pure reads** — habit depends on {biometrics, meal, fuel, train, goal, intention, ritual, progression}; nothing depends back on habit (`feature_slices_are_cycle_free` holds).

- **← Biometrics** (`HabitEvaluator`): M1 `sleep_wake_window` and E4 `bedtime_next_day` from `SleepLogRepository` (wakeup / next-day bedtime vs the goal anchor ± window); M3 `weight_logged_today` from `WeightLogRepository` — **since `mezo-u6jx`** a live weight log existing for the date (date-presence; the `weigh-in-cutoff` wall-clock compare against `created_at` is retired).
- **← Fuel** (`HabitEvaluator`): M6 `breakfast_protein` = Σ protein of today's `breakfast`-slot meals via `FuelDayService.getDay` ≥ `protein-target-g`; E2 `last_meal_before` = last `meal` `logged_at` ≤ `kitchenClose`; M4 `stim_intake_today` / E1 `no_stim_after` join `SupplementIntakeRepository` to **stim-kind** `PantryItemRepository` items — **since `mezo-u6jx` M4 is date-presence** (any stim-kind intake logged for the date satisfies it, no window compare), while **E1 stays wall-clock** (unchanged; still compares each intake's `taken_at` against the resolved cutoff — see the accepted retro-log residual in §9). **Since `mezo-53su` (spec D3) the caffeine cutoff E1 compares against comes from Fuel's ungated `CaffeineCutoffPort`** (`feature/fuel/service`, `LocalTime resolve(UUID)`) — `HabitEvaluator` injects the port and calls `caffeineCutoffPort.resolve(userId)` instead of reading `HabitProperties.caffeineCutoff`; that property + its `mezo.habit.caffeine-cutoff` yml key were **removed**. The resolver is deliberately **not** switch-gated (the habit metric must resolve even with the fuel-settings surface off — the `SleepAnchorPort` idiom), ghosting the config default `"14:00"` when no `fuel_settings` row exists. See [fuel.md](fuel.md) §4/§5.
- **← Train** (`HabitEvaluator`): M5 `training_done_today` = a finished gym session (`WorkoutSessionRepository.findDoneInstanceDates`) **or** a run logged today (`RunSessionLogRepository`) — **since `mezo-u6jx` the run branch is date-presence too**, unifying with the gym half's own date-presence fallback (§9); the wake-anchored cutoff is retired (see `← Sleep goal`).
- **← Intention** (`HabitEvaluator`, `mezo-a686`): the two intention habits complete off `IntentionFocusRepository` (`intention_focus_set` = today has ≥ 1 live focus) and `DailyIntentionRepository` (`intention_reflected` = today's reflection set) — both plain JPA beans injected directly (the cross-feature-read precedent). Today's `daily_intention`/`intention_reflect` rows open `IntentionSheet`/`ReflectSheet` (the honest log surface) — dispatched by `TodayPage`'s `act()` since `RoutineCard` retired. One-directional (habit → intention). See [intention.md](intention.md).
- **← Ritual** (`HabitEvaluator`, `mezo-hvmx`): the `evening_ritual` row's `ritual_closed` metric is a single existence check against `RitualDayRepository.findByCreatedByAndRitualDate` — a live `ritual_day` row for the date means the Napzárás close happened. It sits in `INTRADAY_METRICS` (re-evaluated on every today-read). The ritual endpoints award no XP themselves; completion rides the habit's own catalog XP through the existing HABIT tail. One-directional (habit → ritual) — the ritual domain does not read habit. See the [ritual design spec](../superpowers/specs/2026-07-24-daily-closing-ritual-design.md).
- **← Sleep goal** (`HabitTargets`, `mezo-dbsr`, spec D3): the wake/bed anchors now come from the **sleep goal** through the shared **`SleepAnchorPort`** — `HabitTargets` is a thin adapter over it (`HabitTargets.java:17-24`), no longer a `GoalRepository` + `HabitProperties.defaultWake`/`defaultBed` reader (those config keys are **removed**). The port ghosts config defaults when no sleep-goal row exists (the no-goal default **bed shifted 23:00 → 22:00**). The M1 `sleep_wake_window` / E4 `bedtime_next_day` checks re-centre on the sleep goal's anchor but **keep their 45-min tolerance window** (`mezo.habit.wake-window-min`) — the strict ±15 band is only the sleep-goal regularity *score*, not the habit gate. `kitchenClose = bedTime − kitchen-close-offset-min (90′)`. **Since `mezo-67rb` the M5 `training_done_today` run-branch cutoff was wake-anchored** (`SleepAnchorPort` wake `+ mezo.habit.workout-window-hours`, default 6 — a ghost wake 06:00 reproduced the retired static 12:00); **`mezo-u6jx` retires it** — the run branch is date-presence too now (any run dated today counts, unifying with the gym half), so `HabitProperties.workoutWindowHours` + the `workout-window-hours` yml key are **removed** (see §9 D6). The gym half stays date-presence (spec §3).
- **→ Progression** (`ProgressionService.applyHabit` / `revertHabit`, source `HABIT`): completion rides the shared idempotent `award(...)` tail (`source_type=HABIT`, `source_ref_id=habit_day.id`) onto the habit's **LIFE** skill; un-check reverts by soft-deleting the event + decrementing the skill row directly (§4 schema change #2). The CHECK was relaxed additively. Discipline trait and the Growth journal do **not** consume habit signals in v1 (deliberate — wireable later).
- **→ Today / Growth surfaces:** Today's per-face `TodoCard` rows + morning chain hero, and the Rutin tab (`/me/growth`), as in §2. The `AppHero` ⚡ counter stays **quest-only** — habits do not feed it.
- **→ Today `WindDownBanner` (the `wind_down` habit's SECOND surface, sleep slice C-éj `mezo-d71m`):** during the evening winddown window (`[bed−60, bed)`) the Today `WindDownBanner` ([today.md §2](today.md)) renders the `wind_down` MANUAL habit with its own `Pipa` check, reading `useHabitDay(date)`/`useHabitActions(date)` over the **same `['habitDay', date]` cache as the face's own rows** — so a check on either surface flips the other, and the completion's level-up rides the shared `useLevelUp` overlay from whichever surface performed it. No habit-domain change: it is a second consumer of the existing hooks, not a new metric or catalog row.
- **↔ Account progression / `AppHero` (mock-mode side-effect):** in **mock mode** `useHabitActions.check` also calls `awardGamificationEvent(qc, {type:'HABIT', xpOverride})` (`data/habit/habitHooks.ts:58`) so the `AppHero` account XP/streak/coin ledger moves in an offline demo — the tenth call site of the mock account-XP precedent (see [growth.md §2](growth.md), "Account progression"). `HABIT` is registered in `gamificationTypes.XpEventType` + `xpValues` (`XP_VALUES.HABIT = 0`, `DAILY_CAPS.HABIT = 10` — the amount comes from the habit's own `xpOverride`). **Real mode never calls it** (account XP is derived from the profile there). **The mock arm is NOT idempotent** (`mezo-mvb4.1`, asserted in `habitHooks.test.tsx`): it awards on every `check()` without asking whether the row is already `done`, and one habit is nowhere near the `HABIT` cap of 10 — so two taps of the *same* habit award twice. Real mode cannot: `HabitService.check` rejects an already-done row with `HABIT_ALREADY_DONE`. The only mock-mode guard is the in-flight `pending` withdrawal, and that guards **only the control it belongs to** — which is why a habit must never be offered by two controls at once (the Today Este face's `wind_down` case, [today.md §2](today.md)). Two DERIVED habits DO move mock account-XP through their owning surface's mutation (`mezo-o5hx`): the mock `reflect()` (intention) and the mock ritual `close()` both call **`completeMockDerivedHabit(qc, date, key)`** (`data/habit/habitHooks.ts` — the mock mirror of a server-side derived completion; it flips the row in the `['habitDay', date]` cache, seeding the day from the mock seed if unmounted, and returns whether it flipped so the caller can gate a one-time award). Other DERIVED rows still carry no mock completion path.

## 6. How to use it (consume)

```ts
import { useHabitDay, useHabitActions, useHabitSummary } from '@/data/hooks'

const { habits, levelUps, mode } = useHabitDay(date)      // date = 'YYYY-MM-DD'; habits: HabitItem[]
const { check, uncheck, pending, consumeLevelUps } = useHabitActions(date)
const { data: summary } = useHabitSummary()               // { perfectMorningDays30, perfectEveningDays30, habits[] }

await check('morning_sunlight')                            // MANUAL only → resolves the write's levelUps
```

- `useHabitDay` is a **manual dual-mode** shape (like `useDailyQuests`, not `useDualQuery`): real mode runs `staleTime: 0` and returns the **empty day** (never the seed) while unresolved. `levelUps` is non-empty only on the read that performed the completion — feed `levelUps[0]` to `showLevelUp(...)` then call `consumeLevelUps()` (`TodayPage` does this in an effect, `TodayPage.tsx:136-141`).
- `check(key)` resolves the write's `levelUps` array; the caller surfaces `lu?.[0]` to the overlay.
- Ghost-guard: `habits.length === 0` → contribute no rows (`TodoCard` ghosts on an empty face). Never import `habitApi`/`habitMock` directly — go through `@/data/hooks`.
- Query keys: `['habitDay', date]`, `['habitSummary']`; a real-mode write invalidates both + `['progressionProfile']`.

**The catalog itself — read + CRUD (`mezo-n5e9.2`):**

```ts
import { useHabitCatalog, useHabitCatalogActions } from '@/data/hooks'

const { catalog, isPending } = useHabitCatalog()          // { chains: HabitChainInfo[] }, queryKey ['habitCatalog']
const { createChain, updateChain, deleteChain, reorderChain,
        createDef, updateDef, deleteDef, pending } = useHabitCatalogActions()

await createChain({ title: 'Déli szünet', daypart: 'DAY' })
await reorderChain(chainId, newDefIdOrder)                 // full position replacement — an exact permutation, or 400
```

- `useHabitCatalog` is a **`useDualQuery`** hook (`realStaleTime: 60_000` — the editor is the write surface, so a moderate cache window is fine, unlike `habitDay`'s `staleTime: 0` lazy-eval heartbeat); real mode never falls back to the mock seed while unresolved (`realEmpty: {chains:[]}`).
- Every `useHabitCatalogActions` mutation mirrors a real 409/400 in mock mode too (thrown `Error`s with the same codes — `HABIT_CHAIN_SEED`/`HABIT_CHAIN_NOT_EMPTY`/`HABIT_REORDER_MISMATCH`/`HABIT_DEF_UNKNOWN_CHAIN`), so a consumer never needs a mock-only error path — see the [routine editor](#2-user-facing-behavior) above for the one FE consumer (`RoutineEditorPage` + its sheets).
- **Mock catalog ids are stable non-UUID strings** (`chain-morning`, `def-wake_on_time`, …) — never assume UUID shape when writing a mock-mode consumer/test.

## 7. How to extend it

**Add a habit to a chain — two paths since `mezo-n5e9.1`:**
- **User-created / custom habit (any user, no restart):** `POST /api/habit/def` (chainKey, title, mode, skillKey, xp, optional why/anchorCopy/linkUrl/position; DERIVED requires a metric from `HabitEvaluator.SUPPORTED_METRICS`, §4) — the editor's write API, validated at write time (`HabitAdminService`). **Since `mezo-n5e9.2` the routine editor page calls this directly** (§2's „+ Új habit" / „+ Új rutin"); it is still exercisable via the endpoint (or `HabitAdminService`) directly for anything the editor UI doesn't expose.
- **New BUILT-IN default for every user:** append a `HabitDef` to `content/habit-catalog.json` (unique `key`, correct `chain`/`position`, a LIFE `skillKey`, `xp` 5–15, and the MANUAL ⇔ `metric == "manual"` invariant — `HabitCatalog`'s loader still fails fast on a malformed seed row at startup). This does **not** retrofit existing users automatically: `HabitCatalogService.bootstrapMissing` only imports a seed key a user has never had, and only on that user's *next* catalog touch (`getDay`/`check`/any admin call — NOT `summary`, which is read-only/non-bootstrapping) — there is no push and no per-user migration script.

Either way, then:
- **MANUAL habit** (`mode: "MANUAL"`, `metric: "manual"`): no evaluator work — it completes via the `Pipa` check. Add its key to `habitAction`'s implicit path (MANUAL already maps to `{kind:'check'}`). `morning_pushups` („50 fekvőtámasz") is the plain precedent.
- **Habit with an external link** (`linkUrl`): set the field on the def (it flows `HabitDefEntity` → `HabitMapper` → `HabitResponse` → `HabitItem` → `todayItems.ts` → `ItemRow`). The row auto-renders a trailing `↗` **beside** its action (`.itemrow-link`, or `.fhc-next-link` when the step is promoted into the chain hero) — no per-key code, and the link is never nested inside the row's button. `morning_video` is the precedent; mirror the `linkUrl` in `habitMock.ts` for mock parity.
- **DERIVED habit:** a *seed* DERIVED habit needs a `case` added to `HabitEvaluator.satisfied` reading the owning feature's repository/service (**pure reads only** — honest completion), registered in the right closure set (`INTRADAY_METRICS` / `END_OF_DAY_METRICS` / `METRIC_BED_NEXT_DAY`, which together form `SUPPORTED_METRICS`) so `evaluateIntraday`/`closePast` route it; a *custom* DERIVED habit instead just **picks** one of the already-registered `SUPPORTED_METRICS` at creation time — no new evaluator code, no user-defined evaluators (ADR [0019](../decisions/0019-user-editable-habit-catalog-propose-only-ai.md)). Optionally add a **CTA nav target** in `features/today/logic/habitAction.ts` (`NAV_BY_KEY`, or a bespoke `kind` like `protein_breakfast`'s meal-sheet) so the DERIVED row taps through to its logging surface.
- New tunable → `HabitProperties` (`mezo.habit.*`), never a code constant ([`configuration_conventions.md`](../references/configuration_conventions.md)). New XP → the catalog (seed) or the def's `xp` field (custom/edited).
- **Mock parity:** mirror the new row in `data/habit/habitMock.ts` (`mockHabitDay` + `mockHabitSummary`) so both `pnpm test` modes stay green.
- House standards: contract-first ([`api_contract_conventions.md`](../references/api_contract_conventions.md)), backend per [`docs/references/*.md`](../references/), dual-mode hook recipe in [`_platform-data-layer.md`](_platform-data-layer.md).

**A whole new chain, custom habits, and full catalog CRUD are supported since `mezo-n5e9.1`** (backend; see the admin table in §4 and ADR [0019](../decisions/0019-user-editable-habit-catalog-propose-only-ai.md)) — the data model needed no redesign, exactly as the original spec §10 intended. **Since `mezo-n5e9.2` the routine-editor FE page is built too** (§2, `RoutineEditorPage` + `ChainEditSheet`/`HabitEditSheet`). The **AI suggester** (`.3`, propose-only — the model never writes, ADR 0019) remains the one not-yet-built slice.

## 9. Decisions, gotchas & deferred

- **Decisions:** spec §2 **D1–D9** — own `feature/habit` domain (the quest mirror, D2), per-habit LIFE-skill XP via the `HABIT` source (D3), habit-strength + perfect-day, no hard streak (D4), Today surface + Growth Rutin tab (D5), wake/bed anchors + `HabitProperties` for everything else (D6 — **anchors re-sourced from the sleep goal via `SleepAnchorPort` in `mezo-dbsr`**; the old `HabitProperties.defaultWake`/`defaultBed` keys are gone, no-goal bed default now 22:00, §5 — and since **`mezo-53su` the caffeine cutoff is re-sourced from Fuel's `CaffeineCutoffPort`**, `HabitProperties.caffeineCutoff` + `mezo.habit.caffeine-cutoff` removed; and since **`mezo-67rb` the M5 run-branch cutoff was wake-anchored** — `SleepAnchorPort` wake `+ mezo.habit.workout-window-hours` (6) — **before `mezo-u6jx` retired it for date-presence**: the weigh-in/stim/run wall-clock compares are gone entirely, so `HabitProperties.weighInCutoff`/`morningWindowEnd`/`workoutWindowHours` + their `mezo.habit.*` yml keys are now **removed** (the `mezo-53su`/`mezo-67rb` removal precedent) — see the [honest-derivation fix spec](../superpowers/specs/2026-08-05-habit-honest-derivation-fix-design.md)), the three closure classes (D7), same-day MANUAL un-check with direct decrement (D8), mock parity that also moves the account XP total (D9). **D5's Today half was superseded by [ADR 0014](../decisions/0014-today-daypart-faces.md)** (`mezo-j7u4`): the chains are rows on their daypart face, not a `RoutineCard`; the domain contract is unchanged. ADR [0010](../decisions/0010-gamified-growth-xp-feedback-not-payment.md) is the tone contract (no failure state, no break-punishment).
- **Gotcha — E4's noon deadline:** `bed_on_time` completes only when the **next** morning's sleep log arrives; past next-day 12:00 (`closePast`) it closes quietly `missed`. A late-arriving sleep log after the deadline no longer counts.
- **Gotcha — vacuous kitchen-close:** E2 `last_meal_before` yields **`true`** when **no** meals were logged that day (nothing eaten after close ⇒ the habit is honestly kept), not `missed`.
- **Gotcha — gym date-presence fallback, now unified with the run branch (`mezo-u6jx`):** finished gym sessions have no `completed_at`, so M5's gym half counts a **done instance on the date** (date-presence, an honest fallback per spec §3); **since `mezo-u6jx` the run half is date-presence too** — any run logged for the date satisfies M5, retiring the wake-anchored cutoff (`SleepAnchorPort` wake `+ workout-window-hours`, itself only introduced in `mezo-67rb`) entirely. Both branches are now honest-by-presence.
- **Gotcha — E1 retro-log residual, accepted (`mezo-u6jx`):** `no_stim_after` still compares each stim intake's `taken_at` against the resolved caffeine cutoff — a retro-logged afternoon coffee (`taken_at` is the log moment, not the actual morning consumption) still busts E1, unlike M4 which went date-presence in the same change. Accepted for now (spec §2); the honest fix — an optional „mikor ittad?" time field on the intake log — is deferred (spec §5).
- **Gotcha — END_OF_DAY habits show `pending` all day:** E1/E2 are not in `INTRADAY_METRICS`, so the today-read never completes them — they resolve only at the nightly close or the next-day read. Expected, not a stuck row.
- **Gotcha — deliberate mock-seed deviations (`mezo-o5hx`):** the static mock day has no evaluator, no nightly close and no "tomorrow", so honest derivation cannot be mirrored. Therefore in `habitMock.ts` (a) `caffeine_cutoff` + `kitchen_close` are **MANUAL** (checkable) instead of DERIVED END_OF_DAY — otherwise they'd be permanently dead rows in the demo; (b) **`bed_on_time` is omitted entirely** (E4 could never complete → the evening chain would never reach a perfect evening in mock). Real mode keeps the honest catalog behavior for all three. The two derived rows the user *can* honestly complete in mock (`intention_reflect`, `evening_ritual`) flip via `completeMockDerivedHabit` from their owning surface (§5).
- **Gotcha — MANUAL habits are never auto-completed:** M2/E3 nominally sit in the intraday set but `evaluateIntraday` skips `metric == "manual"` — they complete solely via the `check` write (honest self-claim), and quietly `missed` at close if untapped.
- **Gotcha — the perfect toast fires on mount:** `useChainCelebration`'s `wasComplete` ref starts `false`, so a chain that is already complete when its face first mounts emits the celebration toast once on that mount (an accepted "welcome back" chime, not a per-completion-only event). **Since the faces this also fires on a face SWITCH** — `TodayPage` remounts the `.faceswap` wrapper on every selection, so hopping to a completed face re-chimes. Same accepted semantics, one more way to reach it.
- **Gotcha — after midnight the `WindDownBanner` checks the NEW day's row.** The Today banner (sleep slice C-éj, §5) keys `useHabitDay`/`useHabitActions` on `localDateString()`, so once the wall clock passes midnight (a bed time of e.g. 00:15 puts the winddown window on both sides of midnight) the `wind_down` check writes to the **new** day's `habit_day` row — the same date-source behaviour as the face rows, deliberately consistent (every Today surface uses the local-date string, never a UTC slice).
- **Deferred:** the original spec §10 sub-project ① (custom/user-edited habits + catalog-management UI) is **done** — backend since `mezo-n5e9.1`, editor UI since `mezo-n5e9.2` (§2/§4, §6's catalog hooks) — see ADR [0019](../decisions/0019-user-editable-habit-catalog-propose-only-ai.md); the **AI suggester** remains the one not-yet-built child slice (spec [2026-08-05-routine-editor-design.md](../superpowers/specs/2026-08-05-routine-editor-design.md) `.3`). Still deferred: PWA reminder notifications; companion flavor copy + discipline-trait/Growth-journal HABIT consumption; and the three sibling specs — ② Sleep Cycle screenshot ingestion, ③ Fuel „Mai" slot-timing fix + slot-level AI logging, ④ morning-training reschedule + Tasty Dose/Origin protocol data setup.
- **Correction beyond the original design note (`mezo-n5e9.4`):** `HabitDefUpdateRequest` has no `skillKey` field, so a def's skill is contract-immutable after creation — same as `mode`/`metric` — not editable in `HabitEditSheet`'s edit mode (§2).
