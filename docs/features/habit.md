# Habit — Morning & Evening Routine Engine

> Two fixed habit-stacking chains — a **morning** and an **evening** routine — surfaced on the **Nap** tab as a **„Rutin" tile** on the daypart mosaic (`/nap`), which opens the chains' own full page at **`/nap/rutin`** (tick), and on the **Én** tab as a wide Rutin tile off the Én hub's mosaic, opening **`/me/rutin`** (`RutinHubPage`, `mezo-3zue.3` — build and edit; the routine surface left the Growth family for good, absorbing the former `/me/growth/rutin` overview and the former `/me/routines/edit` editor into one page). **Status: ✅ done** (backend + FE real + FE mock). **The Design 2.0 redesign (`mezo-d20`) changed only where the chains are drawn** — the catalog, the evaluator, the closure classes, the XP tail and every hook are untouched; see [today.md](today.md) for the render-layer history. Driving spec: [`2026-07-19-morning-evening-routine-habit-engine-design.md`](../superpowers/specs/2026-07-19-morning-evening-routine-habit-engine-design.md); driving ADR [0010](../decisions/0010-gamified-growth-xp-feedback-not-payment.md) (XP is feedback, not payment). bd `mezo-d1jb`.

## 1. Summary

**Habit** is a lean habit engine built on habit-stacking psychology: two **fixed identity chains** — 9 MORNING + 6 EVENING catalog habits (incl. the two **intention** habits added by `mezo-a686` — `daily_intention` MORNING / `intention_reflect` EVENING, see [intention.md](intention.md); the two habits added right after morning sunlight — `morning_pushups` „50 fekvőtámasz" / `morning_video` „Reggeli videó" with a clickable external `linkUrl`; and `evening_ritual` „Napzárás", DERIVED off the sleep-anchored closing ritual — see the [ritual design spec](../superpowers/specs/2026-07-24-daily-closing-ritual-design.md)) — each item anchored to an existing routine ("fogmosás után", "vacsora után"). Most completion is **DERIVED** over data the user already logs (sleep, weight, supplement intakes, training, meals) — a habit is **never self-claimed where a real signal exists** — with four MANUAL exceptions (morning sunlight, 50 push-ups, the morning video, evening wind-down). Each habit maps to a **LIFE skill** and earns a small deterministic XP (5–15) through a new idempotent **`HABIT` progression source** — the quest/activity twin. Consistency is a gentle trailing-28-day **habit strength** ratio (a lapse fades, never zeroes) plus a quiet **perfect-day** celebration — **no hard streak, no break-punishment** (the [ADR 0010](../decisions/0010-gamified-growth-xp-feedback-not-payment.md) tone: `missed` renders dim and silent, no red).

It is deliberately the **quest pattern's mirror, not a quest extension** (spec [D2](../superpowers/specs/2026-07-19-morning-evening-routine-habit-engine-design.md)): quests are rotating *offers* (reroll, adaptive difficulty, expiry), habits are *fixed chains* — same machinery (catalog JSON + per-day table + evaluator over pure reads + lazy read-time evaluation), different psychology. The data model is general (chain/position/anchor/mode/metric) so a later custom-habit expansion needs no redesign; v1 ships exactly the two fixed chains.

Status per layer: **backend** ✅ (`feature/habit` — catalog, `habit_day` table, evaluator, service + nightly close job, controller, `HABIT` progression source), **FE real** ✅ (the Nap hub tile + `/nap/rutin` + `/me/rutin`'s `RutinHubPage` over the real endpoints), **FE mock** ✅ (deterministic seed day + summary; mock check also moves the account XP total). Design decisions are spec §2 **D1–D9**; the catalog table is spec §3; the three evaluation-closure classes are **D7**.

## 2. User-facing behavior

**Nap — the „Rutin" tile and the `/nap/rutin` page** (Design 2.0, `mezo-d20.2.1`/`.2.3`; driving decisions [ADR 0032](../decisions/0032-five-tab-ia-dissolved-section-shells.md) + [ADR 0033](../decisions/0033-mozaik-2-tile-language.md)). **`RoutineCard` was deleted long ago** (`mezo-j7u4`), and the `ItemRow`-in-`DayGroups` layer that replaced it is deleted too (`mezo-d20.9.1`) — along with `TodayPage`, `DayGroups`, `TodayRow` and the three `Daypart*` views. The chains now surface in two places on the Nap tab:

- **The hub tile** (`NapHubPage`, `features/today/pages/`) — one washed Mozaik tile per daypart panel, eyebrow „Rutin", clay icon `i-rend`, gold on 🌅 Reggel and lavender on 🌙 Este. Its single datum is the chain's live state: `{next.title} · {done}/{total}` while something is pending, `kész ✓ · {done}/{total}` once the chain is complete. **Honest absence:** if the daypart's chains have no rows at all, the tile is not rendered — no empty tile, no placeholder. Tapping it navigates to `/nap/rutin?dp=reggel|este`; the tile itself never checks anything. Its membership test is catalog-driven exactly as the old bucketing was — a `chainKey` set built from `useHabitCatalog().chains` filtered on `daypart === 'MORNING'|'EVENING'`, keeping the `useHabitDay` rows whose `chain` is in it.
- **The page** (`NapRutinPage`) — a `MozaikPage tone="gold"`. `?dp=` decides which chain **group leads**; the other follows below under its own header with a `{done}/{total}` count. The lead group gets a `PageHero` (chain-group clay spot + `{done}/{total}` + „Reggeli rutin"/„Esti rutin" + „N elem · lánc") and a `StatStrip`: **`{perfectDays}/30` tökéletes reggel/este** (from `useHabitSummary`), **`{chainStrength}% lánc-erő · 28 nap`** (the mean of the group's non-null `strengthPct`s — the cell is omitted entirely when no row has one) and **`+{xp} XP ma`**. Quiet principle line: *„A lánc-erő az elmúlt 28 nap konzisztenciája — egy kihagyás nem nullázza, csak halványítja."*

**A DAY-daypart chain has no Nap surface.** The hub builds only MORNING and EVENING tiles, and `NapRutinPage` renders only those two groups — the ☀️ Nap face slot the catalog-driven bucketing opened up in `mezo-n5e9.2` was lost with `todayItems.ts`'s renderer. A custom DAY chain still gets its own card on `/me/rutin` (`RutinHubPage`, below) and stays fully editable; it simply is not offered on the Nap tab (§9).

What survived, what changed:

- **Each row** (`.nr-row`) is a tick button + title + the `anchorCopy` cue (or `habitHint`'s explainer, below) + a 28-day strength bar with its `{pct}%` — the strength bar is **new on the daily surface**: the list era showed strength only on the routine overview (now `/me/rutin`). The `+N XP` chip per row is gone; XP is aggregated into the stat strip's „XP ma". Completion is the filled `✓` tick plus a struck title, not an icon swap. The `todayItems.ts` **`DEDUP_PAIRS` XP absorption** (`morning_weigh_in`↔`weight_logged`, `morning_workout`↔`gym_session_done`, `wake_on_time`↔`sleep_target`, `protein_breakfast`↔`protein_target`) is **no longer applied on this surface** — habits and quests now live on two different pages (`/nap/rutin` and `/nap/kuldetesek`), so there is no shared list for a duplicate row to appear in; the dedup code is intact but unrendered (§9 and [today.md §9](today.md)).
- **Tick semantics are ADR 0010's, verbatim** (the retired `TodayPage.act()` dispatcher, relocated into the page's `tickAction`): a **MANUAL** pending row checks through `useHabitActions(date).check`; a **done MANUAL** row can honestly un-tick (`uncheck`); a **done DERIVED** row **cannot** (its tick renders inert — un-ticking a derivation would be a lie); a pending **DERIVED** row routes through `logic/habitAction.ts` to its real log surface — `check` · `nav` · `meal-sheet` (Fuel's unified `LogFlowPage`, opened with `initialSlot="breakfast"`) · `sleep-sheet` (`SleepLogSheet`) · `intention-sheet` (`IntentionSheet`) · `intention-reflect` (`ReflectSheet`). Nothing on this page self-completes a derivation.
- **A row with no servable action renders a non-interactive tick.** `habitAction`'s `'none'` (a hinted pending row, or any row that is neither MANUAL nor mapped) yields `tickAction === null`, and the page renders the tick as an `aria-hidden` span rather than a dead button. This is the old `servableAction()` guarantee re-expressed one layer down: **no row ever shows a control this screen cannot serve.**
- **`bed_on_time` stays deliberately passive** (`mezo-o5hx`): tomorrow's sleep log decides it (E4), so `habitAction` returns `'none'` and `habitHint` substitutes „holnap reggel, az alvásnaplódból derül ki" in place of the anchor copy — the button-less row reads as „this ticks by itself" rather than as broken.
- **`wake_on_time` explains an honest out-of-window log the same way (`mezo-czol`):** a sleep log whose wakeup misses the goal window leaves M1 honestly `pending`. `HabitService.getDay` computes a server-only `hint` — e.g. „06:30 — a célablakon kívül (05:30 ± 45′)" — and `habitAction`/`habitHint` treat a hinted pending row exactly like `bed_on_time`'s precedent: no CTA, the hint renders in the anchor line. A still-`pending` row with **no** sleep log yet gets a **null** hint and keeps its actionable tick — „not logged" and „logged, out of window" read as different states (§9).
- **A row with a `linkUrl`** (`morning_video`) has **no surface for it on `/nap/rutin`** — the trailing `↗` affordance died with `ItemRow`. The field still flows `HabitDefEntity → HabitMapper → HabitResponse → HabitItem` and is rendered nowhere on the daily surface (§9).
- **`evening_ritual` is no longer filtered out of the evening chain.** In the islands/list eras the Este hero's Napzárás CTA owned the act, so the row was suppressed (`OWNED_BY_RITUAL_HERO`). That filter lived in `DaypartEvening`, which is deleted; `NapRutinPage` renders every evening-chain row. Its `habitAction` `nav` mapping is unchanged and still routes to `/ritual` — so the same act is now offered both by the Este hero tile's `Zárjuk le a napot` CTA and by this row. Honest duplication, not a designed affordance (§9).
- **`wind_down` is back to ONE surface.** Its second surface — the evening island's/panel's `Leállás megvolt ✓` ghost in the *leállás* phase — went out with `DaypartEvening` and `useWindDownPhase`. The habit is now offered exactly once, by its own row, which *closes* the „a habit must never be offered by two controls at once" hazard the mock arm's non-idempotence made dangerous (§5/§9).
- **In-flight writes withdraw the control rather than dimming it.** While `useHabitActions().pending` is true every tick button on the page is `disabled`, so a double-tap cannot fire a second mutation. The guard is page-wide now (the page renders only habit rows), not scoped to `action.kind === 'habit'` as it had to be on the mixed list.
- **Act-anywhere is unchanged**: selecting Reggel at 22:00 gives every morning row its live tick. The daypart is a *view*, never a gate.
- **Chain completion no longer fires a celebration toast.** `logic/useChainCelebration.ts` and `components/ChainCelebrations.tsx` were **deleted** with `TodayPage` (`mezo-d20.9.1`); nothing mounts a per-chain `wasComplete` watcher any more, so „🌅 Tökéletes reggel" / „🌙 Tökéletes este" / „✨ {title} kész" fire on no surface at all. The per-check reward toast below is what remains (§9).
- **The check's own feedback is a DS reward toast (`mezo-k5sa`), unchanged in mechanism.** `NapRutinPage`'s MANUAL check calls `features/progression/logic/rewardToast.ts`'s `buildHabitRewardToast({ title, chainDone, chainTotal, xp, levelUp })` — `chainDone`/`chainTotal` computed from the row's own chain **before** the check, so the card's eyebrow „Szokás · {chainDone+1} / {chainTotal}" optimistically shows the number the list is about to print — and emits it on the `toastBus` ([_platform-design-system.md §2 item 7](_platform-design-system.md)). The **meter** row shows the server's `LevelUpResult.gains[0]` skill name (real mode) or the literal `'XP'` (mock mode never invents a skill name it doesn't have); a **LEVEL UP** badge renders inline in the same card only when `gains[0].levelAfter > levelBefore`. The full-screen `LevelUpProvider`/`useLevelUp()` overlay still never fires from a habit check — it is Train's alone.
- **The read-triggered `levelUps` are no longer consumed on the daily surface.** `useHabitDay`'s `levelUps` (a DERIVED completion that closed on *this* read) used to be drained by `TodayPage`'s consume-once effect into a toast. `NapRutinPage` never calls `consumeLevelUps()`, so a derived completion that lands on a page read produces **no toast at all**; the only remaining caller is `RitualPage`, which deliberately drains and *drops* them so the Napzárás Harvest act stays the single celebration (§9).
- **Honest ghost:** with no habits (switch off in real mode, or real mode before the day resolves) the hub renders no Rutin tile and `/nap/rutin` renders no group — `groups` filters out any group with zero items and the hero is `null`. No skeleton, no seed leak.
- **Inactive-chain semantics are deliberately split (`mezo-n5e9.2`/`.4`):** the Nap surfaces bucket by whether the catalog knows the chain at all, never by `chain.isActive`, so pausing a chain mid-day doesn't retroactively erase honest history from the current day's view; `/me/rutin`'s chain cards (below) are where „pausing a chain" actually shows up — **a paused chain stays visible there and merely dims** (`.gr-chain.is-inert`, opacity only; every control inside stays live). It is deliberately NOT hidden: the toggle that un-pauses a chain lives on that very card, so filtering inactive chains out would strand a paused chain with no way back (fix wave, `mezo-3zue.3`). The *day* surfaces are the ones that drop it: `useHabitDay` returns ACTIVE defs only, which is why the today branch renders from the catalog and only overlays the day's statuses. (The chain-hero/celebrations half of this rule went away with the celebrations.)

**`/me/rutin` — the routine home (`RutinHubPage`, `mezo-3zue.3`), off the Én hub's wide Rutin tile.** The overview/build/edit surface now lives in **one page** under Én, not two under Growth: it absorbed the former `GrowthRutinPage` (`/me/growth/rutin`, `mezo-rmi0.1` — the date-navigable read-only overview) AND the former routine editor (`RoutineEditorPage`, `/me/routines/edit`, `mezo-n5e9.2` — the chain/def CRUD chrome) into a single `MozaikPage tone="gold"` reached with a `‹ Én` back chip. **`/me/growth/rutin` and `/me/routines/edit` are now bare `<Navigate replace>` redirects to `/me/rutin`** (`app/router.tsx`). Daily ticking is unaffected either way — it stays on `/nap/rutin`, never here: every habit row on this page is either a static status mark or a navigation target, never a tick control.

The page keeps `GrowthRutinPage`'s two branches (date-navigable via a top `DayNavigator` — `‹ prev | tappable date | next ›`, a themed calendar popover, defaults to today, `next` disabled at today) and layers the editor's chrome onto the **today** branch only (a past-day view stays read-only-clean — it is looking at history, not the live catalog):
> - **Today:** a `PageHero` (`i-hajnal` clay icon, big number `{doneToday} / {totalToday}`, name „Rutin", sub = the 28-day mean strength when any habit has one) + a header „✨ AI javaslat" action → `AiSuggestSheet` (below), then two **`.gr-covtile` counter tiles** (`Reggel`/`Este`, each a 30-segment strip filling left-to-right by count with a once-animating stagger, `prefers-reduced-motion`-guarded, off `perfectMorningDays30`/`perfectEveningDays30`), then the `DayNavigator`, then **one card per `useHabitCatalog()` chain — every chain, seed and custom, active and paused** (position order, titled from `chain.title`; a paused one dimmed with `.gr-chain.is-inert`, never hidden) carrying the editor's controls inline — an active `Toggle` (`updateChain(chain.id, {isActive})`) + an `✎` chip opening `ChainEditSheet` in edit mode, and a **`SortableList`** of the chain's habit rows (`reorderChain(chain.id, newDefIds)` on drag, no local staging state). **The today branch renders from the CATALOG and only overlays today's status** where `useHabitDay` has a matching row (fix wave, `mezo-3zue.3`): the day view is ACTIVE-defs-only and returns nothing at all for a chain with no habits today, so deriving the rows from it hid paused defs, stranded a brand-new chain, and sent reorder a **partial** id list — which the backend rejects with 400 `HABIT_REORDER_MISMATCH` (the mock arm mirrors the throw). Each row shows its status mark (only where the day view has one), title, a `FOGG`/`CLEAR`/framework-less badge and a 28-day strength bar, and navigates (never ticks) to `/me/rutin/szokas/{habitKey}` — the per-habit recipe page, **routed since `mezo-3zue.4`** (below). Beside each row, as a **sibling** of the row button (never nested — a button-in-button), sits a per-definition `Toggle` that **pauses** that definition (`updateDef(def.id, {isActive})`); a paused def's row dims via `.row.is-inert`. Each card closes with a **„＋ Új habit"** row opening `HabitEditSheet` in create mode for that chain — so a chain with no habits today (a freshly created one included) still renders, with the affordance that lets it gain habits. **Two honest empty/error states, carried over from the editor** (`mezo-n5e9.2` fix wave): a loading `GhostState` („Rutinok betöltése…") while `isPending` with an empty catalog, and a distinct **retry** `GhostState` („Nem sikerült betölteni a rutinokat." + „Újra" → `refetch()`) when `isError` with an empty catalog — a failed fetch must never render the inviting create view; stale-but-present chains fall through to the normal view. The hero's big `{doneToday} / {totalToday}` is **suppressed entirely until the day view has resolved something real** (no confident „0 / 0", the Én tile's honesty rule). A trailing row offers **„＋ Új szokás-recept"** (→ `/me/rutin/uj`, the recipe wizard below) and **„＋ Új lánc"** (opens `ChainEditSheet` in create mode). **`?new={habitKey}`** (`mezo-3zue.4`) is the wizard's hand-back: the row whose `habitKey` matches gets the `.rt-row-new` highlight class, so a user returning from a save or a re-framing sees which line is the one they just wrote. It is a pure read of the query parameter — no state, no timer, no scroll — and an unknown key simply highlights nothing. **The 30 counter cells visualise the `perfectMorningDays30`/`perfectEveningDays30` COUNTER, not a calendar** — `HabitSummary` carries no daily bitset, so there is deliberately **no "today" cell highlight, no day-to-cell mapping, and no milestone-pill/flash**; a follow-up bd issue, **`mezo-11nm`**, tracks widening `GET /api/habit/summary` with daily bits + a `perfectStreak` field so the real grid can replace the counter-cells.
> - **Past day** (day-focused): the counter tiles and every editing affordance (Toggle/✎/SortableList/„＋" rows) disappear; a compact per-day **summary line** (`Reggel {k}/{n} · Este {k}/{n} · +{XP} XP`) sits over the same chain cards rendered as **status-only rows** — no strength bars (strength is a rolling metric, not a per-day fact). A chain with zero done items that day renders a soft note — **„{Lánc} kimaradt — a lánc másnap folytatódott. A 30 napos erő ettől nem nullázódik."** — never „megszakadt" (ADR 0010's no-failure-state tone, honored down to the copy).
> - **Empty past day:** a quiet ghost — „Nincs rutinadat erre a napra".
>
> Pure FE (no backend/API change — it just re-keys `useHabitDay(date)` on the picked day). Reads `useHabitDay(date)` (per-day statuses) + `useHabitSummary()` (strengths + perfect days, aggregate — today branch only) + `useHabitCatalog()`/`useHabitCatalogActions()` (which cards render + the CRUD mutations, today branch only). **Retroactive yesterday-logging from this page is DEFERRED** (bd `mezo-x9c2`): the past view is read-only, daily check/log stays on the Nap tab. Note the two are not the same affordance — since the daypart faces, the daily surface lets you tick **any of today's** habits from any daypart („act-anywhere"), but still only today's; this page is where other days are *viewed*.

**The chain and definition CRUD contract carried over from the retired `RoutineEditorPage` verbatim** — chain create/edit/delete/pause, def create/pause, reorder, and both ghost states are the same calls on the same sheets, restored in the `mezo-3zue.3` fix wave after the first merge dropped the def-level half. **One deliberate exception: the habit EDIT entry point.** Tapping a habit row no longer opens `HabitEditSheet` in edit mode — it **navigates to the per-habit page `/me/rutin/szokas/{habitKey}`** (`HabitPage`, routed since `mezo-3zue.4`). `HabitEditSheet` therefore survives on this page as the **create** surface only, reached from a card's „＋ Új habit" row; def **delete** now lives on `HabitPage` itself (its two-tap „Szokás törlése"), which is the app's only DELETE affordance for a definition. Where the rest renders also changed: inline on `/me/rutin`'s today cards, not a separate full-screen route.

- **`ChainEditSheet`** (`sheets/ChainEditSheet.tsx`, `{chain?, onClose}`): a title input + a three-way daypart `Chip` picker (🌅 Reggel / ☀️ Napközben / 🌙 Este). Create → `createChain({title, daypart})`; edit → `updateChain(id, {title, daypart})` (both fields ARE updatable post-creation — `HabitChainUpdateRequest` carries `title`/`daypart`/`position`/`isActive`, unlike the def side below). **Delete** is offered only for an **EDITABLE existing chain** — a non-seed (custom) chain with zero defs — mirroring the backend's own two 409 guards (`HABIT_CHAIN_SEED` checked before `HABIT_CHAIN_NOT_EMPTY`, §4); otherwise an inline explainer replaces the button („Az alap rutinok nem törölhetők." / „Csak üres rutin törölhető."). **The „Csak üres rutin törölhető" guard has a real path now** (fix wave, `mezo-n5e9.2`): `HabitEditSheet`'s per-def „Habit törlése" (below) is how a populated custom chain actually GETS to zero defs — delete every def first, then the chain's own delete button un-greys. Before the fix wave this was a dead end (no UI could empty a chain at all). **Since `mezo-3zue.3` that path runs through the per-habit page** (`/me/rutin/szokas/{habitKey}`) rather than a row-tap on the sheet — the hub itself only creates and pauses defs, and `HabitPage`'s two-tap delete (routed in `mezo-3zue.4`) is what actually empties a custom chain.
- **`HabitEditSheet`** (`sheets/HabitEditSheet.tsx`, `{chainKey, def?, onClose}`) still carries the full title/„miért"/horgony-szöveg/XP-`±`-stepper (5–15, step 5)/link-URL/skill-picker/mode-toggle/DERIVED-metric contract from the retired editor, unchanged (§4/§7 — `HabitDefUpdateRequest` still has no `skillKey` field, so mode/metric/skill stay read-only chips once a def exists). **It is no longer `/me/rutin`'s per-habit tap target** — a habit row on the page navigates to `/me/rutin/szokas/{habitKey}` instead of opening this sheet in edit mode (above); the sheet survives as the **create** surface for a **frameworkless** habit, reached from a chain card's „＋ Új habit" row (`mezo-3zue.3`). A habit built on a framework is created by the wizard instead (below) — the two create paths are deliberately separate: the sheet is the quick bare row, the wizard is the recipe.
- **Errors surface globally** — every sheet's save/delete call is a plain mutation call with no local try/catch; a rejected write (mock throws the same `HABIT_CHAIN_SEED`/`HABIT_CHAIN_NOT_EMPTY`/`HABIT_REORDER_MISMATCH`/`HABIT_DEF_UNKNOWN_CHAIN` codes real 409s would) rides the app-level `MutationCache.onError` toast (`app/providers/QueryProvider.tsx`) — no per-sheet error UI needed.
- **AI suggester — „✨ AI javaslat" (`mezo-n5e9.3`, propose-only per ADR 0019):** now a `PageHead` action on `/me/rutin` (was a page-level CTA next to „+ Új rutin" on the old editor) that opens `AiSuggestSheet` (`sheets/AiSuggestSheet.tsx`, `{chainKey?, onClose}`) via the same conditional-wrapper-object idiom as the other two sheets — **v1 is a single entry point**, always mounted with no `chainKey` preselect, though the sheet's own prop already carries a future per-chain preselect. An optional **„Szándék"** hint input (≤200 chars) + a **„Javasolj"** CTA call `useHabitAiSuggest().suggest({chainKey, hint})` (§5) — the result replaces the sheet's own **local** `cards` state, not the query cache, so a fresh run always discards the previous set. Each card renders title/why/anchor/skill/xp/target-chain chips with **„Megnyitom a varázslóban"** / **Elvetem** (drops the card locally, no server call). **Since `mezo-3zue.4` accepting no longer writes anything** — the sheet is entirely write-free. It stashes the whole `HabitSuggestion` in `sessionStorage` under **`mezo.routineWizard.suggestion`** (a query string cannot carry five prose fields legibly), closes itself, and navigates to **`/me/rutin/uj?chain={s.chainKey}`**; the wizard claims the value once on mount, deletes it in the same breath, and seeds its own fields from it. Both the write and the read sit in a `try/catch`, so a private-mode/quota/disabled store loses the proposal but never the navigation — the wizard simply opens on the right chain, unseeded. **Why route it through the wizard:** ADR 0019 makes the suggester propose-only, and this way every accepted proposal also acquires a framework and passes the wizard's own „Vállalom" tick — the human confirmation the ADR requires — instead of becoming a habit on one tap. There is deliberately **no second confirmation** in the sheet; the wizard is the confirmation. A card the user accepted is left in the list rather than removed, because the sheet unmounts with the navigation anyway. **Unavailable** (real-mode 503 suggester-off / 404 whole-surface-off, mapped by the hook itself — §5) renders an honest inline card instead of the form; a resolved-but-empty result renders a quiet one-line ghost rather than implying a failure.

#### `/me/rutin/uj` — the recipe wizard (`RoutineWizardPage`, `mezo-3zue.4`)

Four steps that build **one** habit recipe on **one of two frameworks**. A `MozaikPage tone="gold"` with a `Stepper`, a back chip that walks the steps backwards (and leaves to `/me/rutin` from step 1) and a „Mégse" head action. **The page never ticks a habit** (ADR — ticking lives on `/nap/rutin`) and never creates a DERIVED definition: every recipe is `mode: 'MANUAL'`.

1. **„Milyen keretre építsük?"** — the two framework cards. **⚓ Szokás-láncolás** (BJ Fogg · Tiny Habits — *horgony → pici tett → ünneplés*) or **◈ Négy törvény** (James Clear · Atomic Habits — *jelzés → vágy → válasz → jutalom*), with a tip nudging an undecided user towards Fogg. Nothing else is reachable until one is picked; switching the framework later **drops the commitment tick** (step 4), because the tick is a promise about a sentence the user has read, not a setting.
2. **The framework's opening slot** — FOGG: „Mihez horgonyzod?", a chip row of `habitAnchorOptions(catalog)` (each chip resolving to a real sibling `habitKey`) plus a free-text field (typing clears the resolved key, so the payload is `anchorCopy`, never both). CLEAR: „Mi a jelzés?", chip presets + free text.
3. **The behaviour** — the title field, labelled „pici tett" on Fogg and „válasz" on Clear; on Clear also *vágy* (required) and the optional *identitás*. Then the chain chips, the LIFE-skill grid and the 5–15 XP stepper. A soft, non-blocking warning („Ez nagynak hangzik") appears when a Fogg behaviour runs over six words or names a number above five.
4. **The reward** — FOGG: *ünneplés* („shine"); CLEAR: *jutalom*, defaulting to „a pipa maga" because the log itself is the fourth law's satisfaction. Then the **„Vállalom"** tick, which gates „✓ Mentés".

**The live sentence card is the thesis of the page.** From step 2 on it renders through `routineSentenceParts` — the same pure renderer the habit page uses (§6) — so the wizard and the finished recipe can never drift, each unfilled slot showing its Hungarian placeholder until the user's own words replace it.

**The two payload recipes** (both enforced by `HabitFrameworkValidator`, §4): a **FOGG** save sends `framework: 'FOGG'` plus **either** `anchorHabitKey` **or** `anchorCopy` — never both — plus `celebration`. A **CLEAR** save sends `framework: 'CLEAR'` plus `cue`, `craving`, `reward`, and `identity` only when the user wrote one (an emptied optional key is *omitted*, never sent as `''` — the PATCH ignores a JSON null, so omission is the only honest way to say „unchanged"). Neither recipe sends the other's fields; the backend's `clearForeignFields` nulls whatever the chosen framework does not own.

**Two entrances, two terminal actions.**

- **`?chain={chainKey}`** preselects the chain (used by the AI hand-off above), and `sessionStorage['mezo.routineWizard.suggestion']` seeds title/framework/anchor/cue/craving/reward/celebration/skill/XP from an accepted suggestion. The stash is read **once on mount and removed immediately**, inside a `try/catch`, so a reload cannot resurrect a stale proposal and a broken store cannot break the page. A suggestion never carries an `identity` — that clause is the user's own sentence about who they are becoming.
- **`?prefill={habitKey}`** re-opens an **existing** definition (the habit page's „Keret váltása"/„Keret választása" button). The seed runs in an effect, exactly once, because the catalog may still be resolving on first render — and a re-render must never stomp an edit in progress. **Prefill outranks the stashed suggestion for every field both could fill:** a user who came from „Keret váltása" is editing one specific habit, not accepting a proposal. A `?prefill` key the catalog does not have **falls back to create mode** rather than erroring — the catalog may simply not have resolved.
- **Prefill never skips step 1**: re-framing is exactly the decision the user came to make.
- **With a resolved `prefillDef` the terminal action is `updateDef(def.id, patch)`, not `createDef`** (`mezo-3zue.4`). This is the whole point of „Keret váltása": re-framing **converts** the habit, it does not mint a second one. The patch carries `title`, a clamped `xp`, `framework` and the framework's own fields — **no `mode` and no `skillKey`** (`HabitDefUpdateRequest` has neither) — and `chainKey` **only when the user actually moved the habit**, because the backend reads a bare `chainKey` as a MOVE and, with no `position`, appends the def to the end of the target chain (the same guard `HabitPage`'s save carries).
- Both paths then navigate to **`/me/rutin?new={habitKey}`** — the created def's key from `createDef`'s resolved value, or the converted def's own key — so the hub highlights the row. `useHabitCatalogActions().createDef` resolves with the created `HabitDefInfo` in **both** modes for exactly this reason (the mock arm returns the def it inserted); every other caller ignores the value.

#### `/me/rutin/szokas/:habitKey` — the recipe page (`HabitPage`, `mezo-3zue.4`)

**ONE habit's definition**, reached from a hub row. Route resolution is by `habitKey`, but every write goes through the definition's `id`. A framework band (⚓ / ◈ / „– Keret nélkül" for a legacy def) with a **„Keret váltása"** — „Keret választása" on a frameworkless one — button into `/me/rutin/uj?prefill={habitKey}`; the finished sentence through the same `routineSentenceParts`; a 28-day history strip (a *proportion* strip off the summary's `done28`/`missed28`, not a calendar — the caption says so); the framework's own editable fields; the chain chips and XP stepper; and the two ways out of a habit — **pausing** (prominent, and it promises the strength history survives) and **deleting** (quiet, two taps, the app's only def-DELETE affordance). A chip-linked anchor renders **read-only** with an explainer pointing at „Keret váltása", because the API has no unlink. **No tick control anywhere on this page** — every control here edits the DEFINITION. A deep link that lands before the catalog resolves waits on a ghost; only a *resolved* catalog with no such key redirects to `/me/rutin`.

## 3. Architecture & data flow

The domain is the **`QuestService` mirror**: a static catalog → one per-day table → a pure-read evaluator → the shared progression award tail.

```
NapHubPage (the Rutin tile) / NapRutinPage (the chains) / RutinHubPage (Én — overview + build/edit)
  → useHabitDay(date) / useHabitActions(date) / useHabitSummary()   (@/data/hooks)
      mock: habitMock seed (+ awardGamificationEvent on check)
      real: habitApi → GET /api/habit/day/{date} | POST/DELETE /api/habit/{key}/check | GET /api/habit/summary
              → HabitController → HabitService
                    ├─ getDay: lazy row-per-catalog-entry (today only) → closePast → evaluateIntraday
                    ├─ check/uncheck: MANUAL, today only
                    └─ summary: 28d strength + 30d perfect days
              → HabitCatalogService → habit_chain / habit_def (lazy seed bootstrap, mezo-n5e9.1)
              → HabitEvaluator (pure reads: sleep/weight/intake/train/meal/goal)
              → ProgressionService.applyHabit / revertHabit  (source_type = HABIT)
              → habit_day (Postgres)
```

- **Lazy per-user catalog bootstrap** (`HabitCatalogService.ensureCatalog`, `mezo-n5e9.1`, ADR [0019](../decisions/0019-user-editable-habit-catalog-propose-only-ai.md)): the catalog is no longer static JSON read at request time. `HabitCatalog` is now only the fail-fast-validated **seed** source; the first catalog-touching call for a user — `getDay`, `check`/`uncheck`, or any of the admin endpoints (§4) — imports the two seed chains + any seed def the user has never had into `habit_chain`/`habit_def`, race-guarded the same way as `ensureRows` below. A def the user has soft-deleted is **never** reimported: `HabitDefRepository.findAllKeysEver` is a single deleted-inclusive native probe that tells "never had it" apart from "deleted it", with no short-circuit — a future seed-JSON addition still imports for existing users. The nightly `HabitJob`'s `closePast` deliberately does **not** trigger this bootstrap for a user with zero stale `habit_day` rows, so a dormant account accrues no writes. **`summary` is deliberately NOT a bootstrap point** (`@Transactional(readOnly = true)`, mezo-n5e9.1 review finding 3): it's read on every companion chat turn (`ContextSnapshotAssembler`/`PracticeTools`), so materializing 17 rows there would write a catalog for every dormant account on every chat message; a user with no catalog gets an honest empty summary instead, and `getDay` is the real bootstrap point. The routine editor (backend + editor UI since `mezo-n5e9.2`, §2/§4; the **AI suggester since `mezo-n5e9.3`** — §5's Companion seam, spec [2026-08-05-routine-editor-design.md](../superpowers/specs/2026-08-05-routine-editor-design.md)) is the write side over this same catalog — the suggester itself never writes (ADR 0019): an accepted suggestion rides the exact same `createDef` call as a hand-typed habit.
- **Lazy day materialization** (`HabitService.getDay`/`ensureRows`): the first **today** read inserts one `pending` `habit_day` row per catalog entry, guarded against the cron race by the **partial-unique index** + a `DataIntegrityViolationException` catch that re-reads the winner's rows. A non-today read never creates rows (past days are read as-is). `ensureRows` **reconciles**, not just first-materializes (mezo-n5e9.1 review finding 1 — critical): it inserts a row for every active def with none yet for the date, not only when the day has zero rows, so a def created through the admin API *after* today already materialized still gets a row on the next touch — the gap used to 500 `check()` (a bare `.orElseThrow()` on a never-created row) for exactly that sequence.
- **Three evaluation-closure classes** (spec [D7](../superpowers/specs/2026-07-19-morning-evening-routine-habit-engine-design.md), the metric sets live in `HabitEvaluator`):
  - **INTRADAY** (`INTRADAY_METRICS` — M1 `sleep_wake_window`, M3 `weight_logged_today`, M4 `stim_intake_today`, M5 `training_done_today`, M6 `breakfast_protein`, + the two intention metrics `intention_focus_set` / `intention_reflected` (`mezo-a686`); MANUAL M2/E3 nominally here but skipped): re-evaluated on **every today-read** (`evaluateIntraday`); a `pending → done` transition on this read carries its level-up out on the response. **Since `mezo-u6jx` M3/M4 and M5's run branch are date-presence** — a live log for the date is enough, no wall-clock compare against the log's own `created_at`/`taken_at` (the retired `weigh-in-cutoff`/`morning-window-end`/`workout-window-hours`); see the [honest-derivation fix spec](../superpowers/specs/2026-08-05-habit-honest-derivation-fix-design.md).
  - **END_OF_DAY** (`END_OF_DAY_METRICS` — E1 `no_stim_after`, E2 `last_meal_before`): decidable only once the day is over, so they stay `pending` during the day and close on the **nightly `HabitJob`** or the next-day read (`closePast → closeByEvaluation`).
  - **BED_NEXT_DAY** (`METRIC_BED_NEXT_DAY` = E4 `bedtime_next_day`): completes on the read/close that first sees **the next morning's** sleep log; if the **next-day-noon** deadline passes first (`today.isAfter(habitDate+1) || now > 12:00`), it closes quietly `missed`.
- **`closePast`** (called by both the today-read and the cron) flips every stale `pending` row: END_OF_DAY/intraday metrics get one last honest evaluation, E4 gets the deadline logic, unknown/stale catalog keys close quietly `missed`.
- **Completion** (`complete`) stamps `done_at`/`xp_awarded`/`source`, saves, then — when the `ProgressionGate` is available (`ObjectProvider`) — calls `ProgressionService.applyHabit` (idempotent per `habit_day.id`), passing the row's own `habit_date` as the award's business date (`HabitSignal.occurredOn`, `mezo-huzd` — the same row-borne-date convention QUEST/ACTIVITY signals use for the `level_up_event.occurred_on` column). Since checks are today-only (`requireManualToday`, below) this coincides with the grant instant in v1 — no observable behavior change, just plumbing consistency for whenever a source gains backdating. Award amounts are the catalog XP (deterministic, ADR 0010).
- **Manual path:** `check` flips a MANUAL `pending → done` (today only) and awards; `uncheck` (same-day, MANUAL, `done`) reverts via `revertHabit` — it **soft-deletes** the `level_up_event` and **directly decrements** the skill row (the `moveActivityXp` precedent, no new event), so a re-check can cleanly re-award.
- **Read-triggered heartbeat:** the FE day read runs `staleTime: 0` in real mode (`useHabitDay`) so the server re-evaluates derived completion on every mount/focus — the READ *is* the evaluation trigger, mirroring `useDailyQuests`. Because the READ is the *only* trigger, **every write that can satisfy a DERIVED metric must invalidate `['habitDay']`** so the row re-derives without waiting for a remount. The weight/sleep/meal/gym/run log mutations do this (`mezo-pquo` — they previously did not, so a fresh log left the `✓` stale until the surface remounted), alongside the intention/ritual/sleep-goal/fuel-settings paths that already did; **since `mezo-u6jx` the supplement-intake log/undo (`useStackActions`, [fuel.md](fuel.md) §5) joins the fan-out too** — a stim intake can satisfy `stim_intake_today` (M4) or affect `no_stim_after` (E1), so it invalidates `['habitDay']` on every log/undo. The same log mutations also nudge `['dailyQuests', date]` for the twin quest metrics (`weight_logged`, `sleep_target`, `protein_target`/`own_recipe_meal`, `gym_session_done`).

Identity: **partial unique** `uq_habit_day_user_date_key (created_by, habit_date, habit_key) where is_deleted = false` (+ `idx_habit_day_user_date`). The **same migration** relaxes the released `level_up_event.source_type` CHECK additively: `+= HABIT`.

**Schema change #2 — `level_up_event` partial-unique** (migration [`202607192130_mezo-d1jb_level_up_event_partial_unique.sql`](../../backend/src/main/resources/db/changelog/1.0.0/script/202607192130_mezo-d1jb_level_up_event_partial_unique.sql)): the habit **un-check** is the **first** source to soft-delete a `level_up_event` and later re-award with the same `(created_by, source_type, source_ref_id)`. The original plain unique constraint spanned soft-deleted rows, so the re-insert would collide — this converts it to the house-standard **partial unique** index (`where is_deleted = false`): one *live* award per source ref, soft-deleted rows ignored. GYM/RUN/SPORT/QUEST/ACTIVITY keep identical live-row idempotency.

**Catalog storage — DB-backed since `mezo-n5e9.1`** (ADR [0019](../decisions/0019-user-editable-habit-catalog-propose-only-ai.md), spec [2026-08-05-routine-editor-design.md](../superpowers/specs/2026-08-05-routine-editor-design.md)): two new per-user tables replace "the catalog is a fixed JSON file".

- **`habit_chain`** (migration [`202608051400_mezo-n5e9.1_create_habit_chain.sql`](../../backend/src/main/resources/db/changelog/1.0.0/script/202608051400_mezo-n5e9.1_create_habit_chain.sql)): `id uuid pk`, `created_by` (FK → `app_user`, cascade), `is_deleted`/`created_at`, `chain_key varchar(40)`, `title varchar(80)`, `daypart varchar(8)` (`ck_` `MORNING|DAY|EVENING` — **since `mezo-n5e9.2` read on the FE**: `todayItems.ts` buckets every habit onto its face by its owning chain's `daypart`/`title`, sourced live from `useHabitCatalog()`, not a hardcoded map), `position int`, `is_active bool`. Partial-unique `(created_by, chain_key) where is_deleted = false`.
- **`habit_def`** (migration [`202608051410_mezo-n5e9.1_create_habit_def.sql`](../../backend/src/main/resources/db/changelog/1.0.0/script/202608051410_mezo-n5e9.1_create_habit_def.sql)): `id uuid pk`, `created_by` (FK cascade), `is_deleted`/`created_at`, `habit_key varchar(40)`, `chain_id uuid` (FK → `habit_chain`), `position int`, `title varchar(80)`, `why text`, `anchor_copy varchar(120)`, `mode varchar(7)` (`ck_` `DERIVED|MANUAL`), `metric varchar(40)`, `skill_key varchar(40)`, `skill_kind varchar(4)` (`ck_` = `LIFE`), `xp int` (`ck_` 5–15), `link_url text`, `is_active bool`. Partial-unique `(created_by, habit_key) where is_deleted = false`.

**Schema change #3 — the routine-builder framework columns (`mezo-3zue.2`, migration [`202609021100_mezo-3zue.2_habit_def_framework.sql`](../../backend/src/main/resources/db/changelog/1.0.0/script/202609021100_mezo-3zue.2_habit_def_framework.sql)):** `habit_def` gains seven **all-nullable** columns so a habit can optionally be built as a full behaviour-change recipe on one of two frameworks — Fogg's Tiny Habits or Clear's Four Laws — instead of a bare title/why/xp row. `framework varchar(5)` (`ck_habit_def_framework`: `null` or `FOGG`/`CLEAR`) is the discriminator; `anchor_habit_key varchar(40)` (indexed — `idx_habit_def_user_anchor (created_by, anchor_habit_key)`) is FOGG's optional stacked-anchor reference (a sibling def's `habit_key`, in preference to the free-text `anchor_copy`); `cue varchar(160)`, `craving varchar(200)`, `reward varchar(160)` are CLEAR's 1st/2nd/4th-law fields; `celebration varchar(120)` is FOGG's immediate "shine"; `identity varchar(120)` is CLEAR's optional identity sentence (the only field with no framework-side requirement). Per-framework field sets are enforced in code, not in SQL, by `HabitFrameworkValidator` (`service/HabitFrameworkValidator.java`, `mezo-3zue.2`) — called from `HabitAdminService` after every create/update merge:
  - `framework == null` (the legacy/no-recipe case): **all seven fields must be blank**, or the write 400s `HABIT_FRAMEWORK_FIELDS_ORPHAN` — a half-filled recipe can never hide behind a null framework.
  - `framework == "FOGG"`: needs an anchor (`anchorHabitKey` OR the pre-existing `anchorCopy`) **and** `celebration`, or 400s `HABIT_FRAMEWORK_FOGG_INCOMPLETE`. When `anchorHabitKey` is set it must resolve to a **different**, **active**, **owned** def (`HabitDefRepository.findByCreatedByAndHabitKeyAndDeletedFalse`) or 400s `HABIT_ANCHOR_INVALID`; a free-text-only anchor (`anchorCopy` set, `anchorHabitKey` blank) skips that check entirely.
  - `framework == "CLEAR"`: needs `cue`, `craving` **and** `reward` (identity stays optional), or 400s `HABIT_FRAMEWORK_CLEAR_INCOMPLETE`.
  - `HabitFrameworkValidator.clearForeignFields` runs before validation on every create and update: switching a def from CLEAR to FOGG nulls `cue`/`craving`/`reward`/`identity` (and vice versa nulls `anchorHabitKey`/`celebration`) so a re-framed recipe can never keep a stale field the new framework doesn't own and the sentence renderer would otherwise print.
  - Deleting or deactivating a stacked anchor **releases** its dependents rather than cascading or dangling them (`HabitAdminService.releaseAnchors`, called from both `deleteDef` and `updateDef` when `isActive` flips to `false`): every dependent def's `anchorHabitKey` is nulled, and if its `anchorCopy` was blank it is backfilled with `"kész a " + anchor title` so the FOGG sentence still reads — a demotion to free text, never data loss.
  - The `HabitDefAdmin`/`HabitDefCreateRequest`/`HabitDefUpdateRequest` contract shapes all carry the same seven optional fields (`api/feature/habit/habit.yml`, contract 0.6.0) — `framework: enum[FOGG,CLEAR] nullable`, the rest `string nullable` at their column's `maxLength`.

`content/habit-catalog.json` + the fail-fast `HabitCatalog` loader survive only as the **seed source** (the `QuestCatalog`-pattern loader, unchanged as a loader): **15 `HabitDef`s** (9 MORNING + 6 EVENING — the base 6+4, plus the two `mezo-a686` intention habits: `daily_intention` MORNING pos 9 / `intention_reflect` EVENING pos 3, plus the two habits inserted right after morning sunlight: `morning_pushups` MORNING pos 3 (MANUAL, `mindset`, 10 XP) / `morning_video` MORNING pos 4 (MANUAL, `learning`, 5 XP, carrying a `linkUrl`), plus `evening_ritual` „Napzárás" EVENING pos 4 (DERIVED, `mindset`, 10 XP, metric `ritual_closed` — satisfied by a live row in the [ritual domain](../superpowers/specs/2026-07-24-daily-closing-ritual-design.md)'s `ritual_day` table), all DERIVED unless noted). Each seed row carries `key`, `chain`, `position` (stacking order — EVENING runs `caffeine_cutoff` 1 · `kitchen_close` 2 · `intention_reflect` 3 · `evening_ritual` 4 · `wind_down` 5 · `bed_on_time` 6), `title`/`why`/`anchorCopy` (all HU), `mode` (DERIVED|MANUAL), `metric`, `skillKey` (a LIFE skill), `skillKind` (`LIFE`), `xp` (5–15), and an **optional `linkUrl`**. `HabitCatalogService` (`service/HabitCatalogService.java`) lazily imports these seed rows — plus any new one added to the JSON later — into `habit_chain`/`habit_def` on a user's first catalog touch; a def the user has soft-deleted is never reimported (`HabitDefRepository.findAllKeysEver`, a single deleted-inclusive native probe). **The loader's old fail-fast invariants (chain/mode membership, `skillKind == LIFE`, `5 ≤ xp ≤ 15`, MANUAL ⇔ `metric == "manual"`) now double as write-time validation** in `HabitAdminService` — a startup-only check would no longer catch a bad row created through the editor API. See the habit spec §3 for the base 15-row seed table (still accurate as seed content) + [intention.md §2](intention.md) for the two intention rows.

Errors go through `SystemRuntimeErrorException` + `SystemMessage` per [`error_handling.md`](../references/error_handling.md).

`HabitChainAdmin{id, chainKey, title, daypart, position, isActive, defs[HabitDefAdmin]}`; `HabitDefAdmin{id, habitKey, chainKey, position, title, why?, anchorCopy?, mode, metric, skillKey, xp, linkUrl?, isActive}`. Custom keys are server-generated (`custom_<8-hex>` / `chain_<8-hex>`, `HabitAdminService.generateKey`) — never client-chosen. **Mode/metric are fixed at creation** (`updateHabitDef` cannot change either); a DERIVED def's metric must be one of `HabitEvaluator.SUPPORTED_METRICS` (the union of `INTRADAY_METRICS`/`END_OF_DAY_METRICS`/`METRIC_BED_NEXT_DAY`, §3) or the write 400s `HABIT_METRIC_UNKNOWN`; a MANUAL def's metric is always forced to `"manual"` server-side, and a DERIVED def requesting `"manual"` 400s `HABIT_MODE_METRIC_MISMATCH`. Moving a def across chains (`updateHabitDef` with a new `chainKey`) reads the target chain's live-def count *before* reassigning `chainId` to avoid a JPA auto-flush off-by-one, so a move to an empty chain lands at position 1, not 2. A chain with live defs, or either seed chain (`MORNING`/`EVENING`), rejects `deleteHabitChain`.

`HabitSuggestRequest{chainKey?, hint?}` (`mezo-n5e9.3`) — both optional: `chainKey` ≤40 chars (matches the `chain_key` column width; an unknown/stale value is silently **omitted** from the LLM grounding context rather than rejected, §5), `hint` ≤200 chars (the free-text „szándék"). `HabitSuggestion{title, why, anchorCopy, skillKey, xp, chainKey}` (xp 5–15) carries no `id`/`habitKey` — a suggestion is not yet a resource; accepting one is an ordinary `POST /api/habit/def` call. **Since `mezo-3zue.2` it also carries the same five framework fields as a def** — `framework?: enum[FOGG,CLEAR]`, `cue?`, `craving?`, `reward?`, `celebration?` — all **optional and NOT in the schema's `required` list**, so a model response that omits all five still parses into a valid suggestion (§5).

**FE types** (`data/types.ts`): `HabitChain`/`HabitMode`/`HabitStatus`, `HabitItem`, `HabitStrengthRow`, `HabitSummary`; **`HabitSuggestion`** (`mezo-n5e9.3`) alongside `HabitChainInfo`/`HabitDefInfo`/`HabitCatalog`/`HabitDaypart`. Wire↔domain mapping in `data/habit/habitApi.ts` (day/summary) and `data/habit/habitAdminApi.ts` (catalog CRUD + `suggest()`) off `api.gen.ts`.

## 5. Integrations

All inbound edges are **pure reads** — habit depends on {biometrics, meal, fuel, train, goal, intention, ritual, progression}; none of those eight depend back on habit. **Companion is a separate, ONE-DIRECTIONAL dependent** (companion → habit — the pre-existing `ContextSnapshotAssembler`/`PracticeTools` reads, plus the `HabitSuggestLlmAdapter` suggest seam below): habit itself never imports `feature.companion`, so this is not a cycle (`feature_slices_are_cycle_free` holds).

- **← Biometrics** (`HabitEvaluator`): M1 `sleep_wake_window` and E4 `bedtime_next_day` from `SleepLogRepository` (wakeup / next-day bedtime vs the goal anchor ± window); M3 `weight_logged_today` from `WeightLogRepository` — **since `mezo-u6jx`** a live weight log existing for the date (date-presence; the `weigh-in-cutoff` wall-clock compare against `created_at` is retired).
- **← Fuel** (`HabitEvaluator`): M6 `breakfast_protein` = Σ protein of today's `breakfast`-slot meals via `FuelDayService.getDay` ≥ `protein-target-g`; E2 `last_meal_before` = last `meal` `logged_at` ≤ `kitchenClose`; M4 `stim_intake_today` / E1 `no_stim_after` join `SupplementIntakeRepository` to **stim-kind** `PantryItemRepository` items — **since `mezo-u6jx` M4 is date-presence** (any stim-kind intake logged for the date satisfies it, no window compare), while **E1 stays wall-clock** (unchanged; still compares each intake's `taken_at` against the resolved cutoff — see the accepted retro-log residual in §9). **Since `mezo-53su` (spec D3) the caffeine cutoff E1 compares against comes from Fuel's ungated `CaffeineCutoffPort`** (`feature/fuel/service`, `LocalTime resolve(UUID)`) — `HabitEvaluator` injects the port and calls `caffeineCutoffPort.resolve(userId)` instead of reading `HabitProperties.caffeineCutoff`; that property + its `mezo.habit.caffeine-cutoff` yml key were **removed**. The resolver is deliberately **not** switch-gated (the habit metric must resolve even with the fuel-settings surface off — the `SleepAnchorPort` idiom), ghosting the config default `"14:00"` when no `fuel_settings` row exists. See [fuel.md](fuel.md) §4/§5.
- **← Train** (`HabitEvaluator`): M5 `training_done_today` = a finished gym session (`WorkoutSessionRepository.findDoneInstanceDates`) **or** a run logged today (`RunSessionLogRepository`) — **since `mezo-u6jx` the run branch is date-presence too**, unifying with the gym half's own date-presence fallback (§9); the wake-anchored cutoff is retired (see `← Sleep goal`).
- **← Intention** (`HabitEvaluator`, `mezo-a686`): the two intention habits complete off `IntentionFocusRepository` (`intention_focus_set` = today has ≥ 1 live focus) and `DailyIntentionRepository` (`intention_reflected` = today's reflection set) — both plain JPA beans injected directly (the cross-feature-read precedent). The `daily_intention`/`intention_reflect` rows open `IntentionSheet`/`ReflectSheet` (the honest log surface) — dispatched by `NapRutinPage`'s `tickAction`, the `TodayPage.act()` successor. (The Nap hub's own **Kreed** tile is a third, independent `IntentionSheet` entry point.) One-directional (habit → intention). See [intention.md](intention.md).
- **← Ritual** (`HabitEvaluator`, `mezo-hvmx`): the `evening_ritual` row's `ritual_closed` metric is a single check against `RitualDayRepository.findByCreatedByAndRitualDateAndClosedAtIsNotNull` — a live `ritual_day` row **with a `closed_at`** means the Napzárás close happened. (**`mezo-b3pp.2`:** it used to be a plain existence check, but a `ritual_day` row can now be born from the evening reflection alone, before the close — prose typed must never complete the habit.) It sits in `INTRADAY_METRICS` (re-evaluated on every today-read). The ritual endpoints award no XP themselves; completion rides the habit's own catalog XP through the existing HABIT tail. One-directional (habit → ritual) — the ritual domain does not read habit. See the [ritual design spec](../superpowers/specs/2026-07-24-daily-closing-ritual-design.md).
- **← Sleep goal** (`HabitTargets`, `mezo-dbsr`, spec D3): the wake/bed anchors now come from the **sleep goal** through the shared **`SleepAnchorPort`** — `HabitTargets` is a thin adapter over it (`HabitTargets.java:17-24`), no longer a `GoalRepository` + `HabitProperties.defaultWake`/`defaultBed` reader (those config keys are **removed**). The port ghosts config defaults when no sleep-goal row exists (the no-goal default **bed shifted 23:00 → 22:00**). The M1 `sleep_wake_window` / E4 `bedtime_next_day` checks re-centre on the sleep goal's anchor but **keep their 45-min tolerance window** (`mezo.habit.wake-window-min`) — the strict ±15 band is only the sleep-goal regularity *score*, not the habit gate. `kitchenClose = bedTime − kitchen-close-offset-min (90′)`. **Since `mezo-67rb` the M5 `training_done_today` run-branch cutoff was wake-anchored** (`SleepAnchorPort` wake `+ mezo.habit.workout-window-hours`, default 6 — a ghost wake 06:00 reproduced the retired static 12:00); **`mezo-u6jx` retires it** — the run branch is date-presence too now (any run dated today counts, unifying with the gym half), so `HabitProperties.workoutWindowHours` + the `workout-window-hours` yml key are **removed** (see §9 D6). The gym half stays date-presence (spec §3).
- **→ Progression** (`ProgressionService.applyHabit` / `revertHabit`, source `HABIT`): completion rides the shared idempotent `award(...)` tail (`source_type=HABIT`, `source_ref_id=habit_day.id`) onto the habit's **LIFE** skill; un-check reverts by soft-deleting the event + decrementing the skill row directly (§4 schema change #2). The CHECK was relaxed additively. Discipline trait and the Growth journal do **not** consume habit signals in v1 (deliberate — wireable later).
- **→ Nap / Growth surfaces:** the Nap hub's Rutin tile + `/nap/rutin`, and the Rutin tab (`/me/growth`), as in §2. **The morning island's promoted chain CTA is gone** — it died two render layers ago (`mezo-puci`) and nothing replaced it; the first open step is an ordinary row. The account XP / ⚡ chrome stays **quest-only** and is no longer on the daily surface at all (`AppHero` was deleted with the Design 2.0 shell) — habits never fed it anyway.
- **→ The evening winddown ghost is RETIRED (the `wind_down` habit's former SECOND surface, sleep slice C-éj `mezo-d71m`; relocated by `mezo-euze`, deleted by `mezo-d20.9.1`).** For four render layers the evening *leállás* phase (`[bed−60, bed)`) rendered the `wind_down` MANUAL habit as a `Leállás megvolt ✓` ghost check over the **same `['habitDay', date]` cache** as its list row, with its own `buildHabitRewardToast` call. `DaypartEvening` and `useWindDownPhase` are gone, so that surface is gone: `wind_down` is now offered exactly once, as a row on `/nap/rutin`. **No habit-domain change either way** — the ghost was only ever a second consumer of the existing hooks, never a metric or a catalog row. Its disappearance also retires the two-controls-at-once hazard the mock arm's non-idempotence made real (below).
- **↔ Account progression / `AppHero` (mock-mode side-effect):** in **mock mode** `useHabitActions.check` also calls `awardGamificationEvent(qc, {type:'HABIT', xpOverride})` (`data/habit/habitHooks.ts:58`) so the `AppHero` account XP/streak/coin ledger moves in an offline demo — the tenth call site of the mock account-XP precedent (see [growth.md §2](growth.md), "Account progression"). `HABIT` is registered in `gamificationTypes.XpEventType` + `xpValues` (`XP_VALUES.HABIT = 0`, `DAILY_CAPS.HABIT = 10` — the amount comes from the habit's own `xpOverride`). **Real mode never calls it** (account XP is derived from the profile there). **The mock arm is NOT idempotent** (`mezo-mvb4.1`, asserted in `habitHooks.test.tsx`): it awards on every `check()` without asking whether the row is already `done`, and one habit is nowhere near the `HABIT` cap of 10 — so two taps of the *same* habit award twice. Real mode cannot: `HabitService.check` rejects an already-done row with `HABIT_ALREADY_DONE`. The only mock-mode guard is the in-flight `pending` withdrawal, and that guards **only the control it belongs to** — which is why a habit must never be offered by two controls at once. The historical offender (the Este `wind_down` ghost + its row) is gone with the ghost, and `/nap/rutin`'s `pending` guard is page-wide, so today there is no habit with two tick controls; keep it that way. Two DERIVED habits DO move mock account-XP through their owning surface's mutation (`mezo-o5hx`): the mock `reflect()` (intention) and the mock ritual `close()` both call **`completeMockDerivedHabit(qc, date, key)`** (`data/habit/habitHooks.ts` — the mock mirror of a server-side derived completion; it flips the row in the `['habitDay', date]` cache, seeding the day from the mock seed if unmounted, and returns whether it flipped so the caller can gate a one-time award). Other DERIVED rows still carry no mock completion path.
- **→ Companion (AI suggester, `mezo-n5e9.3`, ADR [0019](../decisions/0019-user-editable-habit-catalog-propose-only-ai.md)):** `HabitSuggestPort` (`service/HabitSuggestPort.java`) is a **habit-owned** port — `suggest(userId, chainKey, hint) → List<Suggestion>` — reached from `HabitAiService` through `ObjectProvider<HabitSuggestPort>` (empty ⇒ a clean 503 `HABIT_AI_UNAVAILABLE`, never a 500). Habit itself still never imports `feature.companion` (ADR 0012's slice-cycle rule stays closed); the one bean that implements the port, `HabitSuggestLlmAdapter`, lives in `feature/companion/llm/` and imports `HabitCatalogService`/`HabitChainEntity`/`HabitDefEntity` directly — i.e. the dependency runs **companion → habit**, the same pre-existing direction `ContextSnapshotAssembler`/`PracticeTools` already established (companion.md), so `ArchUnit`'s `feature_slices_are_cycle_free` needed no new tolerance. The adapter is gated on a three-way `@ConditionalOnProperty` array (`HABIT_AI_SUGGEST_SWITCH` + `COMPANION_SWITCH` + `HABIT_SWITCH` — the `SlotPlanLlmAdapter`/`StackPlacementLlmAdapter` idiom extended by one switch): any one off ⇒ no adapter bean ⇒ the 503 path above. **Propose-only** (ADR 0019): the model only ever returns suggestions — nothing on this path writes a `habit_def` row; an accepted suggestion rides the ordinary `createDef` call (§2/§4). Every suggestion is grounded in and strictly filtered against the caller's OWN data (LIFE skills with real cumulative XP, live chain keys, xp clamped to 5–15) before `HabitAiService.sanitize` re-checks the same bounds as a second defensive layer — a hallucinated skill/chain/xp can never reach the client. The adapter's `CompanionLlm.completeSmart` call (ADR 0008's Pro tier) is tagged `LlmCallContext("habit_ai_suggest", "propose", null, null)` for the `llm_log_history` audit (see [companion.md](companion.md), "LLM call audit log"). **Since `mezo-3zue.2` a suggestion may propose a full framework recipe, not just a bare habit:** the system prompt instructs the model to pick FOGG (fill `anchorCopy` + `celebration`) or CLEAR (fill `cue` + `craving` + `reward`) and always set `framework`; the adapter's own `HabitSuggestPort.Suggestion` record grew the same five fields, parsed by the existing bracket-substring-extract + Jackson `TypeReference<List<Suggestion>>` path unchanged (Jackson leaves an omitted field `null` on the record, so a legacy-shaped or framework-less model response still parses). `HabitAiService.sanitize` copies all five through into the `HabitSuggestion` DTO field-by-field, mapping the raw `framework` string through `FrameworkEnum.fromValue` (an unrecognized value degrades to `null`, not a 5xx — the same propose-only defensive tone as the rest of the method). **This adapter still never writes a `habit_def` row** — a suggested recipe reaches the catalog only through the normal `createDef` call, which is where `HabitFrameworkValidator` (§4) does its real enforcement; the suggester's own framework fields are advisory, not validated at propose time.

## 6. How to use it (consume)

```ts
import { useHabitDay, useHabitActions, useHabitSummary } from '@/data/hooks'

const { habits, levelUps, mode } = useHabitDay(date)      // date = 'YYYY-MM-DD'; habits: HabitItem[]
const { check, uncheck, pending, consumeLevelUps } = useHabitActions(date)
const { data: summary } = useHabitSummary()               // { perfectMorningDays30, perfectEveningDays30, habits[] }

await check('morning_sunlight')                            // MANUAL only → resolves the write's levelUps
```

- `useHabitDay` is a **manual dual-mode** shape (like `useDailyQuests`, not `useDualQuery`): real mode runs `staleTime: 0` and returns the **empty day** (never the seed) while unresolved. `levelUps` is non-empty only on the read that performed the completion — build a reward toast from `levelUps[0]` (`buildHabitRewardToast`) and emit it, then call `consumeLevelUps()`. **Nobody currently does this on the daily surface** — `TodayPage`'s consume-once effect went out with the page and `NapRutinPage` did not inherit it; the only live caller is `RitualPage`, which drains and *drops* them on purpose (§2/§9).
- `check(key)` resolves the write's `levelUps` array; the caller feeds `lu?.[0]` into its own `buildHabitRewardToast` call (`NapRutinPage`'s `tickAction`, the `TodayPage.act()` successor).
- Ghost-guard: `habits.length === 0` → contribute no rows (the hub renders no Rutin tile and `/nap/rutin` renders no group). Never import `habitApi`/`habitMock` directly — go through `@/data/hooks`.
- Query keys: `['habitDay', date]`, `['habitSummary']`; a real-mode write invalidates both + `['progressionProfile']`.

**The catalog itself — read + CRUD (`mezo-n5e9.2`):**

```ts
import { useHabitCatalog, useHabitCatalogActions } from '@/data/hooks'

const { catalog, isPending } = useHabitCatalog()          // { chains: HabitChainInfo[] }, queryKey ['habitCatalog']
const { createChain, updateChain, deleteChain, reorderChain,
        createDef, updateDef, deleteDef, pending } = useHabitCatalogActions()

await createChain({ title: 'Déli szünet', daypart: 'DAY' })
await reorderChain(chainId, newDefIdOrder)                 // full position replacement — an exact permutation, or 400
```

- `useHabitCatalog` is a **`useDualQuery`** hook (`realStaleTime: 60_000` — the editor is the write surface, so a moderate cache window is fine, unlike `habitDay`'s `staleTime: 0` lazy-eval heartbeat); real mode never falls back to the mock seed while unresolved (`realEmpty: {chains:[]}`).
- Every `useHabitCatalogActions` mutation mirrors a real 409/400 in mock mode too (thrown `Error`s with the same codes — `HABIT_CHAIN_SEED`/`HABIT_CHAIN_NOT_EMPTY`/`HABIT_REORDER_MISMATCH`/`HABIT_DEF_UNKNOWN_CHAIN`), so a consumer never needs a mock-only error path — see the [routine home](#2-user-facing-behavior) above for the one FE consumer (`RutinHubPage` + its sheets).
- **Mock catalog ids are stable non-UUID strings** (`chain-morning`, `def-wake_on_time`, …) — never assume UUID shape when writing a mock-mode consumer/test.
- `createDef` **resolves with the created `HabitDefInfo`** in both modes (`mezo-3zue.4`) — the wizard needs its `habitKey` for the `/me/rutin?new=` hand-back. Every other mutation still resolves `undefined`.

**The recipe sentence — `features/me/logic/routineSentence.ts` (`mezo-3zue`):**

```ts
import { routineSentenceParts, routineSentence, recipeFromDef, titlePlaceholder,
         type RoutineRecipe, type SentencePart } from '@/features/me/logic/routineSentence'

// From a stored definition — the second argument resolves a FOGG anchorHabitKey to its title.
const recipe = recipeFromDef(def, (key) => defs.find((d) => d.habitKey === key)?.title)

routineSentence(recipe)        // 'Miután kész a Reggeli fény, leírok egy mondatot — és logolom. Ünneplésül: ökölrázás.'
routineSentenceParts(recipe)   // the same sentence as SentencePart[] — render this, not the string
```

- **Pure**: no hooks, no fetching, no formatting of anything the caller did not pass in. It takes a `RoutineRecipe` (`framework` + the eight prose fields) and returns `SentencePart[]`.
- **Always render the PARTS, never the joined string.** Each part is either a literal (`slot === undefined`) or a slot; an unfilled slot carries its Hungarian **placeholder** text with `filled: false`, which is what lets the wizard show the sentence assembling blank by blank (`.rt-blank` / `.rt-blank.is-filled`). `routineSentence()` — the joined string — exists for tests and `aria-label`s, not for layout.
- **It is the ONLY renderer of a recipe.** The wizard's live card and the recipe page's finished card both call it with the same recipe shape, so the two surfaces cannot drift. A `framework: null` def degrades to a bare `title.` sentence rather than an empty node.
- `titlePlaceholder(framework)` names the behaviour slot the way that framework does („pici tett" vs. Clear's shorter „tett"). Note the deliberate split: the **forms** on both pages label Clear's slot „válasz" (the law's own word), while the **sentence** says „tett" — two surfaces, two names, both intentional.
- The **identity clause is conditional**: it appears only once the user wrote one, so an untouched field never leaves a dangling „Hogy olyan ember legyek, aki identitás."

## 7. How to extend it

**Add a habit to a chain — two paths since `mezo-n5e9.1`:**
- **User-created / custom habit (any user, no restart):** `POST /api/habit/def` (chainKey, title, mode, skillKey, xp, optional why/anchorCopy/linkUrl/position; DERIVED requires a metric from `HabitEvaluator.SUPPORTED_METRICS`, §4) — the editor's write API, validated at write time (`HabitAdminService`). **Since `mezo-n5e9.2` the routine editor page calls this directly** (§2's „+ Új habit" / „+ Új rutin"); it is still exercisable via the endpoint (or `HabitAdminService`) directly for anything the editor UI doesn't expose.
- **New BUILT-IN default for every user:** append a `HabitDef` to `content/habit-catalog.json` (unique `key`, correct `chain`/`position`, a LIFE `skillKey`, `xp` 5–15, and the MANUAL ⇔ `metric == "manual"` invariant — `HabitCatalog`'s loader still fails fast on a malformed seed row at startup). This does **not** retrofit existing users automatically: `HabitCatalogService.bootstrapMissing` only imports a seed key a user has never had, and only on that user's *next* catalog touch (`getDay`/`check`/any admin call — NOT `summary`, which is read-only/non-bootstrapping) — there is no push and no per-user migration script.

Either way, then:
- **MANUAL habit** (`mode: "MANUAL"`, `metric: "manual"`): no evaluator work — it completes via the `Pipa` check. Add its key to `habitAction`'s implicit path (MANUAL already maps to `{kind:'check'}`). `morning_pushups` („50 fekvőtámasz") is the plain precedent.
- **Habit with an external link** (`linkUrl`): set the field on the def; it flows `HabitDefEntity → HabitMapper → HabitResponse → HabitItem` end to end. **There is no renderer for it today** — the trailing `↗` was `ItemRow`'s, and `ItemRow` left the daily surface with the Design 2.0 cleanup; `NapRutinPage`'s row draws tick / title / anchor / strength and nothing else. `morning_video` is the precedent def; mirror the `linkUrl` in `habitMock.ts` for mock parity, but expect it to be invisible until a row affordance is designed (§9). Whatever that affordance turns out to be, keep `ItemRow`'s old rule: **never nest an `<a>` inside the row's own button.**
- **DERIVED habit:** a *seed* DERIVED habit needs a `case` added to `HabitEvaluator.satisfied` reading the owning feature's repository/service (**pure reads only** — honest completion), registered in the right closure set (`INTRADAY_METRICS` / `END_OF_DAY_METRICS` / `METRIC_BED_NEXT_DAY`, which together form `SUPPORTED_METRICS`) so `evaluateIntraday`/`closePast` route it; a *custom* DERIVED habit instead just **picks** one of the already-registered `SUPPORTED_METRICS` at creation time — no new evaluator code, no user-defined evaluators (ADR [0019](../decisions/0019-user-editable-habit-catalog-propose-only-ai.md)). Optionally add a **CTA nav target** in `features/today/logic/habitAction.ts` (`NAV_BY_KEY`, or a bespoke `kind` like `protein_breakfast`'s meal-sheet) so the DERIVED row taps through to its logging surface.
- New tunable → `HabitProperties` (`mezo.habit.*`), never a code constant ([`configuration_conventions.md`](../references/configuration_conventions.md)). New XP → the catalog (seed) or the def's `xp` field (custom/edited).
- **Mock parity:** mirror the new row in `data/habit/habitMock.ts` (`mockHabitDay` + `mockHabitSummary`) so both `pnpm test` modes stay green.
- House standards: contract-first ([`api_contract_conventions.md`](../references/api_contract_conventions.md)), backend per [`docs/references/*.md`](../references/), dual-mode hook recipe in [`_platform-data-layer.md`](_platform-data-layer.md).

**Add a THIRD framework** (`mezo-3zue.4`) — the two-framework design is deliberately open, and the work is mechanical rather than architectural. In order:

1. **Contract + column.** Widen `ck_habit_def_framework` and the `framework` enum in `api/feature/habit/habit.yml` (`HabitDefAdmin`/`HabitDefCreateRequest`/`HabitDefUpdateRequest`/`HabitSuggestion`), adding any field the new framework owns as a nullable column + nullable contract field. **Reuse an existing slot wherever the semantics genuinely match** — a third framework that also needs a cue should use `cue`, not a near-synonym column.
2. **`HabitFrameworkValidator`.** Add the branch: which fields are *required* (its own `HABIT_FRAMEWORK_<NAME>_INCOMPLETE` code) and, in `clearForeignFields`, which fields it does **not** own — that method is what makes converting between frameworks safe, so a framework missing from it will silently carry stale fields into the sentence renderer.
3. **`routineSentence.ts`.** Add the branch to `routineSentenceParts` (its Hungarian literals and its `RecipeSlot`s), a `PLACEHOLDER` entry per new slot, `titlePlaceholder`'s naming if the behaviour slot is called something else, and the `recipeFromDef` mapping. **This is the only place the sentence exists** — do not template it anywhere else, or the wizard and the recipe page will drift.
4. **`RoutineWizardPage`.** Add the framework card to step 1, the `STEP_TITLES`/`STEP_SUBS` row, the per-step fields, the `canProceed` clause, and the `frameworkFields()` branch that builds the payload. The wizard's shape — four steps, framework first, a live sentence, a commitment tick — is the contract; a framework that does not fit four steps is a design question, not a code one.
5. **`HabitPage`** (`FW` band map + the editable-field block + its `canSave` clause) and **`RutinHubPage`** (`FRAMEWORK_LABEL`/`FRAMEWORK_BADGE`).

## 9. Decisions, gotchas & deferred

- **Decisions:** spec §2 **D1–D9** — own `feature/habit` domain (the quest mirror, D2), per-habit LIFE-skill XP via the `HABIT` source (D3), habit-strength + perfect-day, no hard streak (D4), Today surface + Growth Rutin tab (D5), wake/bed anchors + `HabitProperties` for everything else (D6 — **anchors re-sourced from the sleep goal via `SleepAnchorPort` in `mezo-dbsr`**; the old `HabitProperties.defaultWake`/`defaultBed` keys are gone, no-goal bed default now 22:00, §5 — and since **`mezo-53su` the caffeine cutoff is re-sourced from Fuel's `CaffeineCutoffPort`**, `HabitProperties.caffeineCutoff` + `mezo.habit.caffeine-cutoff` removed; and since **`mezo-67rb` the M5 run-branch cutoff was wake-anchored** — `SleepAnchorPort` wake `+ mezo.habit.workout-window-hours` (6) — **before `mezo-u6jx` retired it for date-presence**: the weigh-in/stim/run wall-clock compares are gone entirely, so `HabitProperties.weighInCutoff`/`morningWindowEnd`/`workoutWindowHours` + their `mezo.habit.*` yml keys are now **removed** (the `mezo-53su`/`mezo-67rb` removal precedent) — see the [honest-derivation fix spec](../superpowers/specs/2026-08-05-habit-honest-derivation-fix-design.md)), the three closure classes (D7), same-day MANUAL un-check with direct decrement (D8), mock parity that also moves the account XP total (D9). **D5's Today half has now been superseded five times over** — [ADR 0014](../decisions/0014-today-daypart-faces.md) (`mezo-j7u4`: rows on a daypart face, not a `RoutineCard`), then ADR 0022 / 0025 / 0026, and finally **[ADR 0032](../decisions/0032-five-tab-ia-dissolved-section-shells.md) + [ADR 0033](../decisions/0033-mozaik-2-tile-language.md)** (`mezo-d20`: a hub tile that opens `/nap/rutin`, its own full page). **The domain contract has been unchanged through every one of them** — that is the point worth remembering: five view rewrites, zero catalog/evaluator/XP-tail changes. ADR [0010](../decisions/0010-gamified-growth-xp-feedback-not-payment.md) is the tone contract (no failure state, no break-punishment) and is still enforced in code, now by `NapRutinPage`'s `tickAction`.
- **Gotcha — E4's noon deadline:** `bed_on_time` completes only when the **next** morning's sleep log arrives; past next-day 12:00 (`closePast`) it closes quietly `missed`. A late-arriving sleep log after the deadline no longer counts.
- **Gotcha — vacuous kitchen-close:** E2 `last_meal_before` yields **`true`** when **no** meals were logged that day (nothing eaten after close ⇒ the habit is honestly kept), not `missed`.
- **Gotcha — gym date-presence fallback, now unified with the run branch (`mezo-u6jx`):** finished gym sessions have no `completed_at`, so M5's gym half counts a **done instance on the date** (date-presence, an honest fallback per spec §3); **since `mezo-u6jx` the run half is date-presence too** — any run logged for the date satisfies M5, retiring the wake-anchored cutoff (`SleepAnchorPort` wake `+ workout-window-hours`, itself only introduced in `mezo-67rb`) entirely. Both branches are now honest-by-presence.
- **Gotcha — E1 retro-log residual, accepted (`mezo-u6jx`):** `no_stim_after` still compares each stim intake's `taken_at` against the resolved caffeine cutoff — a retro-logged afternoon coffee (`taken_at` is the log moment, not the actual morning consumption) still busts E1, unlike M4 which went date-presence in the same change. Accepted for now (spec §2); the honest fix — an optional „mikor ittad?" time field on the intake log — is deferred (spec §5).
- **Gotcha — an out-of-window sleep log is NOT the same "pending" as no log at all (`mezo-czol`):** M1 `sleep_wake_window` stays `pending` in both cases, but they read very differently to the user — one honestly logged and missed the window, the other hasn't logged yet. `wake_on_time`'s `hint` disambiguates: non-null only when a sleep log exists for the day AND its wakeup is outside `sleep-goal.wake ± wake-window-min` (`HabitService.wakeHint`); a still-`pending` row with **no** sleep log gets a **null** hint and keeps its `Logolás` CTA (`habitAction` only withdraws the CTA when `hint` is truthy) — the fix must never make an honestly-unlogged day look "explained" — and the hint is strictly a **TODAY-read affordance** (`date.equals(LocalDate.now())`, matching `evaluateIntraday`'s own scope): a past day's rows never materialize/re-evaluate, so a bare `pending` there is a synthetic default, not a proven "out of window" — a past-day read (e.g. the Rutin tab's read-only history view) always gets a null hint, even over an in-window backfilled wakeup.
- **Gotcha — END_OF_DAY habits show `pending` all day:** E1/E2 are not in `INTRADAY_METRICS`, so the today-read never completes them — they resolve only at the nightly close or the next-day read. Expected, not a stuck row.
- **Gotcha — deliberate mock-seed deviations (`mezo-o5hx`):** the static mock day has no evaluator, no nightly close and no "tomorrow", so honest derivation cannot be mirrored. Therefore in `habitMock.ts` (a) `caffeine_cutoff` + `kitchen_close` are **MANUAL** (checkable) instead of DERIVED END_OF_DAY — otherwise they'd be permanently dead rows in the demo; (b) **`bed_on_time` is omitted entirely** (E4 could never complete → the evening chain would never reach a perfect evening in mock). Real mode keeps the honest catalog behavior for all three. The two derived rows the user *can* honestly complete in mock (`intention_reflect`, `evening_ritual`) flip via `completeMockDerivedHabit` from their owning surface (§5).
- **Gotcha — MANUAL habits are never auto-completed:** M2/E3 nominally sit in the intraday set but `evaluateIntraday` skips `metric == "manual"` — they complete solely via the `check` write (honest self-claim), and quietly `missed` at close if untapped.
- **RESOLVED-BY-DELETION — the perfect-chain toast no longer exists.** `useChainCelebration`'s `wasComplete` ref used to start `false`, so an already-complete chain chimed once when its face mounted (an accepted "welcome back" chime) and re-chimed on every island/daypart switch, because the panel's `ChainCelebrations` only mounted while selected. Both the hook and the fan-out component were deleted with `TodayPage` (`mezo-d20.9.1`), and `NapRutinPage` mounts no replacement — **the perfect-morning / perfect-evening celebration fires nowhere today.** The 30-day perfect-day *counters* on `/nap/rutin`'s stat strip and on Growth's Rutin tab are unaffected (they read `useHabitSummary`, not a toast). Re-adding the chime is a design call, not a bug fix — the deferred list below carries it.
- **Gotcha — after midnight a check writes the NEW day's row.** Every daily habit surface keys `useHabitDay`/`useHabitActions` on `localDateString()`, so once the wall clock passes midnight the check lands on the **new** day's `habit_day` row. This used to bite hardest via the winddown ghost (a bed time of e.g. 00:15 put the window on both sides of midnight); the ghost is gone, but the date semantics are unchanged and deliberately consistent — every Nap surface uses the local-date string, never a UTC slice.
- **Gotcha — a derived completion that closes on a page READ is now silent.** `useHabitDay`'s `levelUps` carries the payload of a DERIVED row that flipped `pending → done` during *that* read. `TodayPage` used to drain it into a reward toast; `NapRutinPage` never calls `consumeLevelUps()`, so the row simply appears ticked with no feedback, and the payload stays in the cache until `RitualPage` (the only remaining caller) drops it at Napzárás. The XP is awarded correctly either way — this is a missing *celebration*, not a missing award.
- **Deferred:** the original spec §10 sub-project ① (custom/user-edited habits + catalog-management UI, **incl. the AI suggester**) is **done** — backend since `mezo-n5e9.1`, editor UI since `mezo-n5e9.2`, **AI suggester since `mezo-n5e9.3`** (§2/§4/§5, §6's catalog hooks) — see ADR [0019](../decisions/0019-user-editable-habit-catalog-propose-only-ai.md); the epic's own last child slice (spec [2026-08-05-routine-editor-design.md](../superpowers/specs/2026-08-05-routine-editor-design.md) `.3`) is now shipped. Still deferred: PWA reminder notifications; companion flavor copy + discipline-trait/Growth-journal HABIT consumption; and the three sibling specs — ② Sleep Cycle screenshot ingestion, ③ Fuel „Mai" slot-timing fix + slot-level AI logging, ④ morning-training reschedule + Tasty Dose/Origin protocol data setup.
- **Deferred — gaps the Design 2.0 redesign opened and did not close** (all four are honest holes, not designed simplifications; each needs a design decision before a dev issue):
  1. **No chain-completion celebration** — see the RESOLVED-BY-DELETION bullet above.
  2. **No `linkUrl` affordance on the daily row** — `morning_video`'s external link is carried end to end and rendered nowhere (§7).
  3. **A DAY-daypart chain has no Nap surface** — the hub builds MORNING/EVENING tiles only, and `NapRutinPage` renders those two groups only; a custom DAY chain is editable and visible on Growth but unreachable from the day itself (§2).
  4. **`evening_ritual` is offered twice** — as an ordinary `/nap/rutin` row *and* by the Este hero's `Zárjuk le a napot` CTA, because the `OWNED_BY_RITUAL_HERO` filter lived in the deleted `DaypartEvening`. Both route to `/ritual`, so nothing breaks; it is duplication the earlier layers deliberately avoided (§2).
- **Correction beyond the original design note (`mezo-n5e9.4`):** `HabitDefUpdateRequest` has no `skillKey` field, so a def's skill is contract-immutable after creation — same as `mode`/`metric` — not editable in `HabitEditSheet`'s edit mode (§2).
- **Gotcha — `framework` is nullable, and null is a first-class state, not "not yet migrated" (`mezo-3zue.2`):** every def created before this slice keeps `framework = null` forever — there is no backfill and none is planned. A null-framework def is not "broken" or "incomplete"; it is simply a bare habit, exactly as before, and `HabitFrameworkValidator` actively **enforces** that null-ness by rejecting any of the seven framework fields being set alongside it (`HABIT_FRAMEWORK_FIELDS_ORPHAN`, §4). The FE distinguishes "legacy habit" from "half-filled recipe" purely off whether `framework` is present — there is no separate migration flag.
- **Gotcha — an anchor's lifecycle change releases dependents, it never cascades (`mezo-3zue.2`):** deleting or pausing (`isActive: false`) a def that other defs are FOGG-stacked onto does **not** delete, deactivate, or block-with-409 those dependents. `HabitAdminService.releaseAnchors` demotes each one to a free-text anchor instead — `anchorHabitKey` nulled, `anchorCopy` backfilled only if it was blank (`"kész a " + anchor title`) — so an existing recipe never dangles on a reference to a gone/paused habit, and never silently loses the user's own anchor wording if they had already written one. There is no error code for "this def is someone's anchor" — the operation always succeeds and quietly repairs the dependents.
