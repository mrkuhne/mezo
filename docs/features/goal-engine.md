# Goal Engine (G5–G6) — Feature Documentation

> One-line: the backend **TDEE-bootstrap → segmented projection → soft-guards → feasibility-graded prescription** engine that turns a `Cél` goal + its plan timeline + the EWMA weight trend into a per-segment "recept". **Status: ✅ backend done (goal-system G5, `mezo-g1u`)**; FE surfacing is the recept card in Me/`Cél` (see [`me.md`](me.md) §2). This is a *domain* feature with no route of its own — it produces data the `Cél` surface renders. **Adaptive TDEE has landed** (Diet Plan slice 5, `mezo-r4n7`): a Monday weekly review compares the observed EWMA rate to the goal's target rate and proposes a smoothed kcal correction; once accepted, `prescription.basis="adaptive"` (§3/§9). **Learned expenditure Part 1 has landed** (`mezo-zz91i`): a small Kalman filter learns the user's real non-exercise base from logged intake + the weight trend and serves it automatically as `neatBaselineKcal`, no approve step, exclusive per user with the adaptive-correction suggestion (§3/§9). **Learned expenditure Part 2 has landed** (`mezo-3n2so`): the weekly „Heti tanulás" card + dismiss, the „Hogy tanultam?" week-by-week history page, per-day COMPLETE/INCOMPLETE marks with an immediate re-chain of the affected + every later week, and a per-user learning switch in diet settings — see §3 „Learned expenditure Part 2". Only the Phase-3 **AI evaluator** (replacing the heuristic gate) and the Profile TDEE card's formula-only display (`mezo-qnsl9`, §9) stay deferred.

## 1. Summary

The G5 engine is the analytical core behind a body-weight goal: given the goal (trajectory, target rate, guards, window), the owner's biometric profile, the linked Train plans (mesocycles / running blocks), and the live EWMA weight trend, it computes a **segmented prescription** — per stretch of the goal window, a daily kcal target, a protein target, a sleep-target seed, a projected weekly rate, and a Hungarian rationale — plus a **soft-guard status** (strength + muscle volume) and a **feasibility verdict**. The result is persisted onto the goal as two jsonb columns (`tdee_bootstrap`, `prescription`) and surfaced read-only via `GoalResponse`. The Goal Hub additionally has one ownership-gated, state-led read model at `GET /api/goals/{id}/overview`: it composes the live course, today's kcal/day type, the current segment and next boundary, real plan/sport coverage, guards, and open-suggestion summary without mutating the goal.

The engine is **heuristic + formula-based**: guards WARN, the verdict only colours the surface, and a missing biometric profile yields a graceful "profil szükséges" prescription rather than an error (so the recompute triggers in §3 never break a weigh-in/activation). A hard cross-field invariant now sits before those heuristics: a cut must target below its start weight, a bulk above it, maintain must omit the target weight, and every goal window must span at least seven days. Invalid writes return a typed field-level 400 instead of producing a plausibly formatted but directionally wrong plan.

- **Backend:** ✅ real — five engine services + the weight-trend spine, all config-driven, all integration-tested.
- **FE:** ✅ the recept, now read off the goal overview on `/me/goals/weight` (`GoalsPage`: `GoalCourseHero` + the mosaic tiles, with the detail pages `GoalDietPage`/`GoalSegmentPage`/`GoalGuardsPage`; the old `GoalRecept.tsx` card and its evaluate CTA were deleted in `mezo-8slef`), and the real weight trend — see [`me.md`](me.md) §2/§4 and [`_platform-data-layer.md`](_platform-data-layer.md) §2.

Driving design: [`docs/superpowers/specs/2026-06-18-goal-system-design.md`](../superpowers/specs/2026-06-18-goal-system-design.md) — **§4** (the EWMA-spine projection model, hybrid projection D7) and **§5** (engine services, soft guards D9, feasibility gate D10, prescription assembly §5.4). The grounded numbers (NEAT bands, kcal/kg, protein g/kg, rate bands, the MET model, EWMA half-life) come from the research note [`docs/research/queries/2026-06-18-goal-engine-numbers.md`](../research/queries/2026-06-18-goal-engine-numbers.md).

## 2. User-facing behavior

The central weight-goal editor (`/settings/me/goal`, [Me feature](me.md)) takes a target weight and remaining kg/week pace, derives a date from today's current-weight baseline and preserves the original stored start/history/guards. The backend's existing `rateTargetPctPerWeek` calculation remains based on the **original complete window**. The UI explicitly discloses the difference and requests feasibility for both windows before saving; it does not substitute browser-derived calorie prescriptions. Maintenance has no estimated arrival date.

The engine has **no screen of its own**. Its output appears on `/me/goals/weight` (`Cél`) — moved off `/me/goals` in `mezo-iizd.1` Task 8 so that route could become the general-purpose Célok (life-goals) hub, see [`lifegoal.md`](lifegoal.md) — through the goal overview: `GoalsPage` renders the `GoalCourseHero` (course status, completion ring, signed kg/week) and a mosaic of tiles — today's diet frame (→ `/me/goals/weight/diet`, `GoalDietPage`: day kcal, training/rest-day kcal, protein/carbs/fat), the current segment (→ `/me/goals/weight/segment`, `GoalSegmentPage`: the segment rail across the whole arc), plan links, and the guards (→ `/me/goals/weight/guards`, `GoalGuardsPage`: healthy/total guard count + the top issue). **Historical:** until `mezo-8slef` this was the **recept card** (`GoalRecept.tsx`, deleted — it had been unmounted from the hub already): a feasibility-verdict banner ("Reális" / "Reális, figyelmeztetésekkel" / "Agresszív"), per-segment recept cards (week range, label, kcal / protein g / sleep h / signed kg-per-week, HU rationale), and guard-status pills (strength e1RM trend, muscle weekly-volume floor + rate-cap, and a muted "Fehérje: Fuel-re vár" pill). When a goal had not yet been evaluated (`prescription === null`), that card showed an "Értékeld a célt" CTA firing the `evaluate` action. Full UX detail and the Hungarian labels live in [`me.md`](me.md) §2 (`Recept — the G5 engine finale`).

The engine also runs **invisibly** on the recompute triggers (§3) — logging a weigh-in, activating a goal, or attaching/detaching a plan all silently refresh the active goal's prescription, so the recept the user next opens is current without an explicit re-evaluate.

The redesigned Goal Hub reads a single `GoalOverviewResponse` instead of making the UI reconstruct domain truth from scattered fields. Its primary status is `on_track | watch | learning | invalid`: cut/bulk compare the signed trailing-four-week EWMA rate with the signed target inside a configurable tolerance, maintain compares against a zero-rate band, and missing trend data stays `learning`. Projection is shown only for a non-zero rate moving toward the target. Invalid or missing prescriptions never leak stale kcal; diet is explicitly `unavailable`. A day-type split selects today's training/rest kcal from the union of recurring gym and sport weekdays, while a uniform segment returns its one kcal value.

The dedicated `Tervkapcsolatok` page renders the server-owned mesocycle/running lanes, uncovered goal weeks, and the real recurring sport schedule (sport, training/match kind, location, Hungarian weekday, time and duration). A link that would run past the goal window is deliberately clipped and marked **„A cél végéig”**. The page also explains the calorie model directly: a mesocycle changes projection boundaries and muscle guards but has zero TDEE delta by itself; recurring gym/sport sessions and linked running sessions supply EAT. Consequently, attaching only a mesocycle may correctly leave every kcal segment unchanged.

A suggestion is never a one-tap mutation. The hub only announces that a proposal exists; opening it performs the side-effect-free preview and shows every typed current → proposed field, delta, warning and blocker on a dedicated review page. Apply is fingerprint-gated, so the exact preview the owner saw must still match the current plan and engine inputs; otherwise the server returns the stale conflict and the client asks for a refreshed preview instead of partially applying anything.

Service responsibilities (all `@Service`, constructor-injected, stateless):

- **`WeightTrendService`** (`biometrics/weight/service/WeightTrendService.java`) — the **spine**. Collapses same-day weigh-ins to a daily mean, runs an EWMA (`α = 1 − 0.5^(1/halfLifeDays)`), and computes the OLS weekly rate (whole-window + trailing-4w) and a `dataSufficiency` grade (`none` / `provisional` / `full`). Read-only, no `@Transactional`. Reused by the projection (reconciliation) and the muscle guard (rate-cap), and exposed verbatim at `GET /api/biometrics/weight/trend`.
- **`TdeeBootstrapService`** (`engine/service/TdeeBootstrapService.java`) — the **formula TDEE**. Katch-McArdle when body-fat % is known (`BMR = 370 + 21.6·LBM`, `formula="KATCH"`), else Mifflin-St Jeor (`formula="MSJ"`); then **`neatBaselineKcal = BMR × NEAT`** (the NEAT lifestyle multiplier from `activityLevel` — DESK/MIXED/PHYSICAL, default MIXED 1.35) and **`TDEE = neatBaselineKcal + weeklyEatKcalPerDay`**, where the caller supplies the weekly scheduled training energy from the train-port `WeeklyScheduledActivityService` (gym+sport+active-run, the net activity-energy model at the moderate band ÷ 7 — `mezo-32m82`, replacing the old gross MET×kg×óra sum). Pure; the caller supplies current weight + weekly EAT, so it needs no repository. **Anti-double-count (§6.3, mezo-eujg):** the NEAT multiplier covers ONLY non-exercise daily life; training energy is added **explicitly** via `weeklyEatKcalPerDay`, never baked into the multiplier (the old `BMR × PAL` folded average activity into the multiplier — retired).
- **`GoalProjectionService`** (`engine/service/GoalProjectionService.java`) — the **segmented projection** (spec §4). Walks the window week-by-week in goal-week space, resolves the active load per week (meso phase class from `phaseCurve` + running on/off), collapses contiguous identical loads into `ProjectionSegment`s, and computes per segment the TDEE, daily kcal target, and projected rate for all three trajectories. **Segment maintenance (§6.3, mezo-eujg; net model mezo-32m82):** each segment's TDEE = the NEAT baseline + the scheduled gym+sport EAT (segment-independent) + this segment's running EAT — every training term the net activity-energy model (moderate band) via `WeeklyScheduledActivityService`. Running on/off is the *only* per-segment TDEE delta (`runWeeklyEatKcalPerDay(sessions, weightKg)`); a meso-phase change splits a segment but is a *zero* TDEE delta (its effect is on volume, the muscle guard); gym + volleyball are scheduled + segment-independent (volleyball now counts **explicitly through the weekly schedule**, no longer modelled as ambient). Each segment also carries the goal's **`dailyEnergyBalanceKcal`** = `sign(trajectory) × rate%/100 × kg × kcalPerKg ÷ 7`, with `targetKcal = tdee + dailyEnergyBalance` — the explicit per-day deficit/surplus Fuel now reads straight off the wire ([`fuel.md`](fuel.md) §5). **Reconciliation:** once the trend is ≥ `provisional`, the observed trailing-4w rate becomes the spine, replacing the formula seed. **Day-type kcal split (Diet Plan slice 3, `mezo-sxlj`):** each segment additionally gets a training-day vs rest-day kcal pick via the pure **`DayTypeShiftCalculator.split(segmentKcal, shiftKcal, trainingDays, bmr)`** (`engine/service/DayTypeShiftCalculator.java` — a `static`, no-Spring calculator), called once per segment from `buildSegment` with `shiftKcal` = the resolved `DietPreferences.dayTypeShiftKcal()` (§5 — `diet_settings.day_type_shift_kcal`, ghost 0) and `trainingDays` = that segment's training-day count: `WeeklyScheduledActivityService.scheduledTrainingDayOfWeeks(userId)` (recurring gym ∪ sport weekdays) unioned with the active running block's own session weekdays for the goal-week (the private `runDayOfWeeks` helper, the `sessionsPerWeek` fallback idiom). The math (`S` = the shift setting, `T` = training days/week, `R = 7 − T` rest days/week, `kcal` = the segment's existing uniform target):

```
restDayKcal      = max(kcal − S, ceil(bmr))          // BMR floor — shared with the FE's floor semantics (fuel.md §9)
effectiveShift   = kcal − restDayKcal                 // ≤ S when the floor bit
trainingDayKcal  = kcal + round(effectiveShift × R / T)
```

**Uniform-day edge cases** — `split` returns both fields `null` (the segment behaves exactly as it did pre-slice-3) when `S ≤ 0` (shift off), `T == 0` (no training day to move calories onto), `T == 7` (no rest day to take from), or `effectiveShift ≤ 0` (the floor already absorbed the whole shift). **Weekly-sum invariance:** `T×trainingDayKcal + R×restDayKcal = 7×kcal ± T/2` (only the single `round()` can drift, and only when `effectiveShift × R` doesn't divide evenly by `T`) — the split reallocates the week's calories, it never changes their total. Worked examples: `kcal=2150, S=200, T=4, R=3` (no floor) → rest `1950`, training `2150 + round(200×3/4) = 2300`; `kcal=1800, bmr=1720` (floor bites) → rest `max(1600,1720)=1720`, effective shift `80`, training `1800 + round(80×3/4) = 1860`. `ProjectionSegment` and `GoalPrescriptionJson.Segment` both carry the two nullable outputs verbatim — `trainingDayKcal`/`restDayKcal`, positioned right after `dailyEnergyBalanceKcal` (§4) — jsonb-additive, so a pre-slice-3 persisted prescription deserializes with both `null` and serves byte-identically. Fuel reads them at serve time on both surfaces — see [`fuel.md`](fuel.md) §4/§9 for the serve-time carb derivation and the no-double-counting composition rule.
- **`GuardEvaluationService`** (`engine/service/GuardEvaluationService.java`) — the **soft guards** (spec §5.3, D9 — WARN, never block). Strength: genuinely reuses the `ExerciseRecordService` working-set filter now — both funnel through the shared `OneRepMax.eligible`/`OneRepMax.estimate` (`feature/train/service/OneRepMax.java`, cross-feature goal→train edge): group sets by lift identity (`catalog_id` else `name`) over **working sets only, cap 12** (`OneRepMax.REP_CAP` — was 10, and warmups were wrongly counted before `mezo-88iwa.3`; the guard's own repo query now filters to `kind='working'` before the eligibility check runs), main lift = the identity with the most sets, `breached` when its e1RM trend % drops to `strength.e1rmBreachPct` (−5%). Muscle: per-muscle weekly hard sets from `MuscleGroupVolumeLog` across the linked mesos vs `volume.warnBelow` (6), plus a rate-cap on the trailing-4w EWMA slope vs `rate.capPctPerWeek`. **Protein leg deferred** — `proteinMonitored=false` always; meal logging and goal-aware scoring exist since Diet Plan slice 2 (`mezo-3g5w`, §9), but the guard itself doesn't yet compare the day's/week's actually-logged protein against the prescribed target — that closed loop is slice 5 territory.
- **`GoalEvaluationService`** (`engine/service/GoalEvaluationService.java`) — the **heuristic feasibility gate + prescription assembly** (spec §5.1/§5.4). Grades rate realism, guard satisfiability, and a conflict rule (`grade(...)`, `GoalEvaluationService.java:145-149`); folds segments + guards + a protein target (`proteinTargetGrams`, BW path vs LBM path, capped) into the `GoalPrescriptionJson`. Pure, no I/O, never throws. Its `gradeRate` delegates the cap/band → verdict classification to `GoalFeasibilityService.verdictForRate` so the eval gate and the wizard preview share **one** band definition. **Conflict escalation:** the rule's rate trigger is `RateGrade.overBand()`, which is true for **both** the 0.7–1.0 warnings band **and** the over-cap aggressive band — so a rate that on its own would only be `feasible-with-warnings` (0.7–1.0 %BW/wk) **escalates to `aggressive`** when it coincides with an active running block (a segment whose `activeSystems` contains `"run"`) **and** an active `strength` guard (likely strength breach; adds the "enyhítsd a deficitet vagy told arrébb a futóblokkot" note). Covered by `GoalEvaluationServiceIT`.
- **`GoalFeasibilityService`** (`engine/service/GoalFeasibilityService.java`, G6 `mezo-06n`) — the **stateless realism core**: the single source of (a) the rate-magnitude derivation `deriveRatePctPerWeek` = `|startW − targetW| / startW * 100 / weeks` (valid maintain → 0; invalid direction/window is rejected through `GoalInvariantValidator`; `GoalService.applyUpsert` delegates here so the persisted rate equals the previewed rate), (b) the `verdictForRate` band mapping, and (c) `preview(FeasibilityPreviewRequest)` which derives + grades a draft and — only over the cap — suggests `startDate + ceil(weeksAtCap)` (`weeksAtCap = magnitude / capPctPerWeek`). Pure, config-driven (`GoalEngineProperties`), no I/O.
- **`GoalInvariantValidator`** (`feature/goal/service/GoalInvariantValidator.java`, `mezo-szsj`) — the single hard cross-field gate shared by `GoalService`, `GoalFeasibilityService`, suggestion accept, and the engine's legacy guard. It enforces `cut: target < start`, `bulk: target > start`, `maintain: target == null`, plus a minimum seven-day window. Write/preview conflicts return `GOAL_DIRECTION_TARGET_CONFLICT` on `targetWeightKg` or `GOAL_WINDOW_TOO_SHORT` on `targetDate`. `GoalEngineService.evaluate` uses the side-effect-free `isCoherent` form immediately after its ownership read; a pre-fix incoherent row has both persisted engine artefacts cleared and returns before projection or suggestion triggering, so Fuel cannot consume a wrong-direction prescription.

**Derived weekly rate (G6 `mezo-06n`).** `rateTargetPctPerWeek` is **server-derived**, not a client input: `GoalService.applyUpsert` calls `GoalFeasibilityService.deriveRatePctPerWeek(...)` on every create/update (stored as an unsigned magnitude; the G5 engine applies the trajectory sign). It was dropped from `GoalUpsertRequest` and stays on `GoalResponse`.

`GoalEngineService` is the *only* `@Transactional` link (it writes the goal); every other service is pure/read-only so it is trivially testable in isolation.

**Transaction note:** because each trigger's enclosing method is already `@Transactional`, `evaluate` joins the same transaction — the recompute is part of the triggering write's atomic unit (a failed evaluate would roll back the weigh-in/profile-save/schedule-edit). The weigh-in, diet-settings, and (since mezo-3g5w) all five schedule-mutation paths funnel through the shared `GoalEngineService.recomputeActiveGoal` and deliberately depend on **no** goal: if the owner has no active goal, it returns without calling `evaluate`. The biometric-profile-change path keeps its own separate copy of the same no-goal-graceful check (table row above) rather than calling the shared helper. Either way, a weigh-in/profile-save/schedule-edit must never require a goal. The five schedule-mutation rows are covered by `feature/train/service/ScheduleGoalRecomputeIT` (sport/gym schedule replace + running block activate/close/delete all recompute the active goal's prescription; a schedule replace with no active goal is a no-op).

**Startup reconciliation (Fuel Layer C, `mezo-eujg`).** A **sixth**, batch caller sits outside the write-triggered five: `GoalReevaluateRunner` (`feature/goal/GoalReevaluateRunner.java`) — a `CommandLineRunner`, `@Profile("demofixtures")` (opt-in since S2 `mezo-qw37.2` — the owner's pre-NEAT reconciliation is done on the live DB), `@Order(200)` so it runs after the seed runners — re-`evaluate`s **every non-archived owner goal** at boot. It exists because the NEAT/weekly-EAT migration made any goal's stored prescription stale (old BMR×PAL numbers, no `dailyEnergyBalanceKcal`); the runner refreshes them so the recept the user next opens carries the new model. Idempotent (`evaluate` overwrites both jsonb columns each run, and the graceful no-profile path is safe); ITs annotate `@ActiveProfiles({"demodata", "demofixtures"})` and drive the no-arg `run()` overload against a reset DB.

**Net activity-energy model rollout (`mezo-32m82`).** A **seventh**, one-shot batch caller, this time on **every** profile including prod: `ActivityModelMigrationRunner` (`feature/goal/ActivityModelMigrationRunner.java`, `@Order(207)` — after `GoalReevaluateRunner` (200), before `MealRescoreRunner` (210) so rescoring reads the recomputed targets) does two things at boot: (1) `SportService.reestimateMissing`/`RunningService.reestimateMissing` fill in a fresh net kcal for every logged sport/run row whose `kcal` a companion Liquibase changeset nulled out (the old gross-MET estimates; a row with no resolvable body simply stays honestly `NULL`); (2) it re-`evaluate`s every non-archived goal whose `tdee_bootstrap.activityModel` is missing or below `ActivityEnergyModel.VERSION` (currently `2`) — the marker a fresh `evaluate` writes, so a later boot skips an already-migrated goal. Idempotent by construction (the version marker), and a single goal's evaluate failure is caught + logged, never aborting the rest of the rollout.

### Weekly adaptive review (Diet Plan slice 5, `mezo-r4n7`)

A **parallel, job-driven** loop sitting *outside* `evaluate` — it never runs inline with the triggers above. Every Monday `AdaptiveReviewJob` (`engine/service/AdaptiveReviewJob.java`, `@Scheduled(cron = "${mezo.goal.adaptive.cron}")`, default `"0 40 6 * * MON"` — before the proactive weekly-review job at 6:50, after typical wake weigh-ins) iterates every `AppUserEntity` and calls `AdaptiveReviewService.reviewUser(userId, weekStart)` with per-user try/catch isolation (one owner's failure never sinks the sweep). The bean only exists when `ADAPTIVE_REVIEW_JOB_SWITCH` (`mezo.techcore.cron.adaptive-review-job.enabled`) is `true` — off means no bean, no cron registration.

`AdaptiveReviewService.reviewUser` (suggest-only — it **never** writes a target itself):
1. Resolves the owner's single active, **already-evaluated** goal (`prescription != null`); no goal or no prescription yet → no-op.
2. Reads the live EWMA trend (`WeightTrendService.computeTrend`) and asks the sleep port whether the owner is in sleep debt (`SleepAdequacyPort.sleepDebted(userId, weekStart)`, below).
3. `AdaptiveCorrectionService.compute(goal, trend, sleepDebted)` — the pure math (below); empty → no-op, no suggestion.
4. On a non-empty correction, reads the **just-finished** week's intake adherence (`IntakeAdherencePort.weekAdherence(userId, weekStart.minusDays(7))` — `weekStart` is the Monday the job runs ON, so this is the prior Mon–Sun) and assembles the `weekly_correction` fields onto `GoalSuggestionPayloadJson` (§4), then proposes via the same dedup machinery slice 4 built: `GoalSuggestionService.propose(userId, goalId, KIND_WEEKLY_CORRECTION, "weekly:" + weekStart, payload)`. `propose`'s goal-scoped dedup query on `(goal_id, dedup_key)` (decided rows included) is the **sole** per-week guard — a dismissed week is never re-proposed. That query is backed by a plain (non-unique) index, not a DB-level uniqueness constraint — the single-owner assumption is what makes the application-level check sufficient, no separate exists-query needed.

**`AdaptiveCorrectionService` — the correction math** (`engine/service/AdaptiveCorrectionService.java`), pure + deterministic:

```
neededKcal = (targetRateKgPerWk − observedRateKgPerWk) × kcalPerKg ÷ 7
```

with **signed** kg/week rates (cut negative, bulk positive, maintain 0 — `targetRateKgPerWk` derives from `goal.rateTargetPctPerWeek` the same way the projection does, just re-signed by trajectory). Gates, in order: no trend / `dataSufficiency == NONE` / a null observed rate → empty (not trustworthy yet); `|neededKcal| <` `adaptive.deadBandKcal` (50) → empty (on track — silence, not micro-nudges); otherwise clamp to `±adaptive.maxStepKcal` (120, deliberately small steps — the RP unsmoothed 200g→50g jump is the anti-pattern this clamps against); **sleep-debt damping** then halves the delta **only when it is negative AND the trajectory is not `bulk`** — a negative delta is deficit-deepening on `cut`/`maintain`, but on `bulk` it TRIMS the surplus instead (the owner is gaining faster than the target), so damping must not fire there (final-review fix, mezo-r4n7 — an earlier version conflated "negative" with "deficit-deepening" and halved bulk trims too); a correction that *adds* food is never damped either way, because the guard exists to protect sleep-debt recovery, not to slow progress; if the (possibly halved) delta rounds to 0, empty.

**Spec deviation, deliberate:** the Diet Plan spec (`docs/superpowers/specs/2026-09-02-diet-plan-design.md` §6.6) wrote `deltaKcal = clamp((observedRate − targetRate) × 7700 / 7, ±maxStep)` — the worked examples below show that sign is inverted for the intended behavior (a cut running too slow must produce a *negative* kcal delta, i.e. deepen the deficit). This implementation uses `(target − observed)`; the worked examples are the source of truth, not the prose formula.

Worked examples (`kcalPerKg = 7700` ⇒ ×1100 per kg/week of gap; from `AdaptiveCorrectionServiceTest`):

| Scenario | Target vs observed | Needed | Result |
|---|---|---|---|
| Cut too slow | target −0.48 kg/wk, observed −0.20 kg/wk | −308 kcal | **−120** (clamped) |
| Cut too fast | target −0.48 kg/wk, observed −0.90 kg/wk | +462 kcal | **+120** (clamped, eases up) |
| Bulk too slow | target +0.20 kg/wk (0.25% BW), observed +0.05 kg/wk | +165 kcal | **+120** (clamped) |
| Small gap | target −0.48 kg/wk, observed −0.45 kg/wk | −33 kcal | **empty** (inside the 50-kcal dead-band) |
| Cut too slow **+ sleep debt** | same as row 1 | −308 → clamp −120 | **−60** (halved; the fast-easing +120 case above stays undamped since it's positive) |
| Bulk gaining too fast **+ sleep debt** | target +0.20 kg/wk, observed +0.50 kg/wk | −330 kcal | **−120** (clamped, **NOT halved** despite sleep debt — a negative delta here trims the surplus, it doesn't deepen a deficit; bulk-aware damping fix, mezo-r4n7) |

**Sleep-adequacy port** (`engine/port/SleepAdequacyPort.java`, impl `feature/biometrics/sleep/service/GoalSleepAdequacyAdapter.java`) — a goal-owned port, **not** a dependency on companion's `FlagEvaluator`: same deficit math (`sleep_log.date` is the WAKE morning so today's row IS last night; a long night never repays a short one; unlogged nights are skipped, never counted debt-free) but over the review's **own** window (`adaptive.sleepDebtNights` = 7 nights, `adaptive.sleepDebtMinNights` = 4 honest small-n gate, `adaptive.sleepDebtDeficitHours` = 5.0 cumulative deficit threshold, goal-hours from `sleep_goal.targetMinutes` else the 8.0h ghost) — independent of whether the companion switch (which owns a *different* 3-night flag variant) is on.

**Intake-adherence port** (`engine/port/IntakeAdherencePort.java`, impl `feature/meal/service/GoalIntakeAdherenceAdapter.java`) — context only, it never gates the correction: averages kcal intake/target over **logged days only** off `FuelDayService.getWeek` (a day counts as logged when its consumed kcal is `> 0`; `kcal ≤ 0` means absence — missing data, not a zero-kcal day — and is skipped rather than dragging the average toward zero).

**Preview-gated accept and `basis="adaptive"`** — every suggestion is reviewed through `GoalSuggestionPreviewService` before it can be applied. The service copies the goal field-by-field into a transient draft, uses the I/O-free `GoalSuggestionDraftApplier` on that draft, and calculates both sides with the shared `GoalPrescriptionCalculator`; the calculator is also the engine's persisted evaluation core but itself never saves, emits events, or proposes. Its `calculate(userId, goal, draftPreferences)` overload (mezo-u2pd) lets a caller substitute UNSAVED diet preferences for what `DietPreferencesPort.resolve` would return — the one calculation path, now shared by the persisted evaluation, the suggestion preview and the diet-settings draft preview. The resulting typed projection exposes trajectory, target/window, kcal/day-type split, macros, segment and guards in deterministic changed/unchanged order. A direction conflict remains inspectable as a blocker and cannot be applied; historical accepted/dismissed/superseded rows remain inspectable without an apply token. For an accepted row the applier reverses the one persisted effect on a transient copy before calculating the historical `current` side, while the live goal is the `proposed` side—so reopening an accepted weekly correction never displays a fictitious second calorie reduction.

The apply token is a lowercase SHA-256 semantic fingerprint over the suggestion payload/status, goal inputs and overrides, resolved diet preferences, linked plan metadata (including meso phase structure), and the recurring gym/sport schedule. It deliberately excludes generated and audit timestamps, including `prescription.generatedAt`, so a timestamp-only recompute does not create a false stale state. Accept recomputes the preview and compares the submitted token in constant time; any semantic drift supersedes the proposal in `GoalSuggestionSupersedeWriter`'s independent transaction and returns `GOAL_SUGGESTION_STALE` (409). On a match, the same draft applier updates the managed goal; `weekly_correction` accumulates `deltaKcal` onto `balance_adjustment_kcal`, then the engine re-evaluates and `GoalEvaluationService.assemble` sets `basis="adaptive"` iff that running adjustment is non-zero.

`GoalProjectionService.dailyEnergyBalance` adds the accumulated `balanceAdjustmentKcal` **on top of** the formula balance for **every** trajectory, maintain included — an accepted correction is a deliberate calibration even on a maintenance goal. This composes with slice 4's per-week segment override as **"override wins per week"**: a week carrying an accepted deload/maintenance override does not feel the adjustment (the override replaces the whole balance for that week), every other week does. The adjustment therefore flows through to each segment's `kcal`, and from there to the day-type training/rest split (§3 above) exactly like the formula balance does.

### Learned expenditure (mezo-zz91i, Part 1)

A **parallel loop to the adaptive review above** — same Monday job, different job entirely: instead of *suggesting* a kcal correction the user must accept, this one *learns* the served base itself and serves it automatically, no approve step. Spec: [`docs/superpowers/specs/2026-09-26-learned-expenditure-design.md`](../superpowers/specs/2026-09-26-learned-expenditure-design.md).

**What is learned.** `ExpenditureFilter` (`engine/service/ExpenditureFilter.java`) is a **3-state linear Kalman filter**, pure/no-Spring, one calendar step per day: `x = [m tissue kg, w transient water kg, B base kcal/day]`. `B` is the same quantity the formula calls `bmr × neat` — kcal/day excluding movement. Movement (`planEatPerDay + extraKcal_d`, off `WeeklyScheduledActivityService` + `WorkoutWindowQueryService.movementBetween`) is a *known input*, never learned, so a skipped planned session correctly lowers `B` rather than being absorbed as noise. A day with usable logged intake links weight to `B` through `Δm = (I − B − movement)/ρ` (`ρ = mezo.goal.kcalPerKg`); an unlogged/excluded day instead drifts `m` by the goal's own daily balance (wide variance) and carries **no information about `B`**. A weigh-in updates `m + w + G` where `G` is a deterministic glycogen-water term off an EWMA of carbs (so a sustained carb change is read as water, not fat, and does not slowly bleed into `B`). Seeded at window start with `B₀ = formulaNeatBaselineKcal`, `var = bootstrapUncertaintyKcal²` (the previously-unused `mezo.goal.bootstrapUncertaintyKcal`, now consumed). Output: posterior `(B̂, σ̂)` at the end of *yesterday* (today is never used).

**Which days may teach it (owner decision L2).** `IntakeDayClassifier` (pure) — `UNLOGGED` (`kcal ≤ 0`), `SUSPICIOUS` (`kcal < 0.60 × refMedian`, the median of the prior 28 logged days; fewer than 5 → the day's own **served target** is the reference instead of maintenance, so a compliant cut day is never misjudged as under-eating), `MARKED_INCOMPLETE` (Part 2's per-day mark — no marks exist yet in Part 1, so every suspicious day is simply excluded), else `USABLE`.

**The weekly step (owner decisions L1/L5), `ExpenditureStepPolicy`.** Eligibility gates first: `holding` when the ended week has `< minUsableDaysPerWeek` (4) usable days or `< minWeighInDaysPerWeek` (2) weigh-ins. Otherwise `delta = B̂ − prevApplied`; below `deadBandKcal` (30) the step is 0; a **new** direction moves only half (`delta / 2` — "more likely the scale is slow than that expenditure changed"), a **confirmed** direction (same sign as last week's) moves the full `delta`, both clamped to `±maxStepKcal` (150). The result is railed (`ExpenditureStepPolicy.rails`) so the served base never leaves `formulaBase × (1 ± maxDeviation 0.35)` and never drops below `bmr × minBaseBmrRatio 1.10` — a lower base is physiologically implausible and flags bad data, not a real metabolism. Status: `HOLDING` / `UPDATED` (a non-zero step) / `LEARNING` (σ̂ still `> mediumConfidenceSdKcal` after a zero step — confidence LOW) / `STABLE`. Confidence from σ̂ alone: `≤ 100` `HIGH` „Biztos", `≤ 200` `MEDIUM` „Közepesen biztos", else `LOW` „Még tanulok".

**The orchestrator**, `ExpenditureLearningService.reviewWeek(userId, weekStart)` (`@Transactional`): resolves the active goal's formula bootstrap, gathers the window (`windowDays` = 120 back from the reviewed week, plus a `referenceDays` lookback for the classifier), classifies every day, runs the filter, decides the step, **upserts** the week's `expenditure_estimate` row (idempotent — a re-run replaces the row and recomputes from the *previous* week's row, so a deploy re-run or a Part-2 day-mark edit is always safe), then **supersedes any open `weekly_correction` suggestion** (owner decision L4 — a learner never also gets the weight-only nudge) and calls `goalEngineService.recomputeActiveGoal` so the new base is served immediately. Returns empty when learning is off, the goal has no bootstrap yet, or — for a brand-new (non-existing) learner only — there are fewer than `minUsableDays` (10) usable days in the last 28; an **existing** learner is never handed back to the fallback: a week with no anchor (no weigh-in) is written as `HOLDING` instead, carrying the previous belief and applied base forward (spec §7).

**Fallback reference (`ExpenditureLearningService.balanceOn`).** With too little of the user's own recent history, the classifier judges a day against **that day's own served target**: `prevApplied + planEat + that day's goal-week balance`, where `prevApplied` is the previous week's row's `appliedBaseKcal` when one exists, else `formulaBase + goal.balanceAdjustmentKcal` (the adjustment is only added here — a prior row's applied base already carries it, so adding it again would double-count a moved base). The goal-week balance is the prescription segment covering the date's goal-week, `0` before the goal started or with no prescription yet. This is deliberate: judging a compliant cut day against undifferentiated maintenance would flag every on-plan deficit day as suspicious. The spec (§5.2/§5.3) always specified the served target here.

**How it learned — the persisted explanation (`mezo-y72o3`, „Hogy tanultam?”).** `reviewWeek` is split into a replay (window, classification, filter days + trace, `prevApplied`) and a decide-and-persist step. The same run also builds an `ExpenditureExplanationJson` and stores it on the week's row (`explanation jsonb`), so the explainer never replays the filter on the request path. The explainer is presentation on top of an already-decided week: a `RuntimeException` from it is caught and logged (`warn`), and the week's decision is persisted with `explanation = null`, never rolled back (hardening, `mezo-y72o3`). `ExpenditureFilter.runWithTrace` returns the posterior plus one `DayTrace{date, tissueKg, waterKg, glycogenKg}` per day from the first weigh-in on (the state after that day's update; `glycogenKg` is the `G` the day's weigh-in was priced against, so `m + w + G` is the de-noised scale trend); `run` delegates to it with bit-identical numbers (a frozen-bits test guards this). The pure `ExpenditureExplainer.explain` (`engine/service/`) turns window + classification + trace into: `dataStart` (the first window day with a logged intake or a weigh-in) and counts (`usableDays`, `weighInDays` over the window; `unloggedDays` only from `dataStart` on — the empty days before a user's data began are not "unlogged"; `historyWeeks` = ceil(days from the first weigh-in to the window end / 7)); `avgIntakeKcal` and `avgMovementKcal` over the same usable days (`null` with none); `tissueRateKgPerWeek` (trace tissue end − start, per week) and `tissueKcalPerDay` (× `kcalPerKg`); `simpleBaseKcal = avgIntake − tissueKcal − avgMovement` from the shown rounded parts (`null` when either is missing — e.g. a HOLDING week without weigh-ins); `startBaseKcal` (this week's `prevApplied`); `excludedDays` over the whole window; `waterEvents` (a run of consecutive days whose glycogen rose ≥ `water-event-kg` vs 7 days earlier, reported once: first date, max rise); and `series`, the last 56 days (intake + `usable|suspicious|marked|unlogged`, the day's mean weight, `trendKg = m + w + G`, `tissueKg`; trend/tissue `null` before the first weigh-in). Kilograms are 2-decimal `BigDecimal`s.

**Serving the learned base — the ONE served-target rule**, `LearnedBaseResolver.apply(userId, formula)`: called from the same place the formula bootstrap is computed. When the user has an `expenditure_estimate` row, it replaces `neatBaselineKcal` with the row's `appliedBaseKcal` — **re-railed against TODAY's formula** (which can have moved since the row was written, e.g. after a weigh-in changes weight/profile), never the stale value baked into the row — and `tdee` follows (`= learnedBase + weeklyEatKcalPerDay`). The formula value is kept alongside as `formulaNeatBaselineKcal` so (a) the next weekly run's `prevApplied` fold-in reads the formula, not a compounding learned-on-learned value, and (b) the Fuel breakdown sheet can show both numbers. Nothing else in the projection/prescription pipeline changes — every segment, macro split, guard and Fuel bridge downstream of `tdeeBootstrap.neatBaselineKcal` picks up the learned value automatically, exactly the way `EnergyBase.neatBaselineKcal` already worked for the formula.

**Double-correction trap, closed.** `goal.balanceAdjustmentKcal` (accepted `weekly_correction` deltas, §3 above) is folded into a learner's **first** estimate (`prevApplied` defaults to `formulaBase + adjustment` when no row exists yet) and from then on must not also be added by `GoalProjectionService.dailyEnergyBalance` — it now skips the addition whenever `bootstrap.learned()` is true (`TdeeBootstrapJson.learned()` — `baseSource == "learned"`), for every trajectory, maintain included. The adjustment itself is never cleared (switching learning off in Part 2 will restore it verbatim).

**The Monday dispatcher, `AdaptiveReviewJob`.** Per user: `ExpenditureLearningService.reviewWeek` runs first for the week that just ended; a non-empty result (HOLDING included) means the user is a learner this week and the old `AdaptiveReviewService.reviewUser` weight-only suggestion is **not** called. Only a non-learning user (empty — not eligible, or the goal has no bootstrap) falls through to the existing suggest-only path. The two are exclusive by construction (owner decision L4), never both, never neither for an eligible user.

**Deploy rollout, `ExpenditureRolloutRunner`** (`feature/goal/`, `@Order(208)` — after `ActivityModelMigrationRunner` (207) so it reads already-migrated goals): a one-shot `CommandLineRunner`, all profiles including prod, that reviews the last completed week for every active-goal owner **who has no `expenditure_estimate` row yet**. Idempotent (a second boot finds the row and skips); a per-user exception is caught and logged, never aborting the rest of the rollout. This is what replays a user's existing history into their first estimate on launch (an engineering-delegated call, spec §2). **Since `mezo-y72o3`** it also backfills the explanation: an active-goal owner whose *latest* row has `explanation = null` (written before the explainer existed) goes through `ExpenditureLearningService.backfillExplanation` — **explain-only**: the week is replayed and ONLY `explanation` is set; status/posterior/applied/step/direction/confidence stay as served, no goal recompute, no suggestion supersede. A backfilled explanation therefore reflects the data *as of the backfill* (a meal edited since the original run shows in it). A learner with nothing to replay is logged at info; the next boot skips a filled row. When `mezo.goal.expenditure.enabled` is false the runner skips the whole backfill branch up front, since every per-user call would no-op anyway and only emit „nothing to replay” log lines.

**Config — `mezo.goal.expenditure.*`** (`GoalEngineProperties.Expenditure`, `application.yml:232`): `enabled` (true — global switch; a per-user one is added by Part 2, below), `window-days` (120), `sigma-scale-kg` (0.35), `sigma-tissue-kg` (0.02), `intake-error-pct` (0.10), `sigma-unknown-kcal` (800), `water-phi` (0.90), `sigma-water-kg` (0.20), `sigma-base-kcal` (12), `glycogen-kg-per-g` (0.007), `glycogen-max-kg` (2.0), `glycogen-alpha` (0.4), `suspicious-ratio` (0.60), `reference-days` (28), `min-reference-days` (5), `min-usable-days` (10 — new-learner eligibility over the last 28), `min-usable-days-per-week` (4 — below: HOLDING), `min-weigh-in-days-per-week` (2 — below: HOLDING), `max-step-kcal` (150), `dead-band-kcal` (30), `max-deviation` (0.35 — the plausibility rails), `min-base-bmr-ratio` (1.10), `high-confidence-sd-kcal` (100), `medium-confidence-sd-kcal` (200), `water-event-kg` (0.8 — `mezo-y72o3`: a 7-day glycogen-water rise at least this big is listed as a water event in the explanation). Most constants are exercised by the synthetic-scenario tests (spec §9); not every one has a dedicated scenario.

### Learned expenditure Part 2 (mezo-3n2so) — marks, re-chain, the switch, the weekly card

Makes Part 1's silent learning **visible and correctable**. Spec: [`docs/superpowers/specs/2026-09-27-learned-expenditure-part2-design.md`](../superpowers/specs/2026-09-27-learned-expenditure-part2-design.md) (parent: [`2026-09-26-learned-expenditure-design.md`](../superpowers/specs/2026-09-26-learned-expenditure-design.md)).

**Day marks, `intake_day_mark`.** A user can mark any past or today's day COMPLETE or INCOMPLETE (three FE entry points — the weekly sheet, the learning page's last-14-days list, the day log, §5/[`fuel.md`](fuel.md) §2). `IntakeDayMarkService.mark`/`.clear` (`feature/goal/service/IntakeDayMarkService.java`) upsert/delete the per-user-per-day row (unique `(created_by, day)` where not deleted) and immediately trigger a re-chain — **400** on a future date, **409** when the day has no logged intake (marking an unlogged day is meaningless — `IntakeDayClassifier` never even sees it). `replay` now loads marks for the classifier window from `IntakeDayMarkRepository` and passes them to `IntakeDayClassifier.classify` (`COMPLETE`→TRUE, `INCOMPLETE`→FALSE) instead of Part 1's `Map.of()`; the classifier rule is unchanged (an unlogged day still wins over any mark).

**Immediate re-chain (owner decision P1), `ExpenditureLearningService.rechainFrom(userId, day)`.** Resolves `weekStart(day)`; if that week is the current, not-yet-reviewed week, it returns without recomputing (the mark is saved and simply counts in next Monday's run). Otherwise it re-runs the week step for `weekStart(day)` **and every later week that already has a row, ascending**, via a `persistOnly` variant of the weekly step that skips the per-week goal recompute/supersede — then fires **one** `recomputeActiveGoal` at the end, only if the latest row's `appliedBaseKcal` actually changed. Returns `{appliedBaseBeforeKcal, appliedBaseAfterKcal}` for the caller's change line. A re-chain runs inside the mark's own transaction (§7 below) and always uses **today's** formula base and plan EAT to replay past weeks — rows can drift slightly from what they'd have been if replayed at the time; this is documented, deliberate behavior (spec §4 traps), not a bug.

**The switch (owner decision P3), `diet_settings.learning_enabled`** (default `true`, ghost `mezo.diet-settings.default-learning-enabled: true`), read through the existing `DietPreferencesPort`/`DietPreferences.learningEnabled()`:
- **Off never stops learning** — the weekly job keeps computing and writing `expenditure_estimate` rows every Monday, exactly as before; only the *serving* changes.
- `LearnedBaseResolver.apply` now checks the switch first: off → serves the formula base **+ `balanceAdjustmentKcal`** (the accepted-correction total, exactly as a non-learner would see it) instead of the learned `appliedBaseKcal`; on → Part 1's re-railed learned base as before.
- `reviewWeek` is **not** gated by the switch — but while off it does **not** supersede an open `weekly_correction` suggestion (a user who turned learning off should still be able to accept the weight-only nudge).
- `AdaptiveReviewJob`: switch off → runs the (silent) learning step **and** the weight-only suggestion path (both, unlike Part 1's always-exclusive rule, which only holds while a user is actively served the learned value); switch on → Part 1's behavior (learning, suggestion only as the empty-result fallback).
- `ExpenditureRolloutRunner` is unchanged — it runs the learning step regardless of the switch, which is switch-agnostic by construction.
- Turning the switch back on serves whatever was learned silently while it was off, with the settings page showing the resulting kcal delta after Mentés (§5.5 below).
- Turning the switch back on (a stored false → true flip in `DietSettingsService.setSettings`) first retires the active goal's open `weekly_correction` via `GoalEngineService.retireWeeklyCorrection` (`superseded`, no owner decision) — a correction proposed while the formula served would, once accepted, write a `balanceAdjustmentKcal` the learned path ignores (final-review fix, `DietSettingsApiIT.testSetDietSettings_shouldSupersedeOpenWeeklyCorrection_whenLearningIsSwitchedOn`).

**Card worthiness, `WeeklyCardPolicy.worthSaying(row)`** (`engine/service/WeeklyCardPolicy.java`) — a pure predicate shared by the weekly-card read and the bell (owner decision P4): a row is worth surfacing when `stepKcal != 0`, or it has excluded days, or its status is `HOLDING`. A quiet week (no step, nothing excluded, not holding) gets neither a card nor a bell.

**Dismissal, `expenditure_estimate.dismissed_at`** — the weekly card's per-week, server-side dismiss (so it disappears on every device). The `decideAndPersist` upsert **preserves** `dismissed_at` across a re-chain (clearing/resetting it would resurrect a card the owner already closed).

**`ExpenditureInsightService`** (`feature/goal/service/ExpenditureInsightService.java`) is the read-side orchestrator behind the four new GET endpoints below: the week history, the current weekly card (`204` when `worthSaying` is false, the row is already dismissed, the row isn't for `thisMonday − 7`, or the switch is off), the dismiss action, and the live per-day statuses (`IntakeDayStatus`, computed fresh with `IntakeDayClassifier` + marks — **not** read off a persisted explanation, so a mark made seconds ago is reflected without waiting for a re-chain to finish writing a row).

**Bell, `AppNotificationKind.EXPENDITURE_WEEK`** (`expenditure_week`, key ≤32, feed-only — `familyKey` null, deeplink `/fuel/tanulas`). Emitted **only** by `AdaptiveReviewJob` (never by the rollout runner or a re-chain, owner decision — a re-chain is a correction, not new news), one event per user per week, only when the switch is on and `WeeklyCardPolicy.worthSaying` is true; an `@Async @TransactionalEventListener(AFTER_COMMIT)` listener emits with dedup key `expenditure_week:<weekStart>` (the same idiom as `GoalSuggestionNotificationListener`, §5).

**Carry-over, `basis="learned"`.** `GoalEvaluationService`'s basis derivation now distinguishes a served learned base from an accepted `weekly_correction`: `prescription.basis = "learned"` when `TdeeBootstrapJson.learned()` is true (switch on, a row exists), else the existing `"adaptive"`/`"formula"` rule unchanged. The contract enums carry it: `GoalPrescription.basis` is `formula | adaptive | learned` and `GoalOverviewDiet.basis` is `formula | adaptive | learned | unavailable` (`api/feature/goal/goal.yml`; the enum once lacked `learned` and every goal read 500'd for a learner — `GoalOverviewApiIT.testGoalReads_shouldReturnLearnedBasis_whenLearnerHasTheSwitchOn`). The `Cél` diet page labels it „Tanult alap”. FE-facing confidence stays lowercase everywhere the new endpoints emit it (`low|medium|high`, §6.5's rule, unchanged by Part 2).

## 5. Integrations

**Companion source access:** Chat receives the active weight trajectory, start/target weight and dates, plus the date-current stored prescription in its baseline. Goal history, full prescriptions, timeline links and suggestions are available through the full-source reader. See [companion source access](companion.md#complete-personal-source-access-mezo-rj21410) for ownership, pagination and continuation rules.

The engine is a **consumer hub** — it reads three other domains and writes one:

- **← Biometrics/weight (the spine).** *Contract:* `WeightTrendResponse` (EWMA series + rates + sufficiency) from `WeightTrendService.computeTrend(userId)`. The projection uses it for rate reconciliation; the muscle guard uses `last4wRateKgPerWeek` for the rate-cap. The same service backs `GET /api/biometrics/weight/trend`, which the FE `useWeight` folds into `weightTrends` ([`_platform-data-layer.md`](_platform-data-layer.md) §4).
- **← Biometrics/weight, raw daily means (the learned-expenditure filter's scale input, `mezo-zz91i`).** *Contract:* `WeightTrendQuery.dailyMeanWeightKg(userId, from, to)` (`techcore/query/WeightTrendQuery.java`, implemented by `WeightTrendService`) — the owner's weigh-ins in a range, same-day entries averaged, a day without one absent. Read through the **same feature-neutral techcore seam** the Goal Hub overview already uses (above), deliberately, so `ExpenditureLearningService` gains no new direct edge into biometrics (the frozen goal↔biometrics cycle, `mezo-ah18.15`). This is a *different* read than the EWMA trend: the filter wants raw daily means, not the smoothed spine.
- **← Biometrics/profile.** *Contract:* `BiometricProfileEntity` (sex, heightCm, birthDate, bodyFatPct, **activityLevel**) → the TDEE bootstrap. A missing profile is the graceful path (no throw).
- **← Biometrics/sleep (the sleep-target port, mezo-3g5w).** *Contract:* the sleep-owned **`SleepTargetPort.targetHours(userId)`** (`feature/biometrics/sleep/service`, implemented by `SleepAnchorResolver`) resolves the prescription's `sleepTargetH` from the user's saved `sleep_goal.targetMinutes`, or the config ghost `mezo.sleep.default-target-min` (8.0h) when no sleep-goal row exists — replacing the old hardcoded `DEFAULT_SLEEP_TARGET_H` seed inside `GoalEvaluationService.assemble` (which keeps only a defensive null-fallback of 8.0 for a careless caller). Never null by contract. Covered by `feature/biometrics/sleep/service/SleepTargetResolverTest` (goal-row vs config-ghost resolution) and `GoalEvaluationServiceIT.testAssemble_shouldCarryProvidedSleepTarget_whenSegmentsEmitted` (the resolved value rides onto every segment).
- **← Biometrics/sleep (the adaptive-review sleep-adequacy port, Diet Plan slice 5 `mezo-r4n7`, ADR [0012](../decisions/0012-consumer-owned-llm-ports.md)).** *Contract:* the goal-owned **`SleepAdequacyPort.sleepDebted(userId, today)`** (`engine/port/SleepAdequacyPort.java`), implemented by `GoalSleepAdequacyAdapter` (`feature/biometrics/sleep/service`) — asks "is the owner in sleep debt?" without depending on companion (which owns a *different* flag variant, `FlagEvaluator.sleepDebt`, and may be switched off). Same deficit math, reimplemented independently over the review's own window (`mezo.goal.adaptive.sleepDebtNights` = 7 vs the companion flag's 3-night window) — see §3 for the full math and the sign-convention self-review note. Covered by `GoalSleepAdequacyAdapterIT`.
- **← Train (mesocycles + running blocks).** *Contract:* the goal's `GoalPlanLinkEntity` rows + the linked `MesocycleEntity.phaseCurve` (the per-week phase class) / `RunningBlockEntity.structure` (sessions-per-week) read via the Train repos (ownership-checked), and `MuscleGroupVolumeLogEntity` + `ExerciseSetEntity`/`ExerciseRepository` for the guards (the strength leg reuses `ExerciseRecordService`'s identity idiom, and both now share the same `OneRepMax` eligibility/e1RM gate). See [`train.md`](train.md) for those aggregates.
- **← Train (meso lifecycle event — the meso→diet suggestion bridge, Diet Plan slice 4 `mezo-ktg8`).** *Contract:* Train publishes `MesocycleActivated`/`MesocycleClosed` (`feature/train/MesocycleActivated.java`/`MesocycleClosed.java`) on the real activate (`TrainService.activateMesocycle`) / close (`TrainService.closeMesocycle`, `MesocycleReportService.regenerate`) branches only, never on an idempotent re-activate/re-close. The goal-owned `MesoLifecycleSuggestionListener` (`feature/goal/service/`, `@Async @TransactionalEventListener(AFTER_COMMIT)` — the same `MesoReviewListener` idiom the companion uses for `MesocycleClosed`, [`train.md`](train.md) §5) resolves the owner's active goal and calls `GoalSuggestionTriggerService.onMesoLifecycle` — a **suggestion probe**, not `evaluate` (§3's recompute-trigger table). One-way: Goal never imports Train's write path for this event, it only reads Train's repos elsewhere (above).
- **← Train weekly scheduled EAT (the training-energy port, mezo-eujg).** *Contract:* the train-owned **`WeeklyScheduledActivityService`** (`feature/train/service`) — `totalWeeklyEatKcalPerDay(userId, weightKg)` (the bootstrap's `weeklyEatKcalPerDay`) + `scheduledWeeklyEatKcalPerDay` / `runWeeklyEatKcalPerDay(sessions, weightKg)` (the projection's per-segment gym+sport vs running EAT). ## 6. How to use it (consume)

**Backend** — never call a single engine service to "get the prescription"; call the orchestrator so the artifact is assembled + persisted atomically:

```java
goalEngineService.evaluate(userId, goalId);   // @Transactional; assembles + persists; graceful on no profile
```

Read the result off the goal via the normal `GoalService.getGoal` path (the `GoalMapper` projects the jsonb into `GoalResponse.prescription`/`tdeeBootstrap`). The individual services (`WeightTrendService`, `TdeeBootstrapService`, …) are public and pure — reuse them directly only for a *read-only* derivation (e.g. another feature wanting the EWMA trend), never to mutate goal state.

**Frontend** — read the prescription from `useGoal().goalResponse.prescription` (it rides the goal, no separate hook), and trigger a fresh compute with `useGoalActions().evaluate(goalId)` (POST `/evaluate`, invalidates `['goals']` + the goal timeline). See [`_platform-data-layer.md`](_platform-data-layer.md) §2/§4 for the dual-mode wiring; never call the API client directly from a view.

## 7. How to extend it

Add a tunable, a guard leg, or a projection input — always config-first, contract-first, integration-tested:

1. **New tunable** → add the field to `GoalEngineProperties` (with its validation + a `//` research-range comment) and a default to `mezo.goal.*` in `application.yml`. Never hardcode or `@Value` it ([`configuration_conventions.md`](../references/configuration_conventions.md)).
2. **New engine output field** → contract-first: edit `api/feature/goal/goal.yml` (`GoalPrescription`/`…Segment`), `cd api/generate && npm run generate:api`, then mirror the field on `GoalPrescriptionJson`/`Segment` and project it in `GoalMapper`. An additive jsonb field needs **no migration** (it rides the existing column).
3. **New guard / projection logic** → extend the pure service (`GuardEvaluationService` / `GoalProjectionService`); keep it side-effect-free and config-driven so it stays unit-testable, and add the assembly hook in `GoalEvaluationService`. Follow [`spring_patterns.md`](../references/spring_patterns.md) (constructor DI, `@Transactional` only on the orchestrator).
4. **New recompute trigger** → call `goalEngineService.evaluate(userId, goalId)` from the triggering `@Transactional` service method; rely on the graceful no-profile path (never guard with "only if a profile exists").
5. **Test** integration-first ([`testing_standards.md`](../references/testing_standards.md)) against real Postgres; add data via populators; both FE test modes stay green.

## 9. Decisions, gotchas & deferred

**Key decisions** (spec [`2026-06-18-goal-system-design.md`](../superpowers/specs/2026-06-18-goal-system-design.md)):
- **EWMA trend is the rate spine, not a fixed projected deficit** (§4) — once data is sufficient, the observed trailing-4w slope replaces the formula seed.
- **Training energy is explicit scheduled EAT, not a multiplier** (§6.3, mezo-eujg; net model mezo-32m82) — maintenance = BMR×NEAT (non-exercise only) + weekly scheduled gym+sport EAT + per-segment running EAT (all the net activity-energy model, moderate band, via `WeeklyScheduledActivityService`); meso phase is a zero-TDEE segment boundary, volleyball now counts through the weekly schedule. Adding training explicitly (rather than via a `BMR × PAL` multiplier that bakes it in) is what lets Fuel add the day's live net activity kcal on top without double-counting.
- **Soft guards (D9) + heuristic gate (D10) never block** — the verdict only colours the surface; `evaluate` never throws on a model-shape problem.
- **Graceful no-profile path** — `missingProfile` returns a real prescription with a feasibility note (Task-9 recompute triggers rely on this).
- **Adaptive TDEE is a weekly suggest+approve loop, not a live back-calc** (Diet Plan slice 5, `mezo-r4n7`, §3) — a Monday job compares the EWMA-observed rate to the target rate and proposes a small, dead-banded, clamped kcal correction (`AdaptiveCorrectionService`); the owner accepts or dismisses it exactly like a `phase_change` suggestion, and only on accept does `goal.balanceAdjustmentKcal` accumulate and `prescription.basis` flip to `"adaptive"`. The engine never auto-applies a correction — this is the same suggest+approve philosophy as the meso→diet bridge (§5), applied to the kcal number itself.
- **Learned expenditure is the opposite philosophy on purpose — automatic, not suggest+approve** (`mezo-zz91i`, owner decision L1, §3) — once a user is a learner, the weekly step is applied and served without a review step; the "explain what changed" transparency comes from the Fuel confidence line and the Part 2 weekly card/history page, not from a suggestion the owner must accept. Learning and the adaptive-correction suggestion are **mutually exclusive per user per week while the switch is on** (owner decision L4, enforced by `AdaptiveReviewJob`): a learner never also gets a `weekly_correction`; a non-learner keeps the old suggest+approve path unchanged. **Since `mezo-3n2so`** the exclusivity is switch-gated, not absolute: with the switch off, the job runs both the (silent) learning step and the weight-only suggestion path (§3 „Learned expenditure Part 2").
- **A day mark is a correction, not new data (`mezo-3n2so`)** — marking or clearing a day re-chains every later reviewed week from the classifier onward, replaying with **today's** formula/EAT, not the values that were live when each of those weeks originally ran; the resulting rows can drift slightly from a hypothetical "replay at the time" run. This is documented, deliberate behavior (spec §4), the same trade-off Part 1 already made for the rollout/backfill runners.

**Gotchas:**
- Age/`computedAt` use `LocalDate.now()`/`OffsetDateTime.now()` directly (no `Clock` bean — codebase convention); the services are otherwise pure.
- `neat` is stored unrounded (a multiplier, not kcal); `bmr`/`neatBaselineKcal`/`weeklyEatKcalPerDay`/`tdee` are rounded (2 dp).
- `proteinMonitored` is **always false** — the protein TARGET is prescribed and, since Diet Plan slice 2 (`mezo-3g5w`), Fuel's meal scorer already judges every logged meal's macros against that same goal-aware target (`FuelDayService.dailyTargets` → the 5-arg `MealScoringService.scoreMeal`, see [`fuel.md`](fuel.md) §5). The guard's **own** closed loop — comparing the day's/week's actually-logged protein total against the prescribed target to flag a shortfall on the recept card — is **still not built**; Diet Plan slice 5 closed the analogous *energy* loop (adaptive kcal correction) but deliberately left protein monitoring alone (a separate, still-open gap; a note records the deferral and it must **not** downgrade the verdict).
- **Adaptive-correction sign convention is a deliberate spec deviation** (§3) — the Diet Plan spec (`docs/superpowers/specs/2026-09-02-diet-plan-design.md` §6.6) wrote `deltaKcal = clamp((observedRate − targetRate) × 7700 / 7, ±maxStep)`; `AdaptiveCorrectionService` uses `(target − observed)` instead, because the worked examples (a too-slow cut must deepen the deficit, i.e. a *negative* delta) only hold with that sign. If a future change to this math looks like it's "fixing" the sign back to match the spec prose, check the worked examples first — they are the source of truth, not the Diet Plan spec's §6.6.
- **The sleep-debt guard is a second, independent implementation**, not a reuse of companion's `FlagEvaluator.sleepDebt` — same math, but its own window (7 nights vs the flag's 3) and its own config (`mezo.goal.adaptive.*`), so the adaptive review works even with the companion switch off. Don't conflate the two when changing sleep-debt math — a fix to one does not touch the other.
- **A bounded transient overshoot after a correction is deliberate, not a bug** — the EWMA trend window lags a few days behind an accepted correction's effect, and once it catches up the dead-band stops the review from churning out another nudge chasing the last one; MacroFactor's own adaptive algorithm accepts the same bounded lag rather than over-correcting on noisy short-term feedback.
- **A learning user who stops logging is never handed back to the fallback** (spec §7, a known limitation, revisit if it matters) — once `expenditure_estimate` has a row, `ExpenditureLearningService` always writes one for that user again next week, HOLDING included; the applied base simply freezes rather than the user quietly reverting to the weight-only `weekly_correction` suggestion.
- **The fallback reference** (§3) — a day with too little of the user's own recent history is judged against **that day's served target**, not undifferentiated formula maintenance, so a compliant cut/bulk day is never misread as suspiciously low/high intake. This matches the spec's §5.2/§5.3, which always specified the served target.
- **The Kalman filter is a genuinely separate estimator from the EWMA weight-trend spine** — `ExpenditureFilter` reads raw daily-mean weigh-ins straight off `WeightTrendQuery.dailyMeanWeightKg`, never the smoothed `WeightTrendService.computeTrend` series; the two coexist (the trend still drives rate reconciliation and the muscle guard, §3/§5 above) and must not be conflated when changing either.
- **Prior art, now in the research wiki:** [Trend Arrows and Baselines](../research/concepts/trend-arrows-and-baselines.md) (the rolling-window/arrow pattern this engine and `lifegoal.md`'s scorer both draw on), [Idempotent Daily Recompute](../research/concepts/idempotent-daily-recompute.md) (the one-raw-fact/re-derive/safe-to-rerun shape behind this engine's recompute jobs), and the [Exist.io](../research/entities/exist-io.md) entity (the baseline idea's origin). **Read those pages before citing a source from memory:** the ingest found one of the life-goal design specs' own citations does not support the claim it was attached to, and the correction lives on the wiki page, not repeated here.
