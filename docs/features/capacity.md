## 1. Summary

Capacity answers two numbers per day: **demand** (calendar events scored for mental / social / physical load, plus the planned or logged training) and **capacity** (a personal base scaled by sleep, resting HR, HRV, yesterday's load, fuel, kímélő mode, the morning check-in). Their ratio gives a verdict word `laza | rendben | szoros | tulSok`. Everything numeric is **pure and deterministic**; the model only labels events (and may rephrase the reason line).

K1 ships: the phone sends every calendar field; a **background** model scoring of events with a rule fallback; the load model and learning state; a nullable `capacity` block on the Boop brief; the K3/K4 tables (created now, empty). Driving spec: [`2026-11-21-boop-kapacitas-design.md`](../superpowers/specs/2026-11-21-boop-kapacitas-design.md) §5.1–5.4; plan [`2026-11-21-boop-kapacitas.md`](../superpowers/plans/2026-11-21-boop-kapacitas.md) Tasks 1–6.

Feature flag: `mezo.capacity.enabled` (default true); off → the brief carries `capacity: null`.

## 3. Architecture & data flow

```
phone (EventKit) → PUT /api/wearable/calendar-days → CalendarSnapshotService.replace  (upsert by external_id, soft delete)
        └ publishes CalendarDaysReplacedEvent (in tx) ─AFTER_COMMIT, @Async→ EventScoringRunner.scoreAhead(owner)
              today..today+8 → EventScoringService.scoresFor → ONE cheap-tier CompanionLlm call (45 s) → calendar_event_score (source llm | rule)

GET /api/boop/brief → BoopBriefService → BoopCapacityPort.read → BoopCapacityAdapter → CapacityDayService.day
      events (stored-or-rule score, NEVER a model call) → DemandCalculator → demand units + hourly[19]
      sleep/metrics/train/checkin/meal ports → CapacityCalculator → capacity units + factors → Verdicts.word
```

- **No model call on a request thread.** `CapacityDayService.build` reads `storedOrRule` scores only and calls `EventScoringRunner.requestIfUnscored`, which starts a background run (throttled to once per 10 min per owner) and returns at once. The first read of an unscored day shows rule scores; the next read shows the model's.
- **Single-flight per owner**: a trigger while a run is in flight flags one extra pass instead of starting a second run (the extra pass finds cached scores, so it only calls the model for events changed meanwhile). Failures are logged and swallowed; a stored `rule` row is re-asked by the next run.
- **Failure isolation**: `BoopBriefService` catches any capacity failure, logs a warning and serves the brief with `capacity: null`; the model timeout (45 s) only ever blocks the background thread.
- **Ports/adapters**: capacity reads other features only through `capacity/port/*` implemented by `capacity/service/Capacity*Adapter`; the brief reaches capacity through `BoopCapacityPort` (implemented by `BoopCapacityAdapter`). `wearable` imports nothing from capacity (it only publishes the event).
- **Load model** (spec §5.3): per event a duration-weighted sum of mental/social/physical (`RuleEventScore` when no model score); events clipped to the day's own hours (midnight-crossing events count only their hours on each day); a back-to-back block of ≥ `sequence-block-min` minutes costs ×`sequence-factor`, a gap ≥ `gap-credit-min` earns a small credit; `restores` events subtract half. Training counts as planned (type, duration), then as logged (volume/RPE). Capacity = base (28-day median of his demand on days rated ≥ 4, else his median day, else `default-base-units`) × `headroom` × the factor multipliers (sleep vs need, RHR vs baseline, HRV, yesterday's load, fuel, kímélő floor, check-in). Verdict from demand / capacity at the `verdict.*` thresholds. **Learning** (`LearningState`): fewer than `learning.min-days` full-signal days or `learning.min-labels` labelled days → `tanulo = true`.

## 4. Data model & API

**Config `mezo.capacity.*`** (`CapacityProperties`, defaults in `application.yml`): `enabled`, `verdict.laza|rendben|szoros` (0.6 / 0.9 / 1.0), `headroom` 1.25, `sequence-factor` 1.3, `sequence-block-min` 90, `gap-credit-min` 15, `learning.min-days` 14, `learning.min-labels` 5, `notes-max-chars` 2000, `default-base-units` 6.0; reserved for K3/K4: `proposals.max-per-week` 5, `live.min-interval` PT3H, `sunday.cron` (Sunday 18:00).

**Tables** (changesets `202611211200_…calendar_event_fields.sql`, `202611211210_…capacity.sql`):

| Table | Role | K1 state |
|---|---|---|
| `calendar_event` (+ `attendee_count`, `attendee_names`, `organizer_is_me`, `location`, `recurring`, `availability`, `notes`) | the phone's events, all fields | written |
| `calendar_event_score` | per event + input hash: `mental/social/physical 0–3`, `restores`, `kind`, `confidence`, `source llm\|rule` | written by the runner |
| `capacity_event_feedback` | the owner's "drains / neutral / feeds" correction per event key | written by `EventFeedbackService` (native upsert on `(created_by, event_key)`, revives a soft-deleted row) |
| `day_adjustment` | the ledger: one row per accepted step (K3) | written by `DayAdjustmentService` |
| `capacity_proposal` (+ `fingerprint`, changeset `202611251300_…capacity_proposal_fingerprint.sql`), `capacity_pattern` | K3/K4 proposals, patterns | proposals: stored by `ProposalService` (open → accepted / declined / ignored / undone); patterns: repo only |

**Contract.** `api/feature/wearable/wearable.yml` — calendar events gain `attendeeCount`, `attendeeNames` (≤ 50), `organizerIsMe`, `location`, `recurring`, `availability` (`busy|free|tentative|unavailable`), `notes` (≤ 2000); the per-request cap is 31 days. `api/feature/boop/boop.yml` — the brief gains nullable `capacity: BoopCapacity` = `verdict`, `reason`, `ratio`, `tanulo`, `labelledDays`, `calendarKnown`, `demand[]` (`label`, `start`, `kind`, `level` kicsi/kozepes/nagy/tolt, `eventKey`, nullable `effect` drains/neutral/feeds = his stored label), `factors[]` (`key`, `label`, `value`, `effect` jo/semleges/rossz). Demand items carry `eventKey` = the calendar `external_id` without the trailing `|occurrence` (`EventScoringService.eventKey`), null for training. `api/feature/capacity/capacity.yml` — **`PUT /api/capacity/event-feedback`** (`putCapacityEventFeedback`, body `{eventKey ≤ 200, effect drains|neutral|feeds}`, 204; blank/long key or unknown effect = 400 `VALIDATION_INVALID_VALUE`). The key travels in the body, not the path: device ids carry `/` and `:` (an encoded `/` in a path is refused by the servlet firewall); the server stores it as sent (it never strips again — a device id may itself contain `|`). The label overrides the event's components at read time (`applyFeedback`). The brief's input hash covers the capacity ratio (steps of 0.05), the factors and **each demand item's key + level + label** (so a label regenerates the brief even when the day's units round the same); the demand-bent hourly energy replaces the plain curve (`EnergyCurveModel.hourly` with `capacity.hourly19()`).

**The day-adjustment ledger (K3, `DayAdjustmentService`).** The one list of this week's accepted changes; readers consult it, it never writes `gym_schedule_slot`, the mesocycle, the goal or the season. `applyBundle(owner, proposalId, clientRef)` parses the proposal's `bundle` (`{"steps":[{kind, payload}]}` — `AdjustmentDraft.toBundle/fromBundle`) into typed `AdjustmentPayload` records, validates every step, then writes all rows in one transaction with one `bundle_id` and sets the proposal `accepted` + `decided_at`. It runs under the owner's `CapacityLock` (`pg_advisory_xact_lock`, the `PlannedSkipLock` pattern), so two different proposals accepted at the same moment serialize and the second sees the first one's move (no two moves onto one day). Replaying a `clientRef` returns the rows already written (step 0 carries the `clientRef`, step *i* a name-UUID derived from it — the table's unique key is per row); the same `clientRef` with another proposal → 409 `CAPACITY_CLIENT_REF_REUSED`. Not `open` → 409 `CAPACITY_PROPOSAL_STALE`. Days are the owner's (`mezo.wearable.zone`, injected `Clock`); a day *has started* when it is past, or today with its session running/done. Rules: `MOVE_SESSION_DAY` only within the from-day's Mon–Sun week (422 `CAPACITY_MOVE_OTHER_WEEK`) onto a day with no gym in the raw plan (slot or meso day label), none done, and no other live move there (422 `CAPACITY_MOVE_NOT_EMPTY_DAY`); a running template → 409 `TRAIN_DAY_WORKOUT_RUNNING` (train's rule); a past day → 409 `CAPACITY_DAY_STARTED`. `SKIP_SESSION` goes through train's trusted entry point `PlannedSkipService.upsertForCapacity` (`CapacitySkipPort`) with reason `KAPACITAS` — excused like advice, never the weekly pass; the public `PUT /api/train/skips` refuses `KAPACITAS` (400 `TRAIN_SKIP_REASON_INVALID`) and never re-reasons an existing `KAPACITAS` row (409 `TRAIN_SKIP_CAPACITY_OWNED`). `MOVE_MEAL_ENERGY` `slotKcal` = signed deltas summing to 0 (else 400). `CALENDAR_TODO` rows start `waiting`. `undo` takes back the whole live bundle (skip removed; proposal `undone`) until any of its days started (409 `CAPACITY_DAY_STARTED`; settled → 409 `CAPACITY_ADJUSTMENT_NOT_UNDOABLE`). `expireStale(owner, today)`: a live move whose target gains a planned gym before the day → `expired`; done on its new day, or its target day passed (trained or not — the re-dating stays in history) → `done`; a waiting to-do past its day → `expired`. Reads: `activeFor/activeForRange` (states `active|waiting|done`; a move counts on both days), `list` (any state). The ledger's train checks read the RAW plan through `CapacityTrainPort.gymPlanned/plannedTemplate` — a ledger-aware train reader must never feed back into them. HTTP: `GET /api/capacity/adjustments?from&to` (≤ 62 days), `DELETE /api/capacity/adjustments/{id}` (204). **Calendar to-dos are watched in the sync** (`CalendarTodoWatcher`): after a calendar PUT (`CalendarDaysReplacedEvent`, `@Async` AFTER_COMMIT, own transaction under `CapacityLock`) every `waiting` to-do is checked — `move` → `done` when a live event with the same key (`externalId` without `|occurrence`) starts at the agreed time (±5 min) and no other occurrence is left on the original day; `cancel` → `done` when no event of the key remains on that day (judged only when the PUT carried the day); then `expireStale` runs. Only `waiting` rows are touched, so an expired row is never resurrected; the listener never throws.

**Readers honour the ledger (K3 Task 15).** An accepted change shows everywhere and never in the plan. The reader features own their ports (`train/port/TrainDayAdjustmentPort`, `meal/port/MealDayAdjustmentPort`, `season/port/SeasonAdjustmentPort`, `boop/port/BoopDayAdjustmentPort`); one capacity adapter, `LedgerReadAdapter`, implements all four and depends **only on `DayAdjustmentRepository`** — `DayAdjustmentService` reaches train's services, so the adapter must not, or `WorkoutService → port → … → train` would be a circular bean graph. Rows read: `active`, plus `done` moves (a carried-out move keeps the session on its new day, otherwise past weeks would count it missed); `undone`, `expired` and `waiting` are invisible, and calendar to-dos never touch a reader. What each reader does:
- **Train.** `WorkoutService.findPlannedTemplateForDate(owner, date)` and `getToday` use `effectiveTemplate`: a moved-in session resolves on its new day, a moved-away day is empty (so quest, readiness, proactive, companion and the brief follow too). `getToday` applies today's `LIGHTEN_SESSION` (`round(sets × factor)`, ≥ 1, after the legacy `workout_day_adjustment` delta) and `SHORTEN_SESSION` (`durationEst`). No exercise is dropped. `WorkoutWindowQueryService` (`windowsFor`, `movementBetween`) re-dates the gym slots: a moved-away day has no gym window and no pending gym (unless a workout was logged there anyway), a moved-in day takes the plan day's slot times. `SHIFT_SESSION_TIME` moves the earliest start and `SHORTEN_SESSION` the window length and pending minutes.
- **Effective planned session / days.** `train/service/EffectivePlanService` is the one helper for the read-only prose and flag readers. `plannedSession(owner, date)` returns the template, the label (the actual weekday when moved in), the plan day's slot time, the ledger time (it wins over a one-day override), shortened minutes and sets with lighten. `plannedGymDates` (and its pure static twin) gives the slot weekdays with the moves applied. Users:
  - `BoopDayAssembler` and `BoopDayContext` (the chat AI's "Ma" sessions).
  - `ContextSnapshotAssembler.dayLine`.
  - `MissedWorkoutsRule`, `MomentumAtRiskRule` and `HydrationShortfallProbe`: a moved-away day is not planned, a moved-in day is.

  `PlannedSkipService` gives a moved-in day the virtual kímélő RECOVERY skip, and a moved-away day none. `startWorkout` stamps today's weekday label on an instance of a session moved onto today. `getToday` applies today's lighten/shorten only when the resolved template is today's effective one.
- **Fuel.** No `FuelDayService` change: `pendingMovementKcal` comes from `movementOn`, so the expected extra follows the session. The target still rises only on a logged session (mezo-tb3s2). A session logged on its new day counts as *planned* there.
- **Day plan.** `DayPlanService.moveEnergy` adds each slot's `MOVE_MEAL_ENERGY` delta to that slot's first budgeted window (carbs follow at 4 kcal/g, floored at 0 g) in both `plan` and `skeleton`. The day total is unchanged. That night's `SHIFT_BEDTIME` replaces the anchor's bed time, so the last window and the bedtime gate move with it. The move applies whole or not at all: if a slot is missing or a window would go below 0 kcal, nothing changes.
- **Brief.** `BoopDayAssembler`: `bedtimeTarget` is the `SHIFT_BEDTIME` of the night starting that day. The session's planned time comes from the plan day's slot. `SHIFT_SESSION_TIME` **wins over** the older `workout_time_override` (both are read, no migration). Lines and minutes follow lighten/shorten.
- **Season.** `AdherenceService.withMoves`: the gym session leaves its old day and is planned on its new one, so it counts once.
- Deliberately unread: `SWAP_SESSION_KIND`. No reader shows a walk or mobility session instead of the gym, and the generator does not produce it. The chat context's bedtime chip still shows the sleep goal: companion cannot read boop's port. `SKIP_SESSION` needs no reader: it is a real planned skip.

### Proposals: generator, cross-effects, words (K3)

- **`ProposalGenerator.forWeek(WeekPicture, patterns, props)`** is pure. `WeekPictureService.picture(owner, monday)` reads the week: the load model's seven days, the train windows split into gym sessions (with the raw plan's template) and sport slots, the calendar, started days, whether a kímélő day touches the week, the raw-plan facts the accept rules need (raw gym days, live move targets/origins, skipped days) and the bedtime in effect per night plus the `SleepNeedRule` need.
- **Rules.** Only `szoros` / `túl sok` days, worst day first; at most `proposals.max-per-week`, ranked by relief = Σ over touched days of (ratio − `verdict.rendben`)⁺ before minus after (a matching pattern adds up to 0.1 and lends its `line` to the why lines).
  - `MOVE_SESSION_DAY` → the lightest empty, open day of the same week whose verdict stays `laza`/`rendben`, not next to a heavy session of the same region (heavy = the load model's heavy lower-body label), preferring a target that leaves ≥ 1 rest day before every sport slot; the session keeps its clock time, so the target must have no timed event or sport slot overlapping it ± 30 min; no two moves to one day.
  - No target, or a kímélő week (never adds load: any draft that raises a touched day's ratio is dropped) → `SHORTEN_SESSION` to ⅔ (5-minute steps); on a `túl sok` day shortening cannot fix → `SKIP_SESSION`.
  - `SHIFT_BEDTIME` + linked `SHIFT_SESSION_TIME`: an event ending after 21:00 and a session before 08:00 next day → bed 90 min after the event (quarter hour up), the session after 15 min falling asleep + the need + 30 min to get going; dropped when it would hit the next day's first event.
  - `MOVE_MEAL_ENERGY` (+200 lunch / −200 dinner) on a `túl sok` day with ≥ `sequence-block-min` back-to-back meetings inside 12:00–18:00.
  - `CALENDAR_TODO`: a meeting ≤ 60 min ending < 30 min before a session → one hour earlier, when that hour is free and starts at 08:00 or later.
  - Never `SWAP_SESSION_KIND` (no reader) or `LIGHTEN_SESSION` (the load model has no sets, so it relieves nothing).
  - At most one draft per session (move / shorten / skip / later start / to-do before it) and per set of touched days — the higher relief stays, so no two cards undo each other.
  - Every draft passes `AdjustmentRules.check` — the pure accept rules `DayAdjustmentService` itself throws from (extracted in K3), with the picture as the plan view.
- **`DraftWeek.apply`** (pure) re-prices the touched days: a leaving session takes its demand item's units, an arriving or shortened one is priced by `DemandCalculator.training`; capacity stays as computed. Training items take no part in the sequence factor or gap credit, so the "after" ratio equals what `CapacityDayService` shows once the row is in the ledger (`CrossEffectCalculatorIT` checks this).
- **`CrossEffectCalculator.effects`** → `Effects`: per touched day verdict/ratio before → after and the fuel day's `pendingMovementKcal` before → after (the session's own figure from `WorkoutWindowQueryService.plannedGymKcal`, the same model and body the preview uses, moves with it); changed rest days before sport; the night's bedtime + need; week totals (gym sessions, Σ served targets + expected extras, 7 × need hours); the active season's goal target date (read via `CapacitySeasonPort.targetDate`, never recomputed).
- **`ProposalWordingWriter`**: `template(draft, effects)` builds title, from → to line, 3–4 effect lines and why lines in the spike's phrasing; the kcal line always says the extra comes with the logged session. A session label is never suffixed by rule: only a vetted table (lábnap, láb, hát, kar, váll, mell, has) gives the move title its object („A hátedzést tedd át szombatra”); any other label reads „Tedd át szombatra ezt az edzést: <label>”. `word(draft, effects)` lets the cheap tier rephrase title/effects/why (llm-log feature `capacity_proposal_words`, 45 s) and keeps it only if the line counts hold and every digit run is already in the template text itself (never the raw facts: their ISO dates would let a „26 perc” through) (`techcore/text/DigitGuard`, shared with the brief's capacity reason). It blocks, so only background paths call it; request paths use `word(…, true)` (template only).

### The Átrendezés API (K3 Task 17, `ProposalService`)

- **`GET /api/capacity/week?monday=`** (`getCapacityWeek` → `CapacityWeek {monday, days[], proposals[], adjustments[], patterns[]}`). It first runs `expireStale(owner, today)`. `days` = the load model's seven days (`verdict` laza|rendben|szoros|tulSok, `label` = the word as shown, `ratio`, `calendarKnown`). For the **current or next** week (his zone) with no stored proposal yet it reads one `WeekPicture`, runs `ProposalGenerator.forWeek`, prices every draft with `CrossEffectCalculator` (one fuel week read), words it with `word(…, true)` (template only) and stores it under the owner's lock (re-checking emptiness, so two first reads store one set). For the current or next week it also settles stale cards: an open proposal whose stored fingerprint no longer matches the week as it is now becomes `expired` (under the lock, re-read, only if still open with the same fingerprint), so a stale card never sits there answering 409 — regenerate fills the week again. Past and later weeks are read-only. `adjustments` = `DayAdjustmentService.list` for the week; `patterns` stay `[]` until K4. A non-Monday → 400 `VALIDATION_INVALID_VALUE` on `monday`.
- **„Ha mindet jóváhagyod” (`allEffects`, K3 Task 19 fix round 1).** `CapacityWeek.allEffects` (nullable) = every **open** proposal's steps applied together as one draft bundle through `CrossEffectCalculator` (the same load model, fuel expected extras, `SleepNeedRule` and week totals as a single proposal — never a sum of per-proposal figures), rendered by `ProposalCompareLines.weekLines`: `Túl sok nap a héten` (all seven days; a touched day takes its after-verdict; fewer = 1), `Szoros nap`, `Heti edzés`, `Heti kalória`, `Alvás a héten` (need × 7 — a later bedtime always keeps the full need), `Súlycél`. Null below two open proposals. It reuses the request's `WeekPicture` when the read built one (fingerprint check or generation), else reads one (≈ one picture + one fuel week per read with ≥ 2 open). Test `CapacityApiIT.weekCarriesAllEffectsOfTheOpenProposals`. The effect lines put a no-break space between a number and „kcal”.
- **The phone (K3 Task 19).** The Átrendezés page and *Minden hatása* (`ios/Boop/Kapacitas/`) read the week through `KapacitasStore` (cache `kapacitas/week`); an offline accept is the outbox kind `dayAdjustment` (`{proposalId, clientRef}`, replay idempotent); entry points are the day page's *Mit tennél át?* and Évad's *A jövő heted*. See [`boop-ios.md`](boop-ios.md).
- **Stored proposal.** `day` = the session's day (`ProposalGenerator.sessionDay`, else the draft's `date`, else its first touched day), `bundle` (`AdjustmentDraft.toBundle`), `facts` (+ `rank`), `effects` jsonb = `{move, lines, compare, touchedDays}`, `title`, `why`, `generator_version` 1, `fingerprint`. `compare` are the *Minden hatása* rows from `ProposalCompareLines.lines(Effects)` — `{label, before, after, favours}`: each touched day's verdict (`Csütörtök terhe`; lighter = 1, heavier into szoros/túl sok = −1), each changed expected extra (`… edzésnapi többlet`, kcal), changed rest days before sport, the night's bedtime + need, `Heti edzés`, `Heti kalória`, `Súlycél`; an unknown figure reads „–”. The API's `CapacityProposal` carries `id, kind, day, status, title, move, effectLines, why, effects (compare rows), steps, touchedDays, decidedAt`.
- **Fingerprint** (`ProposalFingerprint.of(picture, touchedDays)`, SHA-256): per touched day the gym sessions as the windows resolve them (template, time, minutes, done, running), sport slots, calendar events (device id + times, not the row id), started, raw planned / skipped / move target / move origin, that night's bedtime. The verdict and ratio are left out — they follow his body through the day.
- **`POST /api/capacity/proposals/{id}/accept`** body `{clientRef}` → the bundle's `CapacityAdjustment` rows. One transaction under `CapacityLock`: a known `clientRef` goes straight to `applyBundle` (replay or 409 reused); otherwise an open proposal's fingerprint is recomputed from a fresh picture and a mismatch → 409 `CAPACITY_PROPOSAL_STALE` (the proposal stays open; the phone asks for new ones).
- **`POST /api/capacity/proposals/{id}/decline`** → `declined` + `decided_at` (again: no-op; another settled state: 409 stale). **`POST /api/capacity/proposals/regenerate?monday=`** (current or next week only, else 400): the week's open proposals → `ignored`; accepted / declined stay; a draft of the same kind for the same day as a declined proposal is dropped; returns the week.
- **The model rephrase** never runs on the request thread or in a transaction: after the rows commit, one task per stored set goes to `applicationTaskExecutor` (the `EventScoringRunner` pattern) and calls `ProposalWordingWriter.word(draft, effects)` (blocking, digit-guarded) under `LlmActorContext.runAs(owner)`. A changed wording is saved in its own short transaction that takes the owner's `CapacityLock` and the row lock **before** re-reading the row (the whole entity is saved, so an earlier read could write `open` back over a fresh accept), and only onto a row that is still open and still carries the template title. A refused task leaves the template words. The writer's model call runs on its OWN small executor (virtual threads, at most 2 at once — only to keep the 45 s timeout), never nested on `applicationTaskExecutor`.

### The live re-plan loop (K3 Task 20, `LiveReplanListener`)

- **Triggers** (all `@Async` + `@TransactionalEventListener(AFTER_COMMIT)`, never on the request thread): biometrics `CheckInSavedEvent`, train `WorkoutFinishedEvent` and `SportSessionLoggedEvent`, wearable `CalendarDaysReplacedEvent`, meal `MealSavedEvent` (create, idempotent create and edit), and wearable's new `DailyMetricsIngestedEvent(owner, dates)` published by `DailyMetricService.ingest` (the Apple Health day totals; a batch carrying neither today nor yesterday — a backfill — runs no pass). None of those features imports capacity.
- **One pass:** TODAY (his zone, injected `Clock`) is re-read through the model-free day path `CapacityDayService.history(owner, today, today)` (stored or rule scores, never starts a model call), plus whether a still-planned gym session of today overlaps a timed calendar event (`CapacityTrainPort.sessions` + `CapacityCalendarPort.events`). Then one transaction under `CapacityLock` compares it with `capacity_live_state` (one row per owner: `day`, `verdict`, `collides`, `proposed_at`): a new day (or no state) compares against an implicit „rendben, no collision" reading, so a day already szoros / túl sok or colliding at its first trigger proposes too; the verdict worse by ≥ 1 step (laza < rendben < szoros < túl sok) or the session started colliding → `ProposalService.proposeToday`; otherwise the reading replaces the stored one (a better day lowers the bar).
- **Rate limit:** at most one today-proposal per `mezo.capacity.live.min-interval` (PT3H), from `proposed_at`. A worsening held back by the interval leaves the stored reading unchanged, so the first trigger after the interval still sees a worse day. `proposed_at` moves only when a proposal about today was stored.
- **`proposeToday`** (inside the listener's transaction, lock held): a week with no proposal yet gets its whole set, exactly as the first week read (otherwise that read would see a non-empty week and never fill the other days); otherwise the generator runs on a fresh picture and only the top draft whose day is today is stored (facts `live: true`), unless a proposal of the same kind for today is open, accepted, declined or undone (ignored / expired ones release it). Words are the template's; the model rephrase is handed to the background after commit (`rephraseLater`). The listener never throws.
- Tests `LiveReplanListenerIT` (worseningByAStepCreatesTodayProposal, sameVerdictCreatesNothing, rateLimitedToOnePerThreeHours, alreadyHeavyAtFirstTriggerProposesWhenWeekHasProposals, healthBackfillOfOldDaysRunsNoPass) drive the real calendar PUT with a pinned clock.
- **The phone:** the Ma wall's `kapacitas` source (`kapacitasWallCandidates`) — one `.improves` card (rank 0.85) while the current week has an open proposal, `.expires` (deadline = the session start) for an open today-proposal while today's session is under three hours away. See [`boop-ios.md`](boop-ios.md).
